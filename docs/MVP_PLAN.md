> 지금 앱은 화면이 거의 갖춰졌지만, 핵심 약속인 **"내 걸음으로 초록불 안에 건널 수 있는지 숫자로"**를 지킬 수 없다. 숫자가 의존하는 입력(방향 코드·횡단 길이·점멸 의미·요일)이 아직 검증되지 않았기 때문이다. MVP는 **숫자 없이도 정직하게 쓸모 있는 단계(MVP-0)**와 **횡단 하나마다 증거가 갖춰진 곳에서만 숫자를 여는 단계(MVP-1)**로 나눠 만든다. 화면 작업과 데이터 검증은 **병렬**로 한다.

## 3. 팀 합의 [팀 합의]

1. **숫자는 임시값으로 열지 않는다.** `~`만 붙인 큰 숫자 금지(PRODUCT_SPEC §6). 틀린 "여유"가 더 위험하다(Sally 반박 R1, John 대응).
2. **gate는 제품 전체가 아니라 횡단 하나마다**, 방향·길이·점멸 의미·날짜 근거가 모두 갖춰진 곳만 연다(Winston). 구역 밖은 '모름'.
3. **숫자가 닫혀 있는 동안에도 보여줄 수 있는 사실**이 있다: 계단(5,294구간)·오르막(추정)·큰길 횡단 개수·교차로 단위 이력 유무·우회 거리(Winston §3). 단, 횡단 단위 이력은 방향이 확정되기 전에는 쓰지 않는다(앱이 쓰는 방향 키까지 맞는 곳 35.9%).
4. **화면 작업과 데이터 검증은 병렬**로 시작한다. 데이터가 기준을 못 넘으면 닫힌 상태로 출시한다(Amelia).
5. 지금 코드는 화면을 더 얹기엔 건강하다(Node 시험 4종·pytest 59·화면 시험 통과). 막는 것은 **gate 근거를 담는 구조가 없다는 것**과 **화면 시험이 CI 밖이라는 것**(Amelia).
6. 프레임워크·번들러 전환은 하지 않는다. 새 코드부터 순수 함수로 분리하고 기존은 건드릴 때만 옮긴다(Amelia, Winston 동의: gate·여유 계산만 DOM 없는 모듈로).
7. 첫 공개는 소수 학습용. 외부 문구에서 "숫자는 준비 중"을 앞세운다(John).

## 5. MVP 정의 [중재안]

**MVP-0 (숫자 닫힘, 소수 학습용 공개)** — 약속: "서울에서 걷기 전에, 건널 횡단이 몇 곳이고 그중 아는 곳이 몇 곳인지 미리 봐요."
- Must: 설문 2단계(건너뛰기), 홈과 `내 위치로 출발`, 위치 실패 시 지도에서 출발 선택, 공개 장소 검색, 결과(여유 있는 길/빠른 길, `정보 없는 횡단 N곳`, 계산 기준), 지도층 `이력 있음 / 미확인`, gate 안전 장치(fail-closed, `?demo=1` 격리), 평일/주말 분리와 '모름', 금칙어 점검, 배포 확인, **실제 휴대전화 완주 1회**
- Sally 18프레임 중 14개(crossing-detail은 MVP-1), 구현 결함 12건 수정(홈 `횡단 정보 표시` 토글 제거, 걷는 중 `시간 0초`, 범례의 점선 `?` 등)
- 성공·반증: John 문서 §4(5명 걷기, 인터뷰, 정직 표시 이해). 중단 조건: 첫 화면 가치 시험(S4)이 0명이면 공개를 멈추고 gate 작업을 앞에 둔다

**MVP-1 (검증 구역에서 숫자 열림) = 'MVP 완료'** — 약속: "내 걸음 기준으로 건널 여유가 몇 초인지, 근거와 함께."
