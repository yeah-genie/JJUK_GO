# 실시간 보행 신호 지도 설계 (2026-10-30)

**지금 상태: 구조는 만들었고, 실제 데이터 연결은 안 됐다(미연결).** 공개 앱에서는 꺼져 있어 아무것도 그리지 않는다.
시험 데이터(`SIGNAL_LIVE_MOCK=1`)로 화면 흐름만 확인했다. 시험 데이터는 실제 신호가 아니며 실제 기능으로 보지 않는다.

## 1. 세 가지 정보는 의미가 다르다
| 정보 | 뜻 | 화면 |
|---|---|---|
| 횡단 시간 지도 | 내 속도로 건너는 데 걸리는 시간(길이 ÷ 속도). 신호와 무관 | 홈의 '횡단 시간 지도' 모드(기본 꺼짐). 회색·노랑·주황 선 |
| 예상 신호 대기 | 과거 신호 기록으로 추정한 경로별 대기 | 결과 화면 비교표의 숫자. 지도 색 없음 |
| **실시간 보행 신호** | 제공기관이 **마지막으로 관측한** 신호 상태 | 확대(16 이상)했을 때 검증된 횡단보도에 배지. 초록 원+‘보행’, 빨강 사각+‘정지’, 점선 원+‘?’(모름) |

- 색만으로 말하지 않는다: 모양(원/사각/점선)과 글자(보행/정지/?)를 같이 쓴다.
- 횡단 시간 지도를 켜면 실시간 배지는 숨긴다(색이 섞이지 않게).
- '보행' 표시는 건너도 된다는 판정이 아니다. 설명창에 "지금 불과 다를 수 있어요. 건널지는 실제 신호를 보고 정해 주세요"를 항상 둔다.
- 현재 초록이라는 이유로 경로를 바꾸지 않는다(도착할 때 신호는 다르다). 길찾기의 예상 대기와 분리.

## 2. 공식 데이터에서 확인한 것 / 아직 모르는 것
**확인(우리 수집 기록·문서)**
- 새 API(10381) 주소 `v2xSignalPhaseTimingFusionCurrentInfo/1.0`, 요청 칸 `itstId`(필수)·`apikey`·`type`·`pageNo`·`numOfRows`. 필드 이름 규칙은 옛 API·일별 파일과 같다.
- **우리 키로 새 API를 부르면 `http_404`**(2026-10-30 수집기 기록 `meta/call_log.csv`, 3:32~4:07 UTC 3건). 옛 API는 같은 키로 성공. → 새 API 사용 신청(승인)이 필요한 것으로 추정.
- 옛 API: 키당 **300초에 1번**(429 `V2X_REPEAT_CALL_LIMIT`, 거절된 호출도 300초를 다시 시작, 2026-10-28 실측). 한 번 부르면 그 시각이 속한 1시간의 1초 단위 기록(최대 약 2,200행)이 온다. 11/15 종료.
- 잔여 시간 단위: 옛 API·일별 파일은 **0.1초**(연속 1초 메시지에서 약 10씩 줄어듦, 실측). 새 API는 미확인.
- 방향: 보행 코드 et=북쪽 다리, st=동쪽, wt=남쪽, nt=서쪽(2026-10-29, 보행·차량 동시 녹색 16/17 + T자 교차로). 대각 코드는 미검증이라 쓰지 않는다.
- 공통 이용안내: 하루 1,000회.

**모름**
- 우리 키에 실제 적용되는 하루 한도·증량 조건, 새 API에도 300초 제한이 있는지(키 기준인지 교차로 기준인지)
- 새 API의 실제 갱신 주기·지연 분포, 행 정렬(최신이 먼저인지), 잔여 시간 단위·기준 시각
- `permissive-Movement-Allowed`가 녹색 점멸인지(그래서 지금은 색을 주지 않는다)
- 교차로별 방향 코드가 실제 어느 횡단보도인지(교차로마다), 한 다리에 횡단보도가 여럿인 경우
- 실시간 데이터를 다시 보여 주는 것이 이용 약관상 괜찮은지

## 3. 호출 예산 (지금 조건으로 계산)
- **키 1개 · 300초에 1번(옛 API 조건):** 하루 최대 약 283번. 교차로 N곳을 돌아가며 부르면 한 곳을 다시 보는 간격 ≈ 5×N분. 보행 신호 주기는 대개 120~160초라 **5분 전 상태는 이미 지난 신호다.** 이 조건으로는 실시간 색 지도를 정직하게 만들 수 없다.
- **하루 1,000번만 제한이라면:** 한 곳을 주기마다 한 번 보면 하루 약 576번 → 하루 종일 볼 수 있는 곳은 약 1.7곳. 5곳이면 '누가 보고 있을 때만' 하루 약 5시간.
- 예: 외부 호출 5초마다 = 하루 17,280번 → 어떤 공개 한도로도 불가.
- **수집기와 키 충돌:** GitHub 수집기가 같은 키로 5분마다 계속 부른다. 같은 키를 앱이 쓰면 둘 다 막힌다. → **앱 전용 키를 따로** 받아 Vercel 환경변수 `TDATA_LIVE_API_KEY`에만 둔다.
- 결론: 새 API 승인 + 실제 한도 확인 전에는 '실시간'을 약속할 수 없다. 한도가 이대로면 "N분 전 관측"을 보여 주는 지연 표시가 최대다.

## 4. 만든 구조
```
브라우저(지도 확대 16+, 화면에 보이는 검증된 횡단보도만)
  └ 15초마다(탭 숨기면 멈춤, 돌아오면 즉시) GET /api/signal-live?ids=…(최대 5곳)
       └ Vercel 함수 api/signal-live.js
            ├ Redis sig:live:{교차로} 읽기(공유 캐시: 같은 교차로를 여러 명이 봐도 한 값)
            └ 가장 오래된 교차로 1곳만 '필요하면' 외부 호출:
                 · sig:lease:upstream  SET NX PX(최소 간격, 기본 305초) → 키 전체에서 한 요청만
                 · sig:budget:{날짜}   INCR(하루 예산, 기본 200) → 넘으면 안 부름
                 · 받은 행 중 원천 시각(trsmUtcTime)이 가장 최근인 행만, 더 최신일 때만 저장(Redis Lua, 늦게 온 옛 응답 무시)
```
- **수집 주체와 수명:** 서버리스라 요청이 끝난 뒤 도는 타이머는 없다. 외부 호출은 '보는 사람이 있을 때 들어온 요청'이 한다. 아무도 안 보면 안 부른다.
- **신선도:** 마지막 HTTP 성공 시각이 아니라 **원천 관측 시각** 기준. 기준값(`max_source_age_s`)은 지연을 실제로 잰 뒤 정한다. **정하기 전(null)에는 색을 주지 않는다.**
- **색을 주는 조건:** 검증된 횡단보도(`config/live_signals.json`의 verified) + 신선함 + 상태가 보행/정지. 그 밖(지연, NULL, 꺼짐, 점멸 미확인, 방향 미확인, 연결 끊김)은 중립 '?'와 이유.
- **잔여 시간:** 원본 값만 저장하고 화면에는 쓰지 않는다(단위·기준 시각 검증 전). 0초가 돼도 다음 색을 지어내지 않는다.
- **갱신 중 화면:** 지도 중심·확대·열어 둔 설명창은 그대로, 바뀐 배지만 고친다(시험으로 확인).
- **SSE/WebSocket:** 쓰지 않는다. 원천이 5분에 한 번이면 전송 방식을 바꿔도 더 새로워지지 않는다.
- 파일: `api/signal-live.js`, `api/_lib/live-signals.js`, `docs/prototype/src/live-signals.js`, `config/live_signals.json`, 시험 `scripts/check_live.cjs`.

## 5. 켜기 전에 실제 데이터로 확인할 것 (순서)
1. T Data에서 10381 사용 신청 → 수집기 기록(`meta/endpoints.json`)에 새 API 성공과 필드 목록이 찍히는지.
2. 앱 전용 키 발급(여러 키 사용이 약관상 되는지 확인) → Vercel 환경변수 `TDATA_LIVE_API_KEY`, `TDATA_LIVE_URL`.
3. 새 API 한도: 300초 제한 유무와 기준(키/교차로), 하루 한도. 수집기를 잠시 멈춘 밤에 1~2번만 시험(거절된 호출도 창을 다시 시작하므로 부딪혀 보지 않는다).
4. 지연 분포: 원천 시각과 받은 시각 차이를 며칠 모아 `max_source_age_s`를 정한다.
5. 행 정렬: 최신 행이 앞이면 `numOfRows`를 줄인다(지금 2,200).
6. 잔여 시간 단위: 연속 응답에서 값 감소 폭으로 확인.
7. 횡단보도 연결: 교차로별 방향 코드 ↔ 지도 횡단보도. 사용자는 현장 확인을 할 수 없으므로 **데이터 대조로만** 한다(보행·차량 동시 녹색, 일별 기록의 방향별 주기, 앱 그래프의 `sig`/`dir` 간선). 통과한 곳만 `verified: true`와 근거(`evidence`)를 적는다.
8. 3~5곳만 `enabled: true` → 색을 보여 준 시간 비율·지연·예산 사용량을 재고 보고.
