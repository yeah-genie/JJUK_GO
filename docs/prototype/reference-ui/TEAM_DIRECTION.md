# BMAD PM·UX 팀 공통 방향 — 2026-10-31

검토: John(PM)·Sally(UX) 역할. 설치된 BMAD 역할 스킬과 설정을 읽고 사용자 요청에 맞춰 검토했다. 이 문서는 제품 방향과 구현 확인 사항이며, 새 시각 디자인 제안이나 운영 배포 승인이 아니다.

## 사용자가 정한 방향

**쭉고는 가장 짧은 길만 찾지 않는다. 조금 더 걸리더라도 내 걸음과 이동 조건에 맞춰 부담을 덜 수 있는 길을 찾는다.**

‘편한 길’이라는 말은 비교 근거가 있을 때만 구체화한다. 예: ‘2분 더 걸으면 확인된 계단 1구간을 피할 수 있어요’. 시간만 늘고 계단·경사·횡단 등의 개선이 없다면 더 편한 길을 꾸며 내지 않는다. 네이버·카카오가 이런 서비스를 할 수 없다고 단정하지 않는다. 쭉고가 검증할 가치는 **내 조건과 허용 추가 시간 안에서 무엇이 줄었는지 이해하고 선택하는 경험**이다.

## 역할별 합의

- **PM:** 검색 후 바로 걷기를 기록하는 것보다, 선택한 경로가 왜 내게 맞는지 알고 출발하는 흐름이 먼저다. ‘편하다’는 종합 점수보다 계단·급경사·오르막·횡단의 실제 차이를 말한다.
- **UX:** 사용자가 모르는 속도 숫자를 강요하지 않는다. 자동 학습이 기본이며, 측정 전·학습 중·직접 설정을 구분한다. 기존 첨부의 5개 화면 순서와 정보 밀도 안에서 상태를 설명한다.
- **공통:** 네이버 지도는 지도 표현과 좌표 표시를 맡을 수 있다. 편한 경로를 고르는 계산·보행 조건·검증된 데이터의 한계는 쭉고가 책임진다. 지도 연동을 곧 네이버 보행 길찾기 API 연동으로 설명하지 않는다.

## 현재 계산과 연결 확인

`src/app.js`의 `computeTrip()`은 보행 그래프의 후보들을 계산한다. `short`는 보행 시간이 짧은 후보이며 `pickAlternative()`가 허용 추가 시간·지표 개선·과도한 우회·다른 지표 악화 등의 조건을 검사한다. 조건을 통과한 후보가 있으면 `jjuk`에 넣고, 없으면 `jjuk`도 `short`를 가리킨다. `refreshSims()`는 같은 길이면 `focus='jjuk'`으로 정리한다.

새 프로토타입은 `refFind()`에서 이 계산을 사용하고 `state.routes[state.focus]`를 지도와 걷기 화면에 넣는다. 실제 모드에 가상의 추가 경로를 만들지는 않는다. 다만 검색 장소를 고를 때 `focus`, `dep`, 이전 고정 경로를 함께 초기화해 이전 선택이 새 OD에 남지 않게 하는 것이 안전하다.

## 우선 조치할 항목 — 최대 다섯 가지

| 우선 | 관찰한 문제 | 원본 구조 안에서 할 조치 | 코드 위치 |
| --- | --- | --- | --- |
| 1 | 자동 학습 OFF가 수동 모드로 전환되면 마지막 학습값 대신 기본 수동 속도로 경로 시간이 갑자기 바뀔 수 있다. | OFF는 학습만 중지하고 마지막 학습 속도를 유지한다. 수동 속도를 고를 때만 수동 모드로 바꾼다. | `ui.js`의 `ref-auto` 처리, `refPace()` |
| 2 | `길찾기`를 누르면 계산 직후 걷기/GPS 기록이 시작된다. 사용자는 계획만 보려 했을 수 있고, 왜 편한지도 출발 전 보지 못한다. | 새 결과 화면을 추가하지 않는다. 같은 걷기 화면의 ‘계획 미리보기’ 상태에서 기존 안내 문장에 `routeSummary()` 또는 `compareLine()`의 실제 차이를 보여 주고 기존 버튼 자리에서 걷기 시작을 명시적으로 선택하게 한다. 시작 후 원본의 일시정지/종료 상태로 전환한다. | `refFind()`, `refShow()`, `refWalking()` |
| 3 | 오늘의 걸음에서 실측 기록이 없어도 계획 경로 전체의 횡단·계단·경사 수치가 표시된다. 실제 지나간 횟수로 오해할 수 있다. | 현재 카드 순서는 유지하고 보조 문구에 ‘선택한 계획 경로 기준’이라고 명시한다. 실제 이동 거리·시간은 GPS 기록이 있을 때만 표시한다. 계획 경로 수치와 실제 기록을 합산하지 않는다. | `refSummary()`의 소개/`route-facts` |
| 4 | 급경사 토글은 선호를 저장하지만 독립 회피 조건으로 계산에 연결되지 않았다. 토글이 켜지면 이용자가 완전 회피를 기대한다. | 예시 모드는 원본을 그대로 재현한다. 실제 모드는 기존 자리의 보조 문구/사용 가능 상태로 준비 중임을 명시하고, 독립 회피 기능을 검증하기 전 완전 회피를 약속하지 않는다. | `refSettings()`, `ref-slope` 처리 |
| 5 | 실제 종료 한 문장은 일반적인 ‘내 걸음으로 걸었어요’라서 더 걸은 시간과 줄인 부담이 드러나지 않는다. | 기존 노란 한 문장 영역에 비교 근거를 연결한다. 대안이 있으면 `compareLine(short,jjuk)` 등 확인된 차이를, 없으면 ‘설정한 시간 안에 부담을 줄이는 다른 길이 없었어요’를 쓴다. 신호 절약량은 검증 가능한 값이 있을 때만 말한다. | `refSummary()`의 `comfort-summary`, `src/app.js`의 `routeSummary()`/`compareLine()` |

위 항목은 검토 당시 코드 기준이다. 루트 개발자가 반영한 조치는 변경 기록과 실제 코드로 확인한다. 이 문서 작성자는 런타임 코드를 수정하지 않았다.

**구분:** ‘조금 더 걸리더라도 편한 길’은 사용자가 확정한 핵심 방향이다. 같은 걷기 화면 안의 ‘계획 미리보기 → 걷기 시작’은 이번 BMAD PM·UX의 제안이며, 루트 개발자가 새 화면을 늘리지 않는 최소 구현 판단으로 채택했다. 이를 사용자가 별도로 승인한 새 화면 설계라고 기록하지 않는다.

연결할 기존 함수는 `routeSummary(base, alt, focus)`이며 `{badge, headline, sub, pros, cons, wait, kind?}`를 반환한다. `alt`가 없으면 대안 없음 문구를 돌려준다. `compareLine(base, alt)`는 추가 시간과 줄어든 부담을 한 문장으로 묶는다. `state.routes.alt`가 참일 때만 실제 대안을 전달한다. 긴 상세 문장을 상단 큰 숫자 자리에 그대로 늘여 넣지 말고, 기존 강한 제목/작은 보조 문장 계층을 유지한다.

## 시작 로고

사용자가 운영 Vercel의 첫 쭉고 로고를 참고해 추가하도록 요청했다. 기존 로고 도형·쭉고 글자·노랑 강조를 재사용하는 범위가 새롭게 승인된 시각 예외다. 다섯 본 화면은 첨부 기준을 계속 유지한다.

- 첫 방문에 약 3.2초를 보여 주는 기존 정책을 재사용한다. 건너뛰기를 제공한다.
- 반복 진입/이미 준비된 화면에는 매번 3.2초를 강요하지 않는다.
- 실제 지도·자료가 아직 준비되지 않았다면 ‘불러오는 중’을 사실대로 표시한다. 로고 대기 시간을 데이터 로딩 성공으로 취급하지 않는다.
- 모션 감소 환경에서는 움직임을 줄여도 로고의 식별은 유지한다.

## 수용 기준

1. 첨부 기준 5개 화면의 시각 순서·CTA 위치를 유지한다. 팀 검토를 이유로 새 대시보드나 별도 디자인을 추가하지 않는다.
2. 실제 OD에서 대안이 있으면 추가 시간과 줄어든 요소가 실제 계산값과 일치한다. 없으면 같은 길을 대안이라고 포장하지 않는다.
3. GPS 전·측정 중·권한 거절·위치 끊김이 구분되며, 실제 이동 기록을 예시 데이터로 채우지 않는다.
4. 출발 전 화면 탐색이 실제 걷기 학습이나 기록으로 저장되지 않는다.
5. 운영 소스/신호 검증 gate/기본 브랜치/운영 배포는 사용자 검토 전 바꾸지 않는다.
