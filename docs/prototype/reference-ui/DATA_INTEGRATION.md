# BMAD 시스템 설계 검증 — 실제 데이터 연결

검토: Winston / 시스템 설계, 2026-10-31 KST. 운영 소스·신호 신뢰 조건·워크플로를 수정하거나 수집을 실행하지 않았다. 읽기 전용으로 GitHub 현재 상태와 코드 연결을 확인했다.

## 결론

**실제 보행 그래프와 과거 신호 자료는 연결돼 있다. 5분마다 성공한 실시간 신호가 앱으로 그대로 들어오는 구조는 아니다.** 새 UI는 기존 엔진과 같은 `seoul/` 자료를 읽는다. `sample=1`의 초록 17초/경로/통계는 별도 시각 예시이며 계산이나 기록으로 들어가면 안 된다.

수집 저장(`data` 브랜치), 과거 패턴 가공(기본 브랜치의 `seoul/signal-hours`), 앱 배포(그 커밋의 정적 자료), 현장 실시간 신호 API는 서로 다른 단계다. 한 단계가 돌아간다고 나머지 단계가 최신이거나 신뢰됐다는 뜻은 아니다.

## 새 UI 어댑터의 중요한 연결 지점

1. **현재 시각 초기화:** 기존 `screens.js`의 `renderResult()`는 실제 모드 새 계산 전 `BASE=nowSeconds()`를 한다. 새 `refFind()`는 `computeTrip()`를 직접 호출하므로 이 초기화를 복원해야 한다. 빠지면 기본값 08:40의 과거 패턴을 조회할 수 있다. 운영 알고리즘 변경이 아니라 호출자에서 기존 준비 단계를 보존하는 수정이다.
2. **실제 모드 표시:** 기존 엔진의 `route.m.waitKnown`, `waitUnknown`, `waitTotal`과 `TRUST` 판정을 따른다. 알려지지 않은 신호를 0초로 쓰지 않는다. 샘플의 ‘17초 남음’이나 ‘2분20초 절약’을 실제 결과의 기본값으로 가져오지 않는다.
3. **실시간/패턴 레이어:** 전용 부팅은 기존 `LIVE.init()`/`SIG.start()`를 자동으로 실행하지 않는다. `LIVE.active()`는 `XW.on`도 확인한다. 단지 함수를 호출한다고 실시간 신호가 생기지 않으며, 현재 설정은 꺼져 있다. 현재 새 UI 실제 callout이 회색인 것은 데이터가 검증되지 않았다는 뜻이다.
4. **급경사:** 기존 경로 지표에는 들어가지만 새 토글의 독립 강제 제외 조건은 없다. 선호 저장을 실제 경로 제약 완료로 쓰지 않는다. 계단 회피는 기존 프로필의 `avoidSteps`가 실제 탐색에 반영된다.
5. **사용자 속도/시간 예산:** `applyPace()` 후 계산해야 하며, 추가 보행 예산은 `state.budget`에 전달한다. 자동 학습에 유효 GPS만 쓰는 기존 필터를 유지한다.
6. **네이버 지도:** 배경 지도와 오버레이를 바꿔도 계산된 보행 경로 좌표·횡단 방향·계단·지형 지표는 기존 엔진에서 받는다. 지도 공급자를 바꿨다고 데이터 coverage나 실시간 신호의 검증 수준이 올라가지는 않는다.

## 메타데이터 읽기 모듈

`data-status.js`는 `window.JJUKGODataStatus.read()`를 제공한다. 운영 엔진과 **같은 배포본**의 `seoul/signal-plans.json` 및 `/api/signal-live?config=1`만 읽는다. 원격 GitHub의 메타데이터만 새로 받아 놓고 실제 계산 자료는 오래된 상태를 ‘최신’이라고 표시하는 일을 피한다. 참조 UI에 자동 주입하거나 원본에 없는 새 패널을 만들지 않았다.

- `historical`: 사용 가능 여부, 시작·끝 날짜, 일수, 후보 교차로 수. `mode`는 항상 `historical`이다.
- `live`: 설정 조회 여부, `unknown/mock/disabled/eligible/unverified` 상태, 검증된 횡단 수, `eligible` 여부.
- `eligible`은 API의 표시 자격만 뜻한다. 특정 신호가 신선하거나 지금 초록이라는 뜻이 아니다. 그 판단은 기존 서버/검증 gate의 개별 응답으로만 한다.
- `config=1` 요청은 현재 서버 코드에서 Redis·외부 T Data 호출 전에 반환된다. 이 모듈이 실제 수집 호출을 발생시키지 않는다.
- 키·좌표·개인 경로를 모듈에 저장하거나 전송하지 않는다. 새 데이터 공급 API나 주기적 타이머를 만들지 않았다.

## 배포·동기화 경계

`history.yml`은 04:20 KST에 새 공식 날짜를 수집하고, 없으면 `data` 브랜치 상태 구간을 과거 형식으로 변환한 뒤 시간별 자료와 운영 엔트리를 커밋한다. 현재 그 워크플로는 새 `build_reference_ui.py`를 실행하지 않는다. 따라서 프로토타입 브랜치가 새 기본 브랜치 자료를 저절로 따라가지는 않는다.

운영 승인 전에는 기본 브랜치 병합이나 워크플로 변경 없이 최신 자료를 받아 별도 빌더를 다시 실행한다. 운영 통합이 승인되면 배포가 사용하는 커밋에서 데이터 가공 → 두 엔트리 빌드 → 검증 순서가 일치하도록 CI를 연결한다. 브라우저가 수집 브랜치의 미검증 원시 상태를 직접 초록 신호로 사용하는 방식은 택하지 않는다.

## 검증 방법

BMAD 구성의 `uv` 실행기는 설치돼 있지 않아 같은 표준 Python 스크립트로 역할 설정과 사용자 설정을 해석했다. 별도 사전/후속 activation hook은 없었다. 네트워크 조작 없이 GitHub connector의 GET으로 실행·커밋·공개 로그·기준 메타데이터를 확인했다. 수집 재실행·API 호출·설정 gate 변경·배포는 하지 않았다.

Node VM에서 날짜 정렬·중복/비정상 날짜 제거, disabled, mock, eligible, unknown, unverified 분리와 외부 수집을 유발하는 `ids=` 요청이 없음을 검증해 통과했다. JS 구문 검사도 통과했다. 실제 위치 이동·현장 신호 대조와 API 승인 작업은 별도다.

## 추가 진단 — 최근 시간 초과/404의 범위

아래는 기존 코드·공개 수집 로그·워크플로 메타데이터만 읽어 좁힌 결과다. T Data에 시험 요청을 보내거나 비밀 키를 읽지 않았다. 원인 가정을 바탕으로 API 주소·시간 제한·횟수·수집 대상을 바꾸지 않았다.

### 확인된 사실

- [실행 41118249209](https://github.com/yeah-genie/JJUK_GO/actions/runs/41118249209)의 checkout, Python 설치, data 브랜치 준비는 성공했고 `Collect` 단계가 진행 중이었다. 최근 실패는 이 단계에서 발생한다. 현재 증거로는 Vercel 배포나 GitHub checkout 실패가 직접 원인이 아니다.
- [endpoints.json](https://github.com/yeah-genie/JJUK_GO/blob/data/meta/endpoints.json)은 성공한 API로 옛 `v2xSignalPhaseTimingFusionInformation`만 기록한다. 첫 성공은 03:37:35 UTC, 마지막 성공은 19:53:33 UTC, 누적 성공 기록은 71회다. 새 `v2xSignalPhaseTimingFusionCurrentInfo`의 성공 항목은 없다. 새 API가 이 키로 실제 성공했다는 증거가 없다.
- `primary_failed_at`은 20:34:07.506 UTC이다. 이는 최신 `http_404` 기록(20:34:07 UTC)과 맞는다. 코드상 이 값은 새 기본 API 실패 때만 갱신된다.
- 두 대상(2217, 20458)에서 각각 시간 초과 세 번 뒤 404 한 번이라는 묶음이 보인다. `timeout_s=20`, `max_retries=3`이며, API 사이와 재시도 사이 모두 305초 간격을 둔다.
- 옛 API 우선 순서, 시간 초과 세 번, 새 API 404를 모의 응답으로 재현했다. 실제 네트워크 없이 기존 클래스에 가짜 시계와 응답만 넣어 `옛 API ×3 → 새 API ×1` 및 305초 간격 유지가 확인됐다.
- [마지막 성공 커밋 fbfe56a](https://github.com/yeah-genie/JJUK_GO/commit/fbfe56a039ee8bada022695c14603294fed5215d)는 로그만 바뀐 것이 아니라 `segments/2026/10/31/044840.csv.gz`도 새로 추가했다. 따라서 적어도 이 회차는 상태 구간 파일 저장까지 이어졌다. 파일명은 회차 시작 시각으로 만들어지므로 실제 제공기관 관측 시각/응답 시각으로 그대로 해석하지 않는다.

### 근거로 좁힐 수 있는 원인

| 현상 | 현재까지 좁힌 범위 | 아직 모르는 점 |
|---|---|---|
| 옛 API의 `TimeoutError` | 옛 API에서 네트워크/응답 읽기가 제한 시간 안에 끝나지 않은 것으로 보인다. 같은 주소의 이전 71회 성공은 확인된다. | 제공기관 지연, 중간 네트워크, 특정 교차로 처리, 요청량 2,200행의 영향 중 무엇인지는 구간별 소요시간/응답 단계 로그가 없어 구분 못 한다. |
| 새 API의 `http_404` | 실패 시각과 `primary_failed_at`, 우선 순서/재시도 코드를 함께 보면 새 기본 API의 404라는 해석이 강하다. 이 API의 성공 기록은 없다. | 실제 서비스 경로/버전 등록 문제인지, 서비스 신청 상태에 따라 404를 반환한 것인지, 제공기관 장애인지 확정할 응답 근거가 없다. 404만으로 ‘키가 틀렸다’고 단정하지 않는다. |
| 5분마다 최신 자료가 안 생김 | 305초는 **키 전체 요청 간격**이다. 한 대상의 세 번 재시도와 API fallback만으로 15분 이상 쓸 수 있다. 전체 교차로를 번갈아 조회하므로 대상별 5분 갱신이 아니다. | 실제 제공기관 관측 시각과 유효 행 수가 회차별 요약과 연결되지 않아 성공 응답이 얼마나 신선했는지는 별도 확인이 필요하다. |
| Actions가 계속 실행/성공으로 보임 | `collect_loop.sh`는 한 번 수집 실패를 경고로 남기고 다음 회차를 계속한다. data 커밋은 실패 로그/호출 예산만 바뀌어도 생긴다. | 실행 중/성공 표시로 성공 자료 수를 추론할 수 없다. |

최근 8건에는 429가 없다. 그러므로 이 구간을 호출 한도 초과로 설명할 근거는 없다. 기존 305초 제한을 줄이거나 무작정 재시도를 늘리는 수정은 하지 않는다. `urlopen(timeout=20)`의 시간 초과는 연결/소켓 읽기 중 발생할 수 있으므로 전체 HTTP 처리 시간의 정확한 측정값으로 간주하지 않는다.

### 가장 작은 수정 제안 — 아직 적용하지 않음

1. **실패 로그부터 구분한다.** `call_log.csv`에 쿼리·키를 제외한 API 이름, 시도 번호, 소요시간, 실패 분류를 남긴다. 현재 실패 행에는 API 이름이 없어서 위 진단도 시각과 코드의 조합에 의존한다. HTTP 오류 본문 전체나 요청 URL은 기록하지 않는다.
2. **응답과 유효 데이터 성공을 분리한다.** 현재 `_get()`은 HTTP 본문 JSON 해석 뒤 `ok`를 기록하고, `check_error()`/레코드 추출은 그다음 `fetch()`에서 한다. `ok`만으로 유효 신호 행을 받았다고 판단할 수 없다. 기존 `ok` 의미를 조용히 바꾸기보다 `http_json_ok`, `data_ok/empty/api_error`, 받은 행 수와 유효 상태 구간 수를 구분해 기록한다.
3. **새 API의 신청/경로 상태를 먼저 확인한다.** 서비스 화면에 표시된 새 API 경로와 이용 승인 여부를 사용자/제공기관이 확인해야 한다. 새 주소를 추측해서 수정하거나 정상 성공 확인 전 옛 API fallback을 제거하지 않는다. 현재 증거로 확정 가능한 자동 수정이 아니다.
4. **그다음 반복되는 결정적 실패의 낭비를 줄인다.** 새 API가 확실히 승인 전/경로 오류라고 확인되면, 반복 404에 대한 endpoint별 유예를 두고 검증된 주소를 사용하도록 최소 조정할 수 있다. 현재 `_ordered_urls()`는 옛 API를 먼저 시도하더라도 그쪽이 실패하면 새 API를 다시 호출한다. 최근 주된 지연은 단순 폴링 간격보다 이 재시도/fallback 경로와 연결돼 있다. 단, 설정 변경 전 승인 상태와 오류 분류 증거가 먼저다.
5. **건강 표시는 마지막 성공 자료로 판단한다.** Actions 상태/커밋 시각과 별도로 대상별 마지막 유효 제공기관 관측 시각, 받은 자료 수, 연속 실패 횟수를 쓴다. 이는 관리·검증용 정보이며 사용자에게 초록 신호 안내를 허용하는 근거를 대체하지 않는다.

이 진단은 수집기를 바꾸기 위한 준비 자료다. 신호 gate, `enabled`, 검증된 횡단 목록, 실제 초록/잔여초 표시 조건은 그대로 유지한다.
