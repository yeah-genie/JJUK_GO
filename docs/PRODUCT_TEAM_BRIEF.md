# 쭉고 제품·디자인·개발 팀 기준

갱신: 2026-10-29 (Asia/Seoul). 다음 Codex·Claude 작업자가 같은 제품 기준으로 이어가기 위한 문서다. BMAD의 기획·UX·개발·QA 관점으로 운영하며, 이 문서 자체가 BMAD 프로젝트 설치·역할 등록·배포 완료를 증명하지는 않는다.

## 제품의 중심

10/29 추가 검토: [차별성 팀 보고서](../reports/DIFFERENTIATION_TEAM_REVIEW_2026-10-29.md). 아래 방향은 제품의 판단 기준이며 경쟁 우위가 이미 입증됐다는 뜻은 아니다. 편한길/계단회피/경사정보/저장 단독 기능은 경쟁사와 겹친다. 좁은 실사용 동선에서 평소 실제길·경쟁사 적절옵션 대비 추가가치를 먼저 검증한다. 새 타겟과 실험 설계는 제안 단계다.

**비슷한 시간이면, 덜 힘들게 걷는 길.**

사용자가 허용한 추가시간 안에서 계단·오르막·신호의 차이를 보고 길을 선택하게 한다. ‘55초 뒤 출발’은 선택한 경로에서 살펴볼 보조 기능이다. 기본 결과의 대표 약속으로 되돌리지 않는다.

## 화면과 기능의 판단 원칙

1. **선택 이유부터 보여준다.** 예상 시간과 함께 줄어드는 계단·오르막·신호를 보여준다. 타이머, 종합 점수, 긴 설명이 첫 선택을 대신하지 않는다.
2. **불리한 차이도 함께 보여준다.** 오르막을 줄이는 대신 계단이 늘면 둘 다 표시한다. ‘덜 힘든 후보’가 모든 요소에서 우월하다는 뜻이 되지 않게 한다.
3. **추가시간은 사용자가 정한다.** 특정 우회시간을 모두가 좋아한다는 가정을 두지 않는다. 같은 시간 조건과 추가시간 조건을 비교할 수 있어야 한다.
4. **동일 경로와 데이터 부족을 구분한다.** 후보가 같으면 개선을 꾸며내지 않는다. 자료가 없는 구간을 계단 없음·평지·대기 없음으로 취급하지 않는다.
5. **추정의 범위를 지킨다.** 과거 신호, 임시 대기 가정, 거친 지형망은 오늘 현장 관측이나 안전·무장애 보증이 아니다. 근거는 상세에서 확인할 수 있게 한다.
6. **기본 행동은 항상 닿아야 한다.** 패널 높이와 내용 길이 때문에 스크롤이나 선택 경로의 걷기 시작이 막히면 출시 품질 문제다.
7. **조작 설명 대신 기능을 명료하게 만든다.** ‘올려서 비교’류의 군더더기를 추가하지 않는다. 접근성용 이름·키보드 동작은 유지하되 화면을 안내 문구로 채우지 않는다.

## 기본 결과의 정보 순서

1. 선택한 경로의 편안함 관련 차이 또는 같은 후보라는 사실.
2. 허용할 추가시간 선택.
3. 경로별 예상 시간·계단·오르막·신호 비교.
4. 선택한 길로 걷기.
5. 접힌 경로 정보·추정 근거, 선택적인 출발 시각 비교.

이는 정보 위계다. 무조건 계단을 피하라거나 신호보다 경사를 항상 우선하라는 개인 선호 규칙은 아니다.

## 역할과 협업 방식

| 역할 | 맡을 일 | 남길 결과 |
|---|---|---|
| 기획 | 사용자 확인 사항과 제안을 분리하고 이번 작업의 목적·완료 기준을 정한다. | 제품 기준, 우선순위, 미해결 선택 |
| UX·디자인 | 화면 위계·문구·터치/키보드 흐름이 제품 약속과 맞는지 검토한다. | 실제 화면 근거와 수정할 구체적 요소 |
| 개발 | 데이터·시간·경로·상태 관리와 레이아웃을 일관되게 구현한다. | 변경 파일, 재현 가능한 검사, 실패 처리 |
| QA·검증 | 일반 흐름과 경계 상황을 독립적으로 확인한다. | 통과/실패 증거, 기기·환경, 검증하지 못한 범위 |
| 조정 담당 | 의견 충돌을 우선순위로 정리하고 변경을 통합·공개 확인한다. | HANDOFF, 날짜별 논의 기록, 커밋·배포 식별자 |

- 같은 파일을 여러 역할이 동시에 고치지 않는다. 검토자는 발견 사항과 수정 대상을 먼저 남기고 구현 담당이 반영한다.
- 실제로 분담한 작업과 한 세션의 역할별 검토를 구분한다. 역할 이름만 붙여 독립 검증이 끝났다고 하지 않는다.
- 사용자에게 이미 확인된 방향을 반복해서 묻지 않는다. 새로 정해야 하는 선호는 제안으로 표시하고, 그 답과 무관한 수정은 계속한다.
- 논의가 기능을 늘리는 방향으로 흐르면 ‘허용 시간 안에서 덜 힘든 길을 고르는 데 어떤 판단을 더해 주는가’를 먼저 확인한다.
- 사용자 지시가 최우선이다. 과거 문서의 상태 표는 작성 당시 기록이며 최신 HANDOFF·구현 증거와 대조한다.

## 아직 해결되지 않은 제품 충돌

- **편한 길이라는 이름과 현재 점수:** 현재 순위는 대기·멈춤·계단 길이·상승량의 휴리스틱이다. 실제 피로 감소를 검증한 점수가 아니다. UI 개편만으로 추천 방식의 타당성이 확정되지 않는다.
- **작은 지형 차이와 표현 강도:** 약120m 지형망에서 계산한 몇 m 차이를 크게 강조하면 정밀한 개선으로 오해할 수 있다. 현장 오차와 커버리지에 맞춘 표현/강조 임계값은 아직 정하지 않았다.
- **추가시간 구간:** 현재 개편의 같은 시간/+2/+5/+10분은 선택 범위를 넓히는 UI 제안이지 사용자 조사 결론은 아니다. 특히 장거리 보행과 짧은 일상 보행의 허용시간을 같은 기준으로 고정할지는 미정이다.
- **신뢰성과 사용 범위:** 서울 전체 장소 조합의 성공률·정확도를 측정하지 않았다. 일단 검증한 구간의 사용 가능 범위를 넓히며, 임의 조합에서 정확한 길찾기라고 홍보하지 않는다.
- **경쟁 차별성:** 네이버·카카오가 기술적으로 할 수 없다는 주장은 하지 않는다. 구체적 출도착지에서 시간과 불편의 교환을 더 잘 설명하고 실제 선택되는지를 검증해야 한다.

## 이어받을 때

[HANDOFF.md](HANDOFF.md), 최신 [논의 기록](discussions/2026-10-29.md), 이 문서를 읽고 시작한다. 새 작업마다 **목적 → 구현 담당 → 검토 담당 → 실제 증거 → 남은 한계**를 남긴다. 코드 검사, 브라우저 확인, 실제 기기 확인, GitHub push, 공개 배포는 각각의 완료 상태로 기록한다. 이번 문서는 방향 합의이며 현재 수정의 통과·배포 상태는 HANDOFF의 최신 항목을 확인한다.
