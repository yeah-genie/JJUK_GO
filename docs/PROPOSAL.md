# 쭉고 (JJUK GO) — 기획서

> 이 문서는 신호 중심 초기 기획이다. 2026-10-28 사용자 논의·게시물로 확인한 최신 방향은 [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md)의 **‘비슷하게 걸리면, 덜 힘든 길’(신호+경사+계단)**이다. 지하철·버스는 후순위다. 아래 초기 MVP 범위·스택·평가계획을 최신 결정으로 간주하지 않는다.

> 가장 짧은 길이 아니라, **기다리는 시간이 가장 짧은 길**.

- 형태: 4주 학부생 MVP (데이터사이언스 · 딥러닝 응용)
- 대상 지역: 서울 강남구 테헤란로 일대 (강남역–역삼–선릉, 약 2×2km)
- 작성일: 2026-10-27

---

## 1. 배경과 문제

도보 길찾기는 거리(또는 보행시간)만 최소화한다. 하지만 도심에서 실제로 시간을 잡아먹고 짜증을 만드는 건 **신호대기**다. 지도앱이 알려준 최단경로가 빨간불 세 번에 걸려 결국 더 늦게 도착하는 일이 흔하다.

2026년 9월 서울시가 C-ITS 기반 **보행신호 실시간 잔여시간 API**와 **교차로–횡단보도 매핑 데이터**를 공개하면서, 처음으로 "어느 횡단보도가 언제 초록불인지"를 프로그램이 알 수 있게 됐다. 과거 신호이력 파일은 공식적으로 확인되지 않지만, 실시간 API 응답에 *잔여시간*이 들어 있어 듬성듬성 호출해도 신호 패턴을 복원할 수 있다. 그래서 이력은 **자동 수집기로 직접 쌓는다** ([DATA_COLLECTION.md](DATA_COLLECTION.md)).

## 2. 제품 정의

| 항목 | 내용 |
|---|---|
| 한 줄 소개 | 목적지까지 덜 멈추고 걷는 길을 찾아주는 도보 길찾기 |
| 최적화 대상 | `보행시간 + 예상 신호대기시간` (신호 *개수*가 아님) |
| 핵심 경험 | "걷다가 덜 멈추는 경험" |
| 타깃 사용자 | 출퇴근·점심시간 도심 직장인, 대학생 등 매일 같은 구간을 걷는 사람 |

### 경쟁/유사 서비스와의 차이

| 서비스 | 질문 | 비고 |
|---|---|---|
| 네이버/카카오 도보 | "가장 짧은 길은?" | 신호대기 미반영 |
| 그린인 (2026.10) | "내 앞 신호가 언제 바뀌지?" | 동일 C-ITS 데이터, 교차로 2,779곳. 경로 기능 없음 |
| **쭉고** | "어느 길로 가야 덜 기다리지?" | 경로 단위 최적화 |

그린인은 경쟁자라기보다, 이 데이터가 실서비스에 쓸 만하다는 **proof-of-concept**다.

### 안전 원칙

- "지금 뛰면 건널 수 있어요" 같은 안내는 **하지 않는다**.
- 모든 시간은 *예상* 값으로 표기하고, "실제 신호를 반드시 확인하세요" 문구를 상시 노출한다. (서울시 API 이용 안내에도 명시된 사항)
- 제품의 역할은 **길 선택 보조**이지, 횡단 판단이 아니다.

## 3. MVP 범위

**포함**
- 대상 지역 도보 그래프 구축 + 횡단보도–신호 매칭
- 경로 3종: ⚡ 빠른 길 / 🚦 신호 적은 길 / 🚶 쭉 가는 길
- 신호이력 기반 대기시간 추정 및 미래 신호 상태 예측 모델
- 근거리(1~2개) 신호 실시간 보정
- 오프라인 리플레이 시뮬레이션 평가 + 현장 검증
- 웹 화면 3개

**제외**
- 서울 전역 확장, 앱스토어 배포
- 회원/즐겨찾기, 턴바이턴 내비게이션
- 육교·지하도·경사 선호 옵션

### 1주차 첫날 검증 항목 (리스크 1순위)
1. D3가 교차로 1개당 1회 호출인지, 다수 교차로 일괄 조회가 되는지 → 호출 예산 설계가 달라짐
2. 실제 응답의 상태 필드 이름·값 형식 (수집기 probe가 `meta/api_probe.json`에 응답 예시를 자동 저장)
3. D1 노드/링크 ↔ D2 횡단보도 좌표의 좌표계 및 공간 매칭 정확도
4. 대상 지역 내 C-ITS 연동 교차로 수(커버리지)

## 5. 시스템 구조

```
[수집기 cron]   GitHub Actions 15분마다 D3 호출 (일일 예산 70%) → data 브랜치에 csv.gz 적재
      │
[전처리]        D1 그래프 + D2 매칭 → crosswalk ↔ (교차로ID, 방향필드) 테이블
      │
[신호 모델]     횡단보도별·시간대별 주기/녹색 길이 추정 + 미래 상태 예측 모델
      │
[라우팅 API]    FastAPI · 시간의존 Dijkstra → 경로 3종 + 횡단보도별 예상 타임라인
      │           └ 근거리 1~2개 신호만 D3 실시간 조회 (서버 캐시, TTL = 다음 신호 전환 시점)
[웹 프론트]     React + Kakao Map JS SDK · 화면 3개
```

- 스택: Python (geopandas, networkx, PyTorch), FastAPI, React
- 저장소: MVP는 Parquet + 메모리 그래프로 충분. 확장 시 PostGIS.

## 6. 알고리즘

### V1 — 신호 적은 길 (정적 데이터만)

엣지 비용:

```
cost(e) = length(e) / v_walk + λ · 1[e는 신호 횡단보도]
v_walk = 1.2 m/s
```

- λ = 0 → ⚡ 빠른 길
- λ = 대상 지역 평균 적색시간 / 2 → 🚦 신호 적은 길

이것만으로도 "빠른 길 11분 20초 · 신호 6개 vs 안 끊기는 길 12분 40초 · 신호 2개" 비교가 가능하다.

### V2 — 기다림 적은 길 (이력 기반)

D4로 횡단보도별 · 요일유형(평일/주말) · 시간대(30분 단위)별 주기 `C`, 보행 녹색 `G`, 적색 `R = C − G`를 추정한다.
스냅샷 하나는 `상태 + 잔여시간`이므로 곧 "다음 전환 시각" 하나다. 여러 날의 전환 시각을 후보 주기로 접어(phase folding) 가장 잘 정렬되는 `C`와 오프셋을 찾는다. 연속 기록이 없어도 고정주기 신호는 복원된다.

보행자가 주기 내 무작위 시점에 도착한다고 가정하면

```
E[W] = P(적색 도착) · E[대기 | 적색] = (R/C) · (R/2) = R² / (2C)
```

이를 엣지 비용에 더하고, 출발시각 `t₀`에서 시작하는 **시간의존 Dijkstra**를 돌린다. 각 엣지 비용이 도착 시각에 따라 달라지지만, 늦게 출발해서 먼저 도착할 수는 없으므로(FIFO) Dijkstra가 그대로 성립한다.

### V3 — 실시간 보정 + 예측 (딥러닝 파트)

도착까지 남은 시간에 따라 근거를 다르게 쓴다.

| 도착까지 | 근거 | 방법 |
|---|---|---|
| ≤ 2분 | 실시간 | D3 현재 상태 + 잔여시간으로 대기시간을 결정적으로 계산 |
| 2~10분 | 예측 모델 | 도착 시점 `t + Δ`의 보행신호 상태 예측 |
| > 10분 | 이력 평균 | V2의 `E[W]` |

**예측 모델**
- 입력: 교차로별 최근 시퀀스(상태, 잔여시간), 시간대·요일 임베딩, 교차로 임베딩
- 출력: Δ ∈ {1, 3, 5, 10분}별 *녹색 확률* 및 기대대기 회귀
- 구조: GRU (비교: 소형 Transformer)
- **Baseline**: 추정 주기로 현재 위상을 단순 외삽 (정주기 신호라면 거의 정확)
- 모델의 존재 이유: 감응신호, 시간대별 신호플랜 전환, 주기 드리프트 때문에 단순 외삽이 틀어지는 구간을 잡는 것. **baseline을 이기지 못하면 baseline을 쓴다** — 이 비교 자체가 프로젝트의 핵심 결과물.
- 학습/검증: D4 이력 시간순 분할 (앞 3주 학습 / 마지막 1주 테스트, 누수 방지)

## 7. 화면 설계

최신 화면 기획은 [UX.md](DESIGN_SYSTEM.md)와 [프로토타입](prototype/index.html)을 따른다. 아래는 초기 안이다.


1. **검색**
   - 출발지(현재 위치 기본) / 도착지 입력, 출발시각(지금 / 지정)
2. **경로 비교**
   - 카드 3장: ⚡ 빠른 길 / 🚦 신호 적은 길 / 🚶 쭉 가는 길
   - 각 카드: `걷기 12:00 + 예상대기 0:55 = 12:55`, 신호 횡단보도 수
   - 카카오 기본 경로 대비 차이 배지 (예: "카카오보다 55초 빠름 예상")
3. **경로 상세**
   - 지도 위 경로 + 횡단보도 마커
   - 횡단보도별 타임라인: "2분 뒤 도착 · 초록 예상 · 대기 0초", "6분 뒤 · 빨강 예상 · 대기 ~25초"
   - 근거 아이콘: 실시간 / 예측 / 평균 / 신호정보 없음
   - 안전 안내 문구 상시 노출

## 8. 평가 계획

### 8.1 오프라인 리플레이 시뮬레이션 (핵심)
D4 실제 이력을 "정답 신호"로 재생한다.

- 무작위 출발–도착 500쌍 × 출발시각 여러 개 (출근·점심·퇴근·한산 시간대)
- 비교군: 최단거리, 카카오 경로, V1, V2, V3
- 지표
  - 실제 총 소요시간 평균 / 중앙값
  - 신호대기시간 절감률
  - 우리 경로가 최단경로보다 빨랐던 비율
  - 예측 총시간 vs 실제 총시간 MAE (약속한 시간을 얼마나 지키는지)

### 8.2 예측 모델 평가
- Δ = 1/3/5/10분에서 녹색 여부 정확도, Brier score
- 잔여시간 MAE
- 모두 baseline 외삽 대비로 보고

### 8.3 현장 검증
- 하지 않는다. 신호는 주기가 있는 패턴이므로 수집 이력 기반 예측을 그대로 쓰고, 효과는 8.1의 리플레이 시뮬레이션으로 보여준다.
- 나중에는 사용자의 실제 걷는 속도를 학습해 예측을 맞춤화한다.

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **호출 간격 제한 (같은 API 300초에 1회, 실측)** | 수집기는 429를 기다렸다 재시도. 제한이 키 전체에 걸리면 서비스는 실시간 호출을 사용자 요청마다 할 수 없으므로 V3를 "이력 기반 예측 중심 + 서버가 주기적으로 모아둔 실시간 캐시"로 바꾼다. `discover` 결과로 확정. |
| API 1,000회/일 한도 | 실시간은 경로 요청 시 근거리 1~2개만 조회. 교차로 단위 서버 캐시(TTL = 다음 신호 전환 시점), 사용자 간 공유. 수집은 하루 한도의 70%로 제한하고 남은 실행 횟수에 맞춰 자동 배분, 한도 초과 응답 시 당일 중단. |
| 방향 필드 ↔ 횡단보도 매칭 오류 | 서울시 방향 매핑 규칙 문서대로 처리 + 대상 지역(수십 개 교차로)은 수작업 검수 |
| 데이터 지연·현장 불일치 | "예상" 표기, 안전 문구, 예측 신뢰도가 낮으면 V2 평균값으로 폴백 |
| C-ITS 미연동 신호 (커버리지 공백) | V1 페널티(λ)로 처리, UI에 "신호정보 없음" 표기 |
| 예측 모델이 baseline보다 못함 | 그 자체를 결과로 보고하고 baseline 채택. 모델 개선 여지(감응신호 교차로 등)를 분석 |
| 특허 (2019 출원·2022 등록, 신호대기 최소 보행경로 제공) | 학교 프로젝트에는 문제 없음. 사업화 시 청구항 범위를 변리사에게 검토 |

## 11. 확장 로드맵

- **V1 → V3** 이후: 대상 지역 확대(여의도, 상암, 도심), 모바일 웹/PWA
- 개인화: 사용자별 실제 보행속도 학습
- 옵션: 그늘·경사·육교 회피 등 다른 비용 항목과 결합 (멀티 목적 경로)
- 인프라: 그린인 사례처럼 사용자 급증 시 교차로 단위 캐시·전환 시점 기반 갱신 필수
