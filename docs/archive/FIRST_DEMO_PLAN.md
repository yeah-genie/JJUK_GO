# Walking 1차 데모 구현 계획

2026-10-28. 사용자 목표: 신호 기능을 넘어 논의한 **신호+계단+경사 Walking 버전**을 구현해 먼저 써보게 한다. 버스·지하철은 후순위다. 사용자가 GPS 가능 여부도 물었으므로 **웹 GPS를 포함한 데모**로 계획한다. 아래 세부 기준과 구현 순서는 에이전트의 실행안이며, 이미 완료된 데모라는 뜻이 아니다.

## 데모에서 끝까지 할 수 있어야 하는 일

HTTPS 링크를 휴대전화에서 열고 위치 사용에 동의하거나 지도로 출발지를 정한다. 목적지를 고르면 빠른 길과 작은 시간 차이의 덜 힘든 대안을 비교한다. 신호·계단 구간·경사 수치와 미확인 항목을 확인하고 하나를 선택해 화면을 켠 채 걸어본다. 현재 위치·다음 확인 지점·남은 경로를 보고, 종료 시 간단히 선택 이유와 체감 피로를 남길 수 있어야 한다.

처음에는 **검증 가능한 서울 일부 경로**에서 완성한다. 기존 서울 검색·지도 범위와 실제 계단/경사/신호 검증 범위는 다르게 표시한다. 광화문은 신호 검증 후보, 용산/이태원은 경사·계단 후보이며 실제 자료와 대안 경로를 확인한 뒤 지원 구간을 확정한다. 지원 범위 밖의 검색을 차단할 필요는 없지만, 자료가 없는 길을 완성된 비교 결과로 포장하지 않는다.

|---|---|---|
| 출발·도착 | 기존 검색·지도 선택 유지, 웹 현재 위치 추가 | 위치 허용/거절/시간 초과 모두 검색을 계속할 수 있음 |

| 출발 시각 | 선택한 경로와 통계·지도 기준 통일 | 시연 기준 시각과 실제 현재 시각을 구별. 검증되지 않은 과거 패턴으로 실시간 횡단 지시를 하지 않음 |

| 결과·피드백 | 걸어본 경로 요약과 간단한 평가 | 예측값과 실제 측정값 구분. 측정하지 않은 멈춤 횟수를 실제 기록으로 쓰지 않음 |
| 공유·배포 | 휴대전화에서 직접 열리는 HTTPS 링크 | localhost가 아닌 링크로 iPhone Safari/Android Chrome 실기기 점검 |

## 구현 순서

### 1. 수집 안정화 — 첫 코드 변경 진행

`TDataClient._get`의 네트워크 오류 재시도도 마지막 호출로부터 305초 간격을 지키게 한다. 프로세스 내 마지막 호출 시각을 유지해 메타파일 없는 경우도 보호한다. JSON 파싱이 끝난 뒤 성공 로그를 남긴다. 교차로 호출 시도 전에 다음 순서를 저장해 한 대상의 오류가 전체 순회를 붙잡지 않게 한다. 실패 대상은 다음 순환에서 다시 방문한다.

**현재 상태:** 코드와 회귀 테스트 3개 추가. 전체 **59개 테스트 통과(3.36초)**. 이 변경은 작업 브랜치에만 있으며 수집 Actions가 도는 기본 브랜치에는 아직 반영하지 않았다. 운영 복구·배포 완료를 뜻하지 않는다. 수집 대상 수와 탐색 비중은 변경하지 않았으므로 약102분의 핵심 재방문 문제도 아직 남아 있다.

### 2. 계단·경사 데이터 연결

계단은 기존 그래프부터 활용한다. `cls=3`만으로 육교 계단을 전부 판정할 수 없으므로 원본 OSM의 계단 여부와 입체보행을 별도 속성으로 보존할지 검토한다. 서울시 공간파일을 열어 실제 계단 레코드·geometry·좌표계를 확인하고 필요한 구간만 파생 JSON으로 만든다. 저장소에는 원본 ZIP을 추가하지 않는다.

경사는 국토지리정보원 공개DEM에서 데모 대상 도엽을 먼저 확보한다. 로그인·전송 프로그램이 필요한 데이터 취득은 실제 진행 가능 여부를 확인하고, 사용자 인증이 필요한 지점에서만 도움을 요청한다. 화면상의 경사 레이어를 원자료 API처럼 사용하지 않는다. 지표면 DEM으로 육교 높이와 실내 계단을 추측하지 않는다.

도로 방향에 따른 상승량, 급경사 구간 거리, 관측/추정/누락을 보존한다. 초기 수치를 피로 점수로 환산하거나 계단 하나를 임의로 몇 분이라고 확정하지 않는다. 데이터가 준비되지 않은 경로는 비교를 제한하거나 미확인으로 표시하되, **계단·경사까지 연결된 경로가 생기기 전에는 목표 Walking 데모 완료로 부르지 않는다.**

### 3. 빠른 길과 덜 힘든 길 비교

기존 A*와 그래프 구조를 확장한다. 별도 대규모 서버나 새로운 프론트 프레임워크부터 만들지 않는다. 신호·계단·경사의 비용을 다르게 둔 소수 후보를 구하고 실제 시간 예산으로 거른다. 이 방식은 초기 휴리스틱이며 모든 최적 대안을 찾는다고 보장하지 않는다. 테스트 경로에서 대안 누락이 심하면 다중 라벨 탐색으로 변경한다.

검증 지역의 동일 출도착지에서 후보가 실제로 나오는지 먼저 확인하고 UI를 연결한다. 현재 `SLOW_OK=30`만 바꿔 모든 대안을 ‘편한 길’로 채택하지 않는다. ‘추가 80초 / 신호 2곳 감소 / 계단 1구간 감소’는 해당 경로의 실제 계산값일 때만 표시한다. 알려지지 않은 신호 대기는 예측 시간에서 빠졌음을 같은 카드에 보여준다.

### 4. 웹 GPS와 실제 걷기 흐름

화면을 연 상태의 GPS는 네이티브 앱 없이 구현 가능하다. 사용자 버튼에서 `getCurrentPosition`으로 출발지를 얻고, 실제 걷기 시작에서 `watchPosition`으로 갱신한다. 브라우저가 GPS·Wi-Fi 등 가능한 위치 공급자를 선택하므로 모든 기기에서 GPS 센서만 사용한다고 보장하지 않는다.

- 위치 권한이 거절되면 지도 선택으로 이어진다. 권한을 자동으로 반복 요청하지 않는다.
- 정확도(m), 마지막 갱신 시각, 위치 끊김을 표시한다. 정확도가 낮으면 ‘정확한 다음 횡단보도’ 판단을 보류한다.
- 경로 위 최근접 위치와 이전 진행을 함께 사용해 경로 진행을 추정한다. 단순 직선 이동거리를 경로 진행으로 쓰지 않는다. 오차가 큰 표본과 큰 점프는 진행 확정에 쓰지 않는다.
- 화면 비활성화/잠금 뒤 갱신이 멈출 수 있음을 알리고 돌아오면 위치를 다시 확인한다. 자동 재탐색은 범위를 정한 뒤 구현하고, 첫 버전에는 이탈 상태와 명시적 재탐색부터 제공할 수 있다.
- 완료/중단/화면 전환에서 `clearWatch` 처리. 앱 서버에 위치 이력을 기본 저장·전송하지 않는다. 선택 피드백과 정확한 이동 이력 수집은 별개로 취급한다.
- 실내·지하·도심 골목의 위치 오차 때문에 GPS만으로 실제 횡단 신호나 멈춤 원인을 확정하지 않는다.

**배포 조건:** HTTPS와 사용자 허용 필요. 로컬 localhost 개발은 가능하지만 다른 휴대전화에서 PC의 `127.0.0.1` 링크로 접속할 수 없다. 휴대전화 공유 데모에는 별도 HTTPS 주소가 필요하다. iframe/인앱 브라우저에서 위치 정책이 막히면 Safari/Chrome의 직접 링크로 안내한다.

**앱 전환을 검토할 시점:** 화면 잠금·다른 앱 사용 중에도 지속 추적, 상시 알림, OS 수준 백그라운드 안내가 핵심이 될 때다. PWA 설치만으로 백그라운드 위치 제한이 없어지지 않는다. 첫 웹 데모는 화면을 켜고 쓰는 범위로 한다.

공식 기술 문서: [Geolocation API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API), [watchPosition](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/watchPosition).

### 5. 사용 가능한 링크와 피드백

데모 데이터와 앱을 HTTPS에 올려 실제 폰에서 걷는다. 최소 확인 시나리오는 위치 허용/거절, 계단 길/우회 길, 오르막 왕복, 신호 미관측, 대안 없음, GPS 끊김, 중단/재시작이다. 예측 수치와 측정된 실제 기록을 분리하고, 경로 선택 이유와 사용 후 평가를 간단히 받는다. 로그인/결제/커뮤니티/대중교통은 이 흐름을 완성하는 데 필요하지 않다.
