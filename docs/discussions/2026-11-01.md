## 후속 사용자 정정: 개발은 계속 여기서 진행

### 구현

- 선택한 경로 아래 접는 '경로 상세': 출발/횡단/계단/급경사 포함 보행로/도착을 경로 누적 거리 순서로 표시한다. 각 행은 지도 위치로 연결한다. 신호 행은 기존 예상/출처 팝업으로 연결한다.

- 계단은 기존 경로 guides, 급경사는 지면 높이가 양쪽에서 확인된 간선의 기존 `f[2]`를 쓴다. 지하/높이 결측은 제외하고, 급경사 포함 보행로의 위치임을 명시한다. 경사 상세구간을 측량한 것처럼 표시하지 않는다.
- 안내 시작 버튼은 스크롤 목록 밖에 유지한다. 상세를 펼치면 위 화살표, 접으면 아래 화살표. 선택한 구간은 목록에서 표시한다.
- 근거 없는 '평일 낮에는 신호 절반쯤 예측' 문구 제거. 대안이 없을 때 전체 도로에 더 편한 길이 없다고 단정하지 않고 현재 탐색 조건에서 찾지 못했다고 표시한다.

### 필요한 API

네이버 Maps Client ID는 기존 연결을 유지한다. 국내 가게·건물 검색은 카카오 로컬 키워드 API를 검토한다. REST API 키가 필요하며 서버의 Authorization 헤더로 사용한다([공식 문서](https://developers.kakao.com/docs/en/local/dev-guide)). 키는 채팅/저장소/프런트 JS에 넣지 않는다. 앱 개발자 콘솔에서 발급 후 Vercel `jjukgo` 프로젝트 환경변수 `KAKAO_REST_API_KEY`로 보관하는 것을 제안했다. **현재 `api/places.js`에는 카카오 어댑터가 아직 없으므로 키만 추가해도 자동 활성화되는 상태는 아니다.** 기존 공개 검색은 유지한다. 카카오 장소 데이터 이용 조건과 지도 표시/출처 조건을 확인한 뒤 어댑터를 연결하고 실제 키로 검증한다. 보행 경로는 기존 엔진을 계속 사용한다.

### 카카오 콘솔 설정 도움

사용자가 앱 1632153에 로그인했지만 설정 위치를 모르겠다고 도움을 요청했다. 브라우저 제어 도구는 `failed to write kernel assets: 지정된 경로를 찾을 수 없습니다`로 초기화 실패하여 실제 콘솔을 읽거나 변경하지 못했다. 최신 공식 문서의 메뉴를 확인해 안내한다.

1. [카카오맵] > [사용 설정] > [상태] ON. 이미 ON이면 유지. 첫 활성화 앱과 추가 앱의 무료/유료 조건이 다르므로 결제 설정은 자동 진행하지 않는다([공식 이용 안내](https://developers.kakao.com/docs/ko/kakaomap/common)).
2. [앱] > [플랫폼 키] > [REST API 키]에서 키 확인/복사. 예전 '앱 키' 메뉴 이름이 개편되었다([공식 앱 설정](https://developers.kakao.com/docs/ko/app-setting/app)). 카카오 로그인 리다이렉트나 Client Secret 변경은 로컬 키워드 검색 설정에 요구하지 않는다.
3. Vercel `jjukgo` 프로젝트 Settings > Environment Variables에 `KAKAO_REST_API_KEY`를 비밀 값으로 저장, Production과 Preview에 적용. 실제 값은 채팅/문서에 남기지 않는다. 키 설정 이후 어댑터 구현과 새 배포/실제 검색 검증이 필요하다.

## 카카오 키 저장 완료 응답 + 화면 단순화 요청

사용자는 환경변수 저장을 마쳤다고 응답했다. 이어 첨부한 성신여대입구역–성신여대성지관 결과 화면이 꽉 차고 정신없다고 지적했고, 다른 복잡한 화면도 네이버/카카오에 익숙한 흐름으로 간단하게 바꾸라고 요청했다. 별도 UI 재설계 제안이 아니라 현재 화면의 정보 밀도를 줄이는 작업이다.

### 구현

- 서버 `api/places.js`: `KAKAO_REST_API_KEY`가 있으면 카카오 키워드 검색. 키는 Authorization 헤더에서만 사용하고 브라우저/응답/문서로 반환하지 않는다. 고정 서울 지원 범위만 전송하며 사용자의 GPS는 보내지 않는다. 키가 없는 환경은 기존 Photon 검색을 유지한다. 인증/권한/쿼터/네트워크 오류는 구분된 짧은 안내로 반환한다. 실패를 다른 업체의 정상 검색인 것처럼 숨기지 않는다.
- 카카오 응답은 `no-store`, 서버 메모리 캐시 없음. 사용 중 검색 목록만 메모리에 유지하고 카카오 선택 장소는 두 UI 모두 최근 목적지 저장 대상에서 제외한다. 이름·좌표·주소·분류만 필요한 형식으로 변환하고 응답 출처를 표시한다. 검색 결과로 별도 POI DB를 구축하지 않는다([공식 FAQ](https://devtalk.kakao.com/t/faq-api/125610), [공식 REST 규격](https://developers.kakao.com/docs/ko/kakaomap/rest-api)).
- 검색 화면 '가게·건물 더 찾기'에서 명시적으로 외부 검색. 주소와 실제 제공처를 표시한다. 기존 비동기 응답 순서 보호를 유지한다.
- 결과: 출발 시각 칩과 반복 설명을 제거. 두 경로의 이름·시간·거리/도착·한 가지 핵심 차이만 표시한다. 신호 정보는 선택 경로의 짧은 한 줄, 모르는 신호의 대기 제외 안내는 한 번만 표시. 계단/급경사/횡단 위치는 접힌 경로 상세로 유지한다.
- 출발 시각 선택은 결과의 '조건' 설정 안으로 이동. 변경 후 돌아갈 때 재계산한다. 공유/조건 버튼과 출발·도착 막대를 작게 정리하고 시작 버튼은 고정 영역에 유지한다.
- 설정: 수동 속도 버튼은 접힌 '직접 속도 설정' 아래, 데이터/계산 설명은 접힌 '계산 기준' 아래로 이동. 자동 학습과 계단/경사 조건은 유지한다.
- 신호 정보창: 남은 시간/미확인과 실시간 아님을 먼저 표시하고 긴 출처 설명은 '자료 기준 보기'로 접는다. 기록 재생은 기존처럼 별도 명시적 동작이다.
- 걷는 중 상단 신호 띠가 보이면 아래 중복 다음 횡단 줄을 숨긴다. 원래 갱신용 ID는 유지하고 아래 영역 높이를 다시 맞춘다.
- 원본 시각 검증용 `sample=1`의 5화면 구성은 유지한다.

## Product Design 전체 UX 점검 요청

사용자는 Product Design 플러그인을 명시해 전체 UI/UX를 점검하고 필요하면 네이버/카카오맵을 참고해 개선하라고 요청했다. 범위는 현재 제품의 검색→경로 비교→걷기→요약이며 기존 색·로고·신호/보행 엔진을 존중한다.

적용 스킬: Product Design index/audit/user-context 및 critical-overrides. audit은 현재 실행에서 캡처한 화면을 근거로 점검하고, 캡처 불가 시 멈추도록 명시한다. 과거 스크린샷이나 코드만으로 전체 시각 점검 완료를 주장할 수 없다.

기존 내장 브라우저 도구를 같은 표면에서 재초기화했으나 `cua.getState()`가 `failed to write kernel assets: 지정된 경로를 찾을 수 없습니다. (os error 3)`로 실패했다. 현재 실행에서는 제품 화면을 읽거나 캡처하지 못했다. 앱 코드는 변경하지 않았다.

대체 도구인 Playwright MCP는 사용 가능하지만 `references/critical-overrides.md`가 "If you need to use the Playwright CLI or MCP directly, ask the user before proceeding."라고 요구한다. 따라서 사용자에게 별도 브라우저에서 공개 쭉고를 열어 모바일 390×844 흐름을 검증하는 데 사용할 수 있는지 확인한다. 로그인 탭/계정 조작/기존 탭 변경은 필요하지 않다. 승인 전에는 대체 도구를 실행하지 않는다.

### Playwright 승인 후 실제 점검과 추가 요구 반영

사용자가 'ㅇㅇ'으로 별도 브라우저 검증을 승인했다. 검색→경로→조건→위치 거부/재연결→시험 GPS 이동→종료/요약을 실제 브라우저에서 캡처했다. 이전 '전체 화면 미검증' 상태는 이번 점검 범위에서 해소됐으며, 야외 GPS와 실제 신호 일치도는 여전히 미검증이다. [전체 감사 보고서와 스크린샷](../../reports/reference-ui/product-design-2026-11-01/AUDIT.md).

추가 사용자 메시지를 모두 현재 작업에 반영했다: 그늘로 벤치마크, 신호 외 기능/대중교통 확장 고민, 사용자에게 필요한 새 페이지 허용, 아스팔트 다크 배경·홈/설정 개선, 전체 아이콘 축소, 진행 캡처/Preview 공유, NRC처럼 종료 후 인증 이미지 저장. 컨셉·확장 제안과 이번 구현 범위는 [경험 방향](../EXPERIENCE_DIRECTION_2026-11-01.md)에 분리해 기록했다. 대중교통/휴식처 기능을 구현한 것으로 말하지 않는다.

홈은 한 입력 묶음+내 위치 버튼, 검색은 분류/빈 목록 축소+명시적 검색/Enter+기본/카카오 결과 병합. 출발 시각이 안 보이던 실제 레이아웃 버그, 과거 기록 큰 자동 말풍선, 위치 오류 중복 알림, 요약의 계획/실측 혼동을 수정했다. 테마는 밝게 기본/아스팔트 선택 저장, 제공자 지도색은 유지. 아이콘만 줄이고 조작 영역은 유지했다.

사용자가 직접 요청한 새 페이지 '걸음 공유'를 추가했다. 실제 경로 실루엣·거리·시간·페이스, 아스팔트/밝게/투명 PNG, 기기 사진 배경(서버 미전송), 명시적 이미지 저장. 실제 GPS 조각이 끊긴 곳을 이어 그리지 않고, 없으면 계획 경로라고 적는다. `?screen=share&sample=1`은 앱/이미지 안에 실제 기록이 아님을 표시하는 시각 예시다. PNG 다운로드(990×1800)·투명 알파·사진 선택/삭제·작은 화면을 검증했다. 실제 개인 GPS/사진은 GitHub에 올리지 않았고 보고서의 위치/이동/사진 파일은 모두 별도 시험 자료다.

앱 코드 작업본 98e80ab의 Vercel Preview READY 링크를 중간에 사용자에게 전달했다. 최종 운영 반영 결과는 실제 확인 후 기록한다.

## Claude: 네이버 지도 흐름으로 맞추기 (11/01)
사용자: "깃허브 확인하고, 네이버 맵이랑 그냥 똑같이 만들되, 신호 부분이랑 우리가 말했던 덜 부담스러운 길 부분만 추가한다고 보면 좋을 거 같아. 시작." / "중간중간 화면 캡쳐하면서 뭐하고 있는지 보여줘"

- GitHub 확인: 코덱스 커밋 10개(카카오 검색, 홈·설정·걷기 정리, 공유 카드, 398e16c까지)를 받아 그 위에 작업했다. 코덱스가 바꾼 것은 덮어쓰지 않았다.
- 흐름은 네이버 지도의 일반적인 순서를 따른다. 쭉고 로고·색은 유지하고, 네이버 로고·이름·상표는 쓰지 않는다.
  - **홈 = 지도:** 위 검색창(장소, 주소 검색)과 설정 버튼, 최근 목적지 칩, 내 위치 버튼, 아래 카드에 "주변 신호"와 "길찾기"
  - **검색 → 장소 카드:** 이름·거리·분류, [출발] [도착]. 도착을 누르면 출발은 내 위치로 바로 길을 찾는다. 출발을 누르면 도착을 고르게 한다.
  - **경로 화면에서 출발·도착을 바꾸면** 홈으로 돌아가지 않고 바로 다시 찾는다.
  - **경로 카드:** "덜 부담스러운 길"(사용자 표현) / "빠른 길", 횡단보도 N회 · 계단 N구간 · 오르막 줄을 추가했다.
- **쭉고만의 것(신호):**
  - 홈 지도에 주변 신호(지도 중심 350m 안, 최대 14개)를 보여 준다. 패턴이 확인된 신호에는 남은 초 숫자를 붙이고, 1초마다 줄어든다(예상, 실시간 아님).
  - 같은 교차로의 방향별 횡단은 그 방향 쪽으로 약 15m 띄워 겹치지 않게 했다.
  - 이를 위해 홈에서도 지금·다음 시간대 신호 패턴을 미리 받는다. 길을 찾으면 엔진이 경로 시간대 패턴으로 다시 받는다.
- **확인**(390×844, 화 14:10 고정, 가짜 GPS):
  - 홈 → 검색 "서울숲" → 장소 카드 → 도착 → 경로 → 안내 시작까지 이어짐
  - 시청 주변 남은 초 14곳이 1초마다 줄어듦
  - 신호를 누르면 "지금 빨강 · 2초 뒤 초록불 (예상)"
  - 페이지 오류 0건
  - 점검 스크립트 통과: reference UI, walk, app shell, places
- **확인 못 함:** 실제 네이버 지도 위 모습(작업 환경에서 네이버 지도가 안 뜸)

## Claude: GPS 재점검, 패턴만 있는 신호 색 표시, 경로 상세 겹침 (11/01)
사용자: "GPS가 잘 안되는데 확인 다시 해주고, 노란색으로 패턴만 확인된 아이콘들 일단 빨,초로 바꿔두고 점점 데이터 쌓일때마다 정확하게 업데이트해." / "경로 상세일때 글씨가 겹쳐."

**GPS에서 찾은 원인과 수정**
1. 걷는 중 위치 오차 50m 초과를 버렸다. 빌딩 사이에서는 50~100m가 흔해 안내가 멈출 수 있었다.
   - 100m까지 받아 진행한다.
   - 걸음 속도 학습은 원래대로 정확한 위치만 쓴다(`trackAdd`의 PACE.ACC).
2. 홈의 내 위치 버튼이 오차 100m 넘는 위치를 받으면 옛 화면 함수로 가서 새 화면에서는 아무 일도 없었다.
   - 대략 위치도 지도에 보여 주고 "대략적인 위치예요(오차 약 N m)"라고 알린다.
   - 출발지로는 100m 이하일 때만 쓴다.
3. 홈 지도에 내 위치 점이 안 보였다. 위치를 받으면 점을 찍고 지도를 옮긴다.
4. 실패 안내를 원인별로 나눴다: 권한 꺼짐(주소창 자물쇠에서 허용), 위치 서비스 꺼짐, 앱 안 브라우저(스레드·카톡·인스타는 Safari·Chrome으로 열기).
   - 스레드 데모로 들어오는 사람은 대부분 앱 안 브라우저라 중요하다.
- 실기기 GPS는 여전히 이 환경에서 확인할 수 없다.

**노란 아이콘(패턴만 있는 신호) → 빨강·초록**

노란 아이콘은 세 종류였다(서울 전체 방향별 개수):

| 시각 | 확인됨 | 이 시간대 패턴은 있으나 다른 날 대조 부족 | 초록 길이 기록만 |
|---|---|---|---|
| 평일 14:10 | 2,730 | 395 | 156 |
| 평일 08:40 | 473 | 1,833 | 975 |
| 토 21:00 | 0 | 4 | 3,277(밤 시간대 자료 자체가 7곳뿐) |

- '대조 부족' 신호는 빨강·초록과 남은 초를 보여 주고 "(예상·검증 중)"이라고 쓴다.
- 같은 시간대에 다른 요일 종류 패턴만 있는 신호는 "(평일/주말 기록 기준)"이라고 쓴다. 숫자 배지는 흰 바탕·점선으로 구분한다.
- 이 신호들은 경로 시간 계산과 걷는 중 신호 띠에는 쓰지 않는다(확인된 패턴만 씀).
- 초록 길이만 아는 기록은 신호가 바뀌는 기준 시각이 없어 색을 정하면 지어내는 것이라 회색으로 남겼다.
- 자동 갱신: `history.yml`(매일 04:20 KST)이 신호 패턴을 다시 만든다. 이번에 새 화면용 기록 요약(`reference-ui/signal-facts.json`)과 새 화면 빌드도 같이 다시 만들게 했다. 자료가 쌓여 다른 날 대조를 통과하면 '검증 중'이 자동으로 '확인됨'이 된다.

**경로 상세 겹침**
- 경로 카드 높이가 104px로 눌려, 줄이 많은 카드(먼 길 경고)의 아래 줄이 '경로 상세' 위로 넘쳤다.
- 카드가 내용만큼 늘어나게 했다(129px로 확인).
