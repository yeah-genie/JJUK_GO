## 옛 실시간 API와 새 실시간 API 비교
| 항목 | 옛 API | 새 API(10381) | 같음? |
|---|---|---|---|
| 주소 | `v2xSignalPhaseTimingFusionInformation/1.0` | `v2xSignalPhaseTimingFusionCurrentInfo/1.0` | 다름 |
| 교차로 번호 `itstId` | 예: 2217, 20386 | 안내서 예: 2217, 20386 | **같음**(확인: 두 번호 모두 하루치 파일 교차로 목록에 있음) |
| 방향별 신호 상태 | `etPdsgStatNm` 같은 이름 | 같은 이름 규칙 `{방향}{종류}sg StatNm` | **같음**(안내서 기준) |
| 남은 시간 | `etPdsgRmdrCs` (0.1초 단위) | 같은 이름, 0.1초 단위 | **같음**(안내서 기준) |
| 열쇠 이름 | `apiKey` | 안내서는 `apikey` | 둘 다 보내도록 함 |

- **모름:** 이 작업 환경에서는 T Data 서버에 접속이 안 돼서 새 API 응답을 직접 받아 보지 못했다. 그래서 수집기가 실제로 받으면 그 필드 목록을 `data` 브랜치 `meta/endpoints.json`에 남기게 했다.
- **확인:** 지금 저장 형식(`itst_id,direction,movement,state,start_utc,end_utc,rem_start_ds,rem_end_ds,samples`)은 실시간 수집과 하루치 파일이 같다. 다른 점은 `movement` 글자 크기(`Pd`/`pd`)뿐이라 변환 때 소문자로 맞춘다.
- **확인:** 같은 교차로·같은 방향 코드에서 초록 길이가 실시간(10/28~29)과 하루치 파일(10/27)이 대부분 같았다(예: 2217 et 20초/20초, 1537 ne 13초/13초, 3011 nt 11초/11초). 일부는 달랐다(1835 nt 29초/17초, 2212 et 10초/4초). 날짜·시간대가 달라서일 수 있다(추정). 같은 날짜끼리는 아직 못 비교했다.

## 바꾼 것
1. **수집기(`collect.yml`)가 새 API부터 부른다.** 실패하거나 빈 응답이면 옛 API로 넘어간다(11/15까지). 한 번 넘어가면 6시간 동안은 답한 쪽부터 부른다(호출 간격 5분을 아끼려고). 어느 쪽이 답했는지·필드 목록은 `meta/endpoints.json`, 호출마다는 `meta/call_log.csv` 마지막 칸에 남는다.
2. **실시간 수집도 같은 이력 형식으로 쌓는다.** `scripts/realtime_to_history.py`가 `data` 브랜치 조각을 하루(한국 시각) 파일 `official-history/날짜.csv.gz`로 만든다. 보행 신호만, 상태 3가지만, 겹친 구간은 합친다. **하루치 파일이 없는 날만** 채운다.
3. **하루치 파일이 나오면 그걸로 바꾼다.** 하루치 파일은 서울 전체라 더 넓다. 실시간으로 채운 날은 표시(`source_kind: realtime`)를 남기고, 나중에 하루치 파일이 나오면 덮어쓴다.
4. `history.yml`에 2번 단계를 넣었다(매일 04:20 KST).

## 남은 확인
- 새 API를 쓰려면 T Data에서 **10381 서비스 사용 신청**이 따로 필요할 수 있다. `call_log.csv`에 `http_401`/`http_403`이 계속 보이면 신청이 필요하다는 뜻이다(그동안은 옛 API로 계속 모음).
- 10/30 02시 이후 옛 API 호출이 시간 초과(`TimeoutError`)로 계속 실패하고 있었다. 새 API로 바뀌면 나아지는지 본다.
- 실시간 수집은 교차로 수가 적다(10/28: 21곳). 앱에 쓰는 패턴은 여전히 하루치 파일이 중심이다.
