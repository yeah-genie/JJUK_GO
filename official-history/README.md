# 서울시 공식 신호 이력 — 보행 데이터

출처: [서울교통빅데이터플랫폼 신호제어기 신호 및 잔여시간 정보](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=10382), 서울특별시 C-ITS/미래첨단교통과. 원본 페이지의 저작자 표시(BY) 조건에 따라 출처를 표시한다.

원본 ZIP 샘플 한 개는 [GitHub Release](https://github.com/yeah-genie/JJUK_GO/releases/tag/signal-history-sample-20261027)에 별도로 공개했다. SHA256은 날짜 메타데이터와 일치한다. 원본은 코드 Git 기록이나 Vercel 출력에 포함하지 않는다.

- `sample.csv`: 첫 검증 날짜의 보행 신호 구간200행. 원본 전체가 아닌 정규화된 표본.
- `YYYYMMDD.csv.gz`: 원본에서 보행 신호만 추출한 상태 구간. **전체 자료는 위 Release에 보관**하며 날짜 메타데이터에 직접 URL·해시가 있다. 로컬 생성 파일은 무시하고 첫10/27 표본만 기존 Git 커밋에 유지한다. 관측 공백5초 초과·상태 전환·잔여시간 재증가 시 분리. 원본 전체를 풀거나 차량 신호를 보관하지 않는다.
- `YYYYMMDD.json`: 공식 다운로드 URL, 원본 SHA256, 용량, 행 수, 교차로 범위와 시간 범위.
- `manifest.json`: 처리 완료한 날짜와 공식 목록. 구간의 시작~끝 사이에 관측이 끊긴 시간을 연속 관측으로 해석하지 않는다.

첫 표본2026-10-27은 원본 ZIP224,035,944바이트/CSV2,811,355,223바이트,7,904,997행, 교차로2,550곳. 유효 보행 신호는2,393곳/4,852방향이며 보행 구간 압축 결과7,173,390바이트다. **교차로마다 하루 종일 관측된 것은 아니다.** 예를 들어1537번은 전체 시간 범위가 길지만 한 보행 방향의 실제 표본은3,085개로 공백이 많다.

재현: `.venv/Scripts/python.exe scripts/import_official_history.py --date 20261027`, 전체 목록: `--all --remove-raw`. 네트워크·CSV 읽기 실패 시 완료 메타데이터를 쓰지 않는다. ZIP은 무시된 `datastore/history/raw/`에서 임시 처리한다. 원본 날짜별 파일은 한 번 처리 후 압축 구간으로 보관하고, 새로운 일자만 추가한다.

이 자료는 과거 관측이며 현재 신호를 보장하지 않는다. 사고·공사 원인 정보도 들어 있지 않다. API의 향후 역할은 기준 패턴과 현재 신호 차이의 보조 확인이며, 사고·공사 원인 판단에는 별도의 사건 정보가 필요하다.

## 앱용 패턴

`scripts/export_history_plans.py`는 방향·날짜·시간대별로 나눠 실제 관측 구간만 표본화한다. 최소400개 관측, 학습 부분에서 주기2회 이상·위상90% 이상·불순도2% 이하, 별도 뒷부분 상태 일치율95% 이상인 패턴만 통과시킨다. 후보 주기는 학습 구간의 보행 초록 종료시각 차이에서 얻는다. 각 시간대/방향은 가장 최근에 통과한 날짜를 사용한다. **오늘의 정확도, 대기시간 오차 보장, 요일별 보편 패턴으로 검증된 것은 아니다.** 지도 방향 대응은 기존 가정이며 현장 검증 필요.

앱은 기존08:40 기준 체험을 유지한다.24개 시간대 파일 중08·09·10시만 불러오며, 해당 방향·시간대의 패턴이 없으면 미확인으로 처리한다. 선택한 패턴의 실제 날짜·시간 범위·관측량·동일 날짜 검증 결과를 신호 상세에서 볼 수 있다. 실패한 다운로드를 이전4개 내장 패턴으로 조용히 대체하지 않는다.

## 이후 갱신

`.github/workflows/history.yml`은 신규 날짜만 처리하고 원본 ZIP을 정리한 뒤 압축 구간은 Release, 메타데이터·앱용 파일은 Git에 보관하도록 준비했다. 기존 시간대 패턴을 보존하는 증분 갱신을 사용한다. **현재 작업 브랜치에만 있으면 예약 실행되지 않는다.** 기본 브랜치 반영과 Vercel Git 연동을 확인하기 전까지 매일 자동 배포 완료로 표현하지 않는다. 기존 API 수집은 수동 비활성화 상태이므로 API 보조 점검을 도입할 때 별도 검증 후 활성화해야 한다.
