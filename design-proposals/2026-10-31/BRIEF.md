쭉고의 현재 UI를 개선하는 방식으로 작업하지 마세요.
이번 작업은 기존 화면의 리팩터링이 아니라 UI를 처음부터 다시 설계하는 전면 재디자인입니다.
현재 쭉고에서 유지해야 하는 것은 아래뿐입니다.

* 쭉고 로고
* 현재 서비스의 메인 컬러와 브랜드 톤
* 현재 동작하는 길찾기 기능과 데이터 로직
* 출발지/도착지 검색
* 두 경로 비교
* 걷기 시작
* 횡단보도 및 신호 데이터
* 걸음 속도 개인화 기능

그 외의 레이아웃, 카드 구조, 정보 배치, 지도 위 UI, 버튼 위치, 컴포넌트 형태는 모두 기존 것을 버리고 새로 설계하세요.
특히 현재 UI를 기반으로 조금씩 수정하거나 기존 카드에 정보를 추가하지 마세요.

## 디자인 목표
이 서비스는 네이버지도나 카카오맵처럼 종합 지도 앱이 아닙니다.
쭉고의 핵심 가치는 “몇 분 더 걸을지보다, 신호·횡단보도·경사 때문에 얼마나 덜 불편하게 걸을 수 있는 길인지 보여주는 것”입니다.
따라서 사용자가 결과 화면을 본 후 3초 안에 다음을 이해해야 합니다.
1. 어느 길을 추천하는가 2. 왜 그 길을 추천하는가 3. 빠른 길과 얼마나 차이 나는가 4. 신호 대기 시간이 얼마나 줄어드는가 5. 앞으로 만날 횡단보도의 상태가 어떤가

## 가장 중요한 디자인 원칙
1. **지도 중심** — 지도는 화면에서 가장 중요한 영역. 정보 카드 때문에 지도가 작은 배경처럼 보이면 안 된다. 지도 위에는 선택된 경로와 해당 경로의 횡단보도만 명확하게. 경로와 관계없는 주변 횡단보도는 매우 작고 흐리게 또는 숨김.
2. **다음 횡단보도 강조** — 모든 신호를 동일하게 강조하지 말 것. 다음에 만날 횡단보도 하나가 가장 중요(예: 다음 횡단보도 / 74m / 횡단 가능 · 17초 남음). 나머지는 보조.
3. **단순한 시간 비교가 아니라 신호 경험 비교** — 예: 신호 적은 길 15분 · 1.1km, 예상 신호대기 40초, 횡단보도 3개 / 빠른 길 13분 · 1.0km, 예상 신호대기 3분, 횡단보도 6개. “2분 더 걷지만 신호에서는 훨씬 덜 기다리는구나”를 바로 이해.
4. **추천 이유는 하나만 강하게** — 장점 4~5개 나열 금지. 가장 중요한 하나를 자연어로(예: “약 2분 더 걸리지만 신호대기를 2분 줄여요”, “긴 신호 대기가 없는 길이에요”). 나머지는 상세보기.
5. **Progressive disclosure** — 첫 화면에는 의사결정에 필요한 최소 정보만. 신호 개수·계단·경사·급경사·횡단보도 상세·데이터 기준·예상 대기시간 계산 방식은 자세히 보기에서.
6. **카드 남용 금지** — 작은 카드와 아이콘으로 화면 아래를 채우지 말 것. 대시보드처럼 만들지 말 것. 모바일 소비자용 지도 앱처럼. 한 화면의 큰 시각적 그룹은 최대 3~4개.
7. **모바일 지도 앱다운 시각적 완성도** — Apple Maps, Citymapper, Google Maps, Transit의 정보 위계와 간결함 참고(복제 금지). AI SaaS 대시보드·금융 대시보드·관리자 페이지·데이터 분석 화면 느낌 금지.

## 결과 화면의 권장 정보 구조
1. 출발지 / 도착지 2. 큰 지도 3. 지도 위 다음 횡단보도 정보 4. 경로 비교 5. 걷기 시작 CTA

## 경로 비교 UI
두 개의 큰 복잡한 카드를 나란히 놓는 방식에 얽매이지 말 것. 더 좋은 방식이 있으면 새로 설계. 최소한 총 걷는 시간, 거리, 예상 신호대기, 왜 추천하는지는 비교 가능해야 한다.

## 색상
새 브랜드 컬러를 만들지 말 것. 현재 jjukgo.vercel.app의 로고·메인 컬러·배경색·강조색·기본 텍스트 컬러를 추출해 사용. 신호 상태는 초록=횡단 가능, 빨강=대기, 회색=데이터 없음. 브랜드 컬러와 신호 컬러를 혼동하지 말 것.

## 금지사항
기존 UI를 기반으로 조금씩 수정 / 기존 카드 구조 재사용 / 요구사항을 전부 화면에 넣기 / 설명 문구 많이 / 작은 아이콘 여러 개 / 모든 정보에 색상 / 테두리 박스 남발 / 화면 아래 정보 카드가 절반 이상 / 관리자 대시보드 / 모든 횡단보도를 크게 / 구현 편의성 때문에 디자인 타협.

## 작업 방식
기존 코드를 바로 수정하지 말 것. 현재 코드에서 필요한 기능과 데이터만 파악. 기존 UI 구현을 source of truth로 쓰지 않고 새 모바일 UI를 처음부터 설계. HTML/CSS 또는 별도 prototype에서 만들어 실제 모바일 화면으로 렌더링. 기존 production UI는 수정하지 말 것. **서로 다른 3가지 디자인 방향**(정보 구조 자체가 다른): A. 지도 중심형, B. 경로 비교 중심형, C. 지도 + bottom sheet 혼합형. 각 안을 390×844로 렌더링하고 스크린샷. 사용자가 선택할 때까지 production에 적용하지 말 것.
