# 신호를 고려한 최소 예상시간과 한국 공공데이터

확인일2026-10-29. 사용자 제안: 신호 상황을 고려한 최소 소요시간을 산정하고, 한국 상황에 필요한 데이터셋/공공API가 있는지 확인한다.

## 판단

**신호를 포함한 가장 빠른 예상 경로를 비교 기준으로 삼고, 그보다 몇 분 더 걸려 어떤 불편을 줄이는지 보여주는 방향이 적절하다.** 신호를 적게 지나는 길이 반드시 가장 빨리 도착하는 길은 아니다. 걷는 시간과 도착 시각의 대기를 함께 비교해야 한다.

예시는 설명용 가상값이다. A는걷기15분+신호대기4분=19분, B는걷기16분+대기1분=17분이면 B가 빠르다. 편한 후보가18분이면 ‘빠른 예상 경로보다1분 추가’로 설명한다. 실제 앱 성과 수치가 아니다.

출발 위치·목적지·출발 시각·보행속도를 고정하고, 경로의 각 횡단보도까지 도착하는 시각을 순서대로 계산한다. 이전 신호 대기는 다음 신호 도착 시각에 반드시 포함한다.

`경로 예상시간 = 출입구 연결을 포함한 보행시간 + 각 신호에 도착하는 시각의 예상 대기`

횡단 자체의 걷는 시간은 보행구간에 포함하며 대기로 다시 더하지 않는다. 멈춤에 대한 불편 점수는 편한 길 순위에 사용할 수 있지만 물리적 이동시간인 것처럼 ETA에 더하지 않는다.

## ‘최소’의 의미와 구현 범위

- 첫 기준은 **지금 출발**이다. 출발을 늦추는 별도 비교에서는 출발 전 기다린 시간도 지금부터 도착까지의 총시간에 포함한다. 경로 이동시간만 줄었다고 더 일찍 도착하는 것은 아니다.
- 실시간은 **현재 신호와 잔여시간**을 뜻한다. 현재 초록이30초 남았다는 사실만으로5분 뒤 도착할 횡단보도의 상태를 알 수 없다. 미래 현시는 이력/주기/운영계획 등 별도 예측이 필요하다.
- 이력은 예상의 근거이며 오늘의 교통·감응 제어·공사·보행 호출·시간대 변경을 완전히 보장하지 않는다. 신호 차이가 났다고 원인을 사고로 단정할 수도 없다.
- 모르는 신호는 미확인이다. 가정을 포함한 ETA와 자료 범위를 표시한다. 예측 구간을 검증하기 전 정밀한 신뢰구간을 만들어 표시하지 않는다.
- 신호 방향/횡단보도 대응, 녹색 점등과 점멸 구간, 사용자의 속도·횡단 길이를 확인해야 한다. 경로 ETA가 횡단을 시작하라는 지시가 되어서는 안 된다.
- 전체 보행망과 시간 의존 비용의 조건을 검증하기 전 ‘서울 전체의 정확한 최솟값’을 주장하지 않는다. 처음에는 **검증한 후보 중 신호를 반영한 가장 빠른 예상시간**이라고 표현한다. 전역 최적화가 필요하면 보행망 누락/탐색 범위와 FIFO 등 시간 의존 탐색 가정도 확인한다.

## 현재 코드에서 확인한 상태

대상 `docs/prototype/src/app.js`, 이번 작업 전 코드 기준이다.

| 위치/기능 | 현재 상태 | 남은 일 |
|---|---|---|
| `search(...,"short",dep)` | 보행시간+도착 시각의 신호대기를 탐색 비용으로 사용 | 현장 방향 대응, 시간대 경계, 전체 후보/탐색 범위 검증 |
| `simulate()` | 앞 신호 대기를 다음 도착 시각에 반영하고 미확인 신호 대기를 포함 | 실제 대기·소요시간과 비교 |
| `refreshSims()` | short/jjuk/gentle 세 후보를 총시간 기준으로 정렬, 시간예산 안에서 부담 비용 비교 | 세 후보가 모든 가능한 대안을 대표하지는 않음 |
| `SPEED=1.2` | 모든 사람에게 같은 속도 | 수동 속도 선택과 계산 전체 반영, 이후 보정 검증 |
| `UNKNOWN_SIG_COST=45` | 미확인 신호당45초 임시 가정 | 관측으로 가정 평가, 모르는 신호를 실제 관측처럼 쓰지 않음 |
| `MIN_GREEN=8` | 남은 녹색8초 미만이면 다음 주기 대기 가정 | 고정8초가 모든 횡단 길이/속도에 충분하다는 근거 없음 |
| 걷기 화면 남은 시간 | 남은 거리/고정속도 중심 | 결과 화면과 같이 남은 신호대기를 포함하도록 정리 필요 |

따라서 계산 기반은 일부 있으나 새 제안이 완전히 구현/실측 검증된 것은 아니다. 이번 작업에서는 코드를 변경하지 않았다.

사용자가 이전에 정한 **일별 이력 중심, API는 차이 확인** 운영 방향은 변경하지 않았다. collect 재활성화나 새 수집/예약을 설정하지 않았다. history 예약은 작업 브랜치에 준비된 상태이며 기본 브랜치 반영/운영 검증 완료로 바뀌지 않았다.

## 중요 정정: ‘실시간’의 의미

이전 보고서는 서울시 정책 설명의2026-02-02실시간 공개를 확인했다. 이번에는 **개별 데이터셋 설명을 대조**했다. S-DoT환경정보는1시간 단위 최소/최대/평균을 실시간 제공한다고 명시한다. 즉 공개 시점이 빠르다고 센서의 매초 원시값이 공개되는 것은 아니다. 수정/지연 자료의 `DATA_NO` 구분도 확인해야 한다. 해당 API를 초 단위 신호 보정이나 골목별 순간 소음·공기질에 그대로 쓸 수 있다고 해석하면 안 된다.

이번 S-DoT페이지의 센서 수는1,170대로 안내되고 서울시 정책 설명은2026년3월 기준1,100개소다. 기준일/범위가 다른 수치를 단순히 서로 모순이라고 판단하지 않는다. 인증 응답이나 모든 항목의 실제 수신 여부는 시험하지 않았다.

## 권장 실행 순서 — 구현 완료 아님

1. 현장 확인할 서울 경로 몇 쌍에서 보행로와 횡단 방향을 정확히 맞춘다.
2. 고정 출발 시각·개인 속도에 대해 신호 반영 최소 예상시간을 계산하고 미확인 가정/자료 날짜를 함께 표시한다.
3. 동일 조건에서 편한 후보를 비교하고 ‘빠른 예상 경로 대비 추가시간’을 일관되게 사용한다. 걷기 중 ETA도 같은 기준으로 맞춘다.
4. 실제시간/신호 대기를 측정해 이력 예측 오차와 미확인45초 가정을 평가한다. 모델 오차가 있는 채1초 단위 최적이라고 홍보하지 않는다.
5. 새 통합API의 지원 교차로/방향·시각·호출 제한을 작게 검증하고 이력 대비 차이 확인에 연결한다. 키는 서버에서 사용하고 Git/프런트에 공개하지 않는다.
6. 그 뒤 한국의 비노출·PM간섭 등은 확보되는 구간 자료로 별도 효용을 비교한다. 날씨/견인/환경센서를 모으면 길 품질이 자동으로 완성된다고 가정하지 않는다.

이번에는 소스 읽기와 공식 문서/카탈로그/미리보기 확인을 했다. 비밀키 조회·실제 API 호출·원본 ZIP 추가 다운로드·전체 파일 스키마/건수 검증·코드 수정·테스트·배포·예약 변경은 하지 않았다. 따라서 ‘데이터가 존재함’과 ‘우리 키로 정상 수신·서울 전체 범위 검증·앱 연동 완료’를 구분한다.
