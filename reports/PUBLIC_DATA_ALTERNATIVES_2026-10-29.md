# API 병목과 공개데이터 대안

2026-10-29 · 공식 사이트와 현재 저장소 대조. 운영 API 호출·파일 다운로드·수집기 변경·서비스 배포는 하지 않았다.

## 판단과 이전 조사 정정

신호 예측 범위 확대에는 수집 제한과 관측 공백이 장애물이다. 그러나 GPS 실패는 위치 공급자·브라우저와 앱 상태 관리 문제이고, 경로별 시간 불일치는 앱 계산 문제다. 현재 배포는 GitHub 수집 결과를 자동으로 읽지 않고 내장 과거 신호 패턴을 사용한다. 데이터를 더 모아도 연결과 계산을 고치기 전에는 화면이 자동으로 개선되지 않는다.

**가장 유력한 대안은 T Data의 일별 신호 이력 파일이다.** 이전 `docs/DATA_COLLECTION.md`의 ‘공식 과거 신호이력 파일은 확인되지 않았다’는 판단을 정정한다. 공개일2026-10-15인 파일 서비스를 이전 조사에서 놓쳤다. 공개 목록 확인과 내용·완전성·자동 다운로드 검증은 다르다.

| 병목 | 확인된 근거 | 대안의 효과 |
|---|---|---|
| 신호 관측 공백 | 기존 키 전체300초 간격 제한 실측. 핵심10곳+탐색 교대라 핵심 한 곳 재방문 이론상101분40초 | 일별 이력의 범위가 충분하면 학습용 수집 부담을 줄일 가능성 |
| 수집 장애 | 10/29 01:18 점검에서306초 간격 회복, 직전4시간16분 성공 공백 | 이력으로 보충 가능성. 파일도 누락 검증 필요 |
| 앱 갱신 | 배포 내장 패턴과 수집 결과 자동 연결 없음 | 공급원 외에 앱 연결 작업 필요 |
| PC GPS | 실제 timeout 관찰, 화면 전환 뒤 대기 문구 잔류 재현 | 신호 API와 무관. 실패·재시도·직접 출발지 선택 수정 |
| 시간 비교 | 미관측 신호 대기 처리 및 출발 후보/선택 결과 경로 불일치 | 데이터 추가 전에 계산 기준 통일 |

수집 상태는 당시 스냅샷이며 지금까지 정상이라는 의미가 아니다. [수집 점검](collector-check-2026-10-29.md), [32개 앱 감사 항목](BMAD_AUDIT_2026-10-29.md) 참고.

## 1. 일별 신호 이력 파일: 첫 검증 대상

[T Data 신호제어기 신호 및 잔여시간 정보](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=10382)는 전일 자료·일별 갱신, 공개일2026-10-15로 안내된다.

공개 파일 선택 목록에서 `signalPhaseTimeFusion_20261014.zip`부터 `signalPhaseTimeFusion_20261027.zip`까지14개 날짜를 확인했다. 포털 분류는 CSV지만 실제 배포는 ZIP이며 비CSV 미리보기를 제공하지 않는다. 사용자 ZIP 선호를 고려해 이번에는 다운로드하지 않았다. **14일이 고정 보존기간이거나 서울 모든 교차로를 포함한다고 판단하지 않는다.**

활용 제안: 날짜별 이력을 서버 작업에서 읽고 필요한 보행 신호의 상태 전환·관측 범위·패턴 통계만 추출한다. 사용자가 매번 ZIP을 받거나 앱이 원본 전체를 받을 필요는 없다. 도입 전 크기·접근 조건을 확인하고 임시 저장 한도·정리 정책을 정한다. 아직 자동화·삭제를 실행하지 않았다.

필수 검증:

1. 파일 크기, 다운로드 로그인 필요 여부, 안정적인 공식 취득 경로.
2. 날짜별 대상 교차로 포함 여부, 보행 방향별 NULL 비율, 시간대별 공백.
3. 시간 단위·시간대·중복·상태 전환과 기존 파서 호환성. 명세 필드명과 단위 설명을 표본 대조.
4. 주중/주말·시간대별 변화와 다음 날 예측 정확도. 자료 부족은 예측 불가로 남기며 대기0초로 채우지 않음.

이 자료는 **분석·학습·재현용 이력**이다. 오늘 지금 켜진 보행 신호를 보장하지 않는다.

## 2. 새 실시간 API: 기존 서비스 종료 대응

[2026-10-21 공지](https://t-data.seoul.go.kr/board/notice/detail.do?boardId=104)는 기존 신호·잔여시간 API3종의 종료일을 **2026-11-15**로 안내한다. 단기 이력은 파일, 실시간은 새 OpenAPI를 사용하도록 명시한다. 이전9월 공지의 기존 서비스 계속 제공 설명보다 최신 종료 공지를 우선한다.

- 현재 `config/collector.toml`: `v2xSignalPhaseTimingFusionInformation/1.0`.
- [새 결합 현시 API](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=10381)의 화면 샘플 URL: `v2xSignalPhaseTimingFusionCurrentInfo/1.0`.
- 교차로ID·인증키 필요, 시군구코드 인자 존재. 보행 방향별 상태·잔여시간과 전송시각 필드를 명세에서 확인했다. 시군구코드가 있다고 구 전체를 한 번에 받는다고 해석하지 않는다.
- [신규 서비스 안내](https://t-data.seoul.go.kr/board/notice/detail.do?boardId=102)는 기존 이력+현재 상태 방식과 새 현재 상태용 서비스를 구분한다.
- **새 API의 호출 제한·키 권한·실제 반환 범위는 미검증.** 기존 키 사용 가능이나300초 제한 해제를 약속하지 않는다. 수집과 충돌할 직접 시험 호출도 하지 않았다.

주소만 바꾸고 기존 이력 수집을 그대로 돌리면 적절하지 않을 수 있다. 이력 취득과 현재 상태 조회를 별도 역할로 설계하고 인증·파싱·제한을 검증한다.

OSM 기반 보행망·계단 분류도 이미 있으므로 새 신호 API를 기다리며 걷기 전체 구현을 멈출 이유는 없다. 검출되지 않은 계단을 없음으로, 거친 지형 추정을 정밀 수치로 표시하지 않는 보완이 필요하다.

## 권장 순서 — 제안, 구현 전

1. 일별 이력 한 날짜의 접근 조건·크기를 확인하고 작은 검증 지역의 교차로/보행 방향/시간대 누락률을 계산. 충분하면 학습용 수집 전환.
2. 기존 서비스 종료 전에 새 현시 API의 인증·쿼터·응답을 검증. 현재 관측이 가능한 범위만 연결.
3. GPS와 시간 계산을 병행 수정. 데이터 대기와 무관한 제품 결함.
4. 계단·지형 자료 대조, 좁은 지역 현장 검증, 모르는 구간을 경로에 표시.
5. 과거 패턴과 현재 관측을 구분. 이력만으로 지금 출발하면 무조건 무정차라고 약속하지 않음. 실시간이 없어도 덜 힘든 경로 비교는 제공 가능.

이번 확인 범위에서 서울 모든 보행 신호를 무제한 제공하는 별도 공개 API는 찾지 못했다. 그러나 **학습용 수집을 일별 이력으로 대체할 구체적 후보는 찾았다.** 현재5분 순환 수집만 확대하기 전에 이를 검증하는 것이 우선이다.
