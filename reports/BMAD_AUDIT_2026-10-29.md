# 쭉고 전체 점검 — GPS·시간·브랜드·경로 신뢰성

2026-10-29 · 대상 https://jjukgo.vercel.app/ · 코드 기준 e31ee59(프로토타입 소스는 배포 eeb4f90과 차이 없음)

## 판단

후속 질문 ‘API 때문에 늦어지는지, 다른 공개자료는 없는지’는 [공개데이터 대안 조사](PUBLIC_DATA_ALTERNATIVES_2026-10-29.md)에 기록했다. 공식 일별 신호 이력 파일 확인으로 이전 판단을 정정했고 기존 API의11월15일 종료 공지도 확인했다. 아래 앱 결함과 데이터 공급 문제는 구분한다.

현재는 **실제 GPS 걷기와 과거 신호 패턴 체험이 한 흐름에 섞인 검증용 프로토타입**이다. 걷기 서비스로 공개한 상태에서 사용자가 기대하는 현재 위치·현재 시각·도착 예상·안내의 기준이 충분히 일치하지 않는다.

사용자가 말한 세 가지는 모두 개선 대상이다. GPS는 이 PC 내장 브라우저에서 시간 초과가 실제 관찰됐고, 별도로 앱의 대기 상태가 남는 버그도 재현했다. 시간 입력은 걷기 목적보다 시·분 조작 자체가 앞선다. 색 값은 유지됐지만 기본 화면에서 브랜드가 드러나는 면적·선택 상태·글자 인상이 약해졌다.

우선은 **위치 상태 → 시간 계산 일치 → 시연과 실제 걷기 분리 → 시간 UI와 브랜드 → 현장 검증** 순서가 적절하다. 색만 먼저 고치면 잘못 이해하기 쉬운 수치를 더 그럴듯하게 만들 수 있다.

## 방법과 한계

- 설치된 BMAD 6.13.0-next의 party-mode/역할별 검토 방식을 참조하고 Product Design audit의 화면·행동·접근성 기준을 적용했다. 프로젝트 `_bmad`와 역할 레지스트리는 없다. roster resolver 결과는 `party_mode=session`, `installed_agents_resolved=false`, `members=[]`였다. **독립 에이전트 팀이나 BMAD 프로젝트 초기화가 완료됐다는 뜻이 아니다.** 기획·UX·개발·QA 관점을 한 세션에서 교차 검토한 보고서다.
- 사용자는 GPS 문제 발생 환경을 **PC 또는 이 앱의 내장 브라우저**라고 확인했다.
- 같은 내장 브라우저에서 실제 홈·검색·경로·조건·신호·출발비교·걷기·시연·요약을 조작했다. 위치 허용을 대신 승인하지 않았다. OS 위치 공급자 문제인지 브라우저 권한 전달 문제인지는 확정하지 못했다. 실제 위치 좌표를 이 보고서에 저장하지 않았다.
- 화면17개를 로컬에 캡처했다. E15는 크기 전환 직후여서 최종 판정 근거에서 제외했다. 나머지16개는 저장된 파일을 직접 열어 확인했다. 스크린샷은 공개 GitHub에 올리지 않고 로컬 `.pytest_cache/bmad-audit-20261029/`에 보관한다.

### 유지할 장점

기존 지도·하단 시트·노랑/아스팔트 조합은 재활용할 가치가 있다. 미확인 신호 대기 제외, 오르막 추정, 실제 신호 확인 문구를 넣은 점도 유지한다. 320px 기본 결과에서 가로 넘침은 관찰되지 않았고 걷기 버튼은 화면 안에 있었다. 검색 결과가 없을 때 아무것도 안 보여 주는 대신 복구 문구를 제공한다. GPS 좌표를 최근 검색/서버에 기본 저장하지 않는 처리, 화면을 숨길 때 위치 구독을 해제하는 처리도 있다.

## 실사용 전에 고칠 것

### F01. 위치 요청 중 화면을 바꾸면 ‘찾고 있어요’가 남는다 — 확정 버그

홈·검색에서 동일한 ‘내 위치를 찾고 있어요…’가 계속 보였다(E04–E06). `locate()`는 화면 또는 request 번호가 달라지면 성공/실패 응답을 버린다. `show()`/`stopGPS()`는 번호를 바꾸지만 대기 문구를 완료·취소 상태로 바꾸지 않는다.

모의 재현: 홈에서 요청 → 결과 화면으로 변경/번호 갱신 → 시간초과 응답. 문구는 여전히 ‘찾고 있어요…’다. 사용자는 계속 요청 중이라고 오해하고 버튼을 반복 누를 수 있다.

개선: 위치 상태를 `미연결/요청중/연결/대략위치/실패/취소`로 관리하고, 취소된 요청의 대기 표시도 종료한다. 중복 요청 중 버튼 상태를 명확히 한다. 완료 기준: 화면 전환과 늦은 응답을 섞어도 유령 대기 문구가 남지 않는다.

근거: [app.js:545](../docs/prototype/src/app.js#L545), [560](../docs/prototype/src/app.js#L560), [1011](../docs/prototype/src/app.js#L1011).

### F02. 이 PC 내장 브라우저에서는 위치를 얻지 못하고 시간 초과 — 관찰 확정, 근본 원인 미확정

걷기 시작 뒤 ‘GPS 연결 중’에서 ‘위치 연결이 늦어져요…’로 바뀌고 거리 세 칸은 비어 있었다(E12). 코드의 timeout 오류 경로와 일치한다. HTTPS만으로 위치 공급이 보장되지는 않는다. OS·브라우저의 실제 권한/공급자 원인을 이번에 확정하지 못했다.

개선: 권한거절/위치사용불가/시간초과/범위밖/정확도부족을 구별하고, 해당 환경에서 가능한 조치와 ‘지도에서 출발지 선택’을 바로 제공한다. 동일 PC의 일반 브라우저와 휴대전화 직접 링크에서도 비교한다. [MDN: 위치 요청의 HTTPS·권한·정책 조건](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition).

근거: [app.js:557](../docs/prototype/src/app.js#L557), [777](../docs/prototype/src/app.js#L777).

### F03. 출발지 찾기와 실제 걷기에 같은100m 정확도 제한을 적용 — 확정 코드, 사용자 발생 여부 미확인

`readFix()`가 오차100m를 넘는 위치를 전부 거절한다. PC가 대략적인 위치만 주는 경우에도 출발 후보를 보여 주지 못한다. 가상 오차500m 입력은 거절됨을 재현했다. 이 PC의 실제 응답 오차가500m였다는 뜻은 아니다.

개선: 출발지 탐색은 대략 위치+오차 범위+지도 수동 보정, 걷기 진행은 별도의 엄격한 정확도 기준으로 구분한다. 정확하지 않은 위치를 횡단 안내에 그대로 쓰지 않는다. [MDN: accuracy는 미터 단위의 위치 오차 정보](https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/accuracy).

근거: [app.js:549](../docs/prototype/src/app.js#L549).

### F04. 출발지 확인 없이 예시 출발지에서 경로가 만들어진다 — 코드·화면 확인

초기 출발지는 서대문역이며 홈에서는 출발지 필드가 보이지 않는다. 목적지만 검색하면 그 출발지/직전 출발지를 쓴다. 검색 화면에서는 시청역 기준 거리라고 나타나기도 했다(E05). GPS 실패 뒤에도 실제 내 출발지로 찾았다고 오해할 여지가 있다.

개선: ‘내 위치 연결/직접 지정/예시 출발지’를 분명히 구별하고, 실제 걷기를 시작하기 전에 출발지를 확인한다. GPS 아이콘으로 화면만 이동한 것을 출발지 변경으로 보지 않도록 한다.

근거: [app.js:495](../docs/prototype/src/app.js#L495), [560](../docs/prototype/src/app.js#L560), [982](../docs/prototype/src/app.js#L982).

### F05. 경로 선택·화면 시간·다음 신호 도착 계산이 다른 기준이다 — 모의 재현

탐색은 모르는 신호에45초 비용을 포함한다. `simulate()`는 그 신호의 대기를0초로 넘겨 총시간과 뒤 신호 도착을 계산한다. 각주가 있더라도 결과의 정밀한 분/초·신호 판단을 신뢰하기 어렵다.

120m/미관측 신호1곳 가상 경로는 화면 시뮬레이션100초, 예산 판정145초다. 더 중요한 사례는 미관측 신호 뒤의 정동 신호다. 같은 가상 경로에서 미확인 대기를 제외하면 대기0초, 가정상45초 지연을 넣으면 약91.06초가 된다. **실제 미관측 대기가45초라고 검증한 것은 아니다.** 불확실한 앞 구간 때문에 뒤 신호의 정확한 예측도 흔들린다는 증거다.

개선: 시간/상태 추정 모델을 한 곳에서 계산한다. 미확인 대기는 범위나 불확실성으로 전달하고, 그 영향을 받은 뒤 신호를 확정 초록/정확한 대기초로 제시하지 않는다. 마감 추천에도 같은 모델을 쓴다.

근거: [app.js:126](../docs/prototype/src/app.js#L126), [200](../docs/prototype/src/app.js#L200), [518](../docs/prototype/src/app.js#L518).

### F06. ‘같은 길의 출발 비교’인데 길이 바뀌고 선택 후 결과도 달라진다 — 화면·모의 재현

추천 카드는 선택한 고정 경로를5초 간격으로 검사한다. 별도 출발 목록은1분 간격마다 `routeFor('jjuk', d)`로 길을 새로 찾으며 전체 시간예산 후보 선택과도 다르다. 서대문→청계 예시의15개 시각 중12개는 기준 경로와 달랐다. 목록의08:41 ‘멈춤0번’을 선택한 상태에서는 결과에 ‘신호 패턴이 없어 신호 개수만 비교’하는 다른 후보가 표시됐다(E10–E11).

개선: 고정 경로 출발 비교인지 출발마다 재탐색인지 하나를 명시한다. 목록에서 계산한 route/sim을 선택 후 그대로 쓰거나 같은 선택 함수를 호출한다. 완료 기준: 목록·추천 카드·지도·선택 결과의 경로 ID와 지표가 일치한다.

근거: [app.js:608](../docs/prototype/src/app.js#L608), [868](../docs/prototype/src/app.js#L868), [1041](../docs/prototype/src/app.js#L1041).

### F07. 현재 시각/GPS와 과거 신호 체험이 섞여 있다 — 확정

`BASE`는08:40, `REAL.date`는2026-10-28이다. 실제 날짜29일에 신호 상세가 ‘앞으로6분’, 목록이08:40을 ‘지금’이라고 부른다(E09–E10). 작은 시연 표시와 현재 위치 연결만으로 이 차이를 충분히 설명하기 어렵다. API가 계속 수집되어도 배포 파일의 내장 패턴을 자동 갱신하는 연결은 없다.

개선: **실제 걷기**와 **신호 패턴 체험**을 모드로 분리한다. 실제 걷기에는 현재 시각과 검증된 최신성 범위를 쓰고, 과거 체험에는 관측 날짜/재생 기준을 지속 표시한다. 현재성을 검증하지 못한 신호색은 현재 안내에 쓰지 않는다.

근거: [app.js:5](../docs/prototype/src/app.js#L5), [52](../docs/prototype/src/app.js#L52), [885](../docs/prototype/src/app.js#L885).

### F08. 신호 방향·횡단 여유·시간대의 검증 수준보다 표현이 단정적이다 — 코드·화면 확인

`known(id)`는 교차로 ID 존재만 검사한다. 방향에 계획이 없으면 기본 계획을 쓰며, 상세 화면도 C-ITS 방향 대응이 가정임을 밝힌다. `MIN_GREEN=8`은 횡단보도 폭/사람별 속도와 무관하다. 상세에는 ‘초록불, 그대로 건너요’ 같은 표현이 존재한다.

개선: 방향 일치·유효시간대·관측 신선도·횡단 길이를 검증한 범위를 분리한다. 부족한 경우 ‘체험 예상’으로 제한한다. 실제 건너기 여부를 앱이 확정하지 않는다.

## 특히 요청한 디자인의 방향 — 아직 확정·구현 아님

### 시간

홈은 ‘언제까지/언제 출발’이라는 걷기 의사결정을 먼저 보여 준다. 도착 마감은 한 줄로 표시하고 누르면 **직접 입력+빠른 조절**이 함께 있는 작은 전용 시트를 연다. 마감이 없으면 큰 비활성09:10 상자는 접는다. 과거 체험의 시간과 실제 현재 시간은 같은 조절 UI에서 섞지 않는다.

출발 비교는15개 비슷한 막대보다 ‘바로 출발/조금 뒤 출발’의2~3개 후보와 바뀌는 도착·대기 범위를 먼저 보여 준다. 막대를 유지한다면 회색 표식의 뜻과 미확인 대기 범위를 함께 설명한다.

### 색·브랜드

원래 복원본4c9796c와 현재의 `lane #F6C343`, `asphalt #2A3140`, `zebra #F7F8F5`, `muted #687082`는 같다. 문제는 토큰 삭제가 아니라 화면에서 쓰는 역할이다. 복잡함을 줄이며 어두운 추천 카드와 특징 있는 표시를 접은 뒤, 기본 화면에 흰 카드와 회색 글씨가 남았다.

추천 경로/선택 상태/진행에 노랑을 일관되게 쓰고, 핵심 현재 상태와 숫자는 아스팔트로 잡는 방향을 제안한다. 검색·시간·경로·걷기의 주요 컴포넌트를 같은 어휘로 묶는다. 핵심 로고/횡단보도·차선 모티프는 적게 반복하되 기능을 방해하지 않게 한다. 빨강·초록은 검증된 신호 상태 설명과 혼동되지 않게 제한한다. 새로운 색을 늘리는 것이 우선은 아니다.

### 한 화면에 남길 것

현재 모드, 출발지 연결 여부, 추천 이유 하나, 예상 시간의 불확실성, 걷기 시작을 남긴다. ‘덜 힘든 길’의 이유를 접힌 기술 상세 안에만 두지 않는다. 사용자가 원하는 것은 숫자 여러 개보다 **이 길을 골라도 되는 이유**다.

## 검증 우선순위와 완료 기준

1. **위치:** 요청 취소·응답 지연·권한 거절·대략 위치를 구별한다. 내장 브라우저가 시간 초과해도 멈춘 요청처럼 보이지 않고 지도 수동 선택으로 이어진다.
2. **시간:** 탐색·예산·마감·출발 추천·다음 신호 도착이 같은 시간 모델을 쓴다. 미확인 대기 영향은 숨기지 않는다. 목록을 선택한 뒤 경로와 수치가 맞는다.
3. **모드:** 현재 걷기와10/28 신호 체험의 날짜·위치·기록을 명확히 분리한다.
4. **인터페이스:** 시간 입력과 추천/선택 색 역할을 바꾼 뒤 같은 과업을 말 없이 수행할 수 있는지 관찰한다. 모의 화면만 예뻐졌다고 완료하지 않는다.
5. **현장:** 휴대전화 직접 링크에서 위치 허용/거절/오차/잠금복귀/이탈을 확인하고, 실제 계단·경사·횡단 구간의 대조 표본을 확보한다. 안전한 현장 동행 기록으로 예측 오차를 확인한다.

이 항목들은 에이전트의 개선 제안이며 사용자 확정 설계/구현 완료가 아니다.
