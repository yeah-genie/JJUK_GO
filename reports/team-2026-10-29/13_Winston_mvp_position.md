## 1. 결론 (한 단락)

gate는 **제품 전체에 하나가 아니라 횡단 하나마다 하나**로 두는 것이 맞다. 다섯 조건(방향, 점멸·진입 의미, 길이, 날짜 안정성, 개인 속도) 중 앞의 둘은 "하나의 사실"이라 현장 30분과 명세 질의 한 건으로 풀릴 수 있고, 길이는 열린데이터광장 키 하나로 풀린다. 날짜 안정성은 Codex 측정(평일끼리 일치율 95% 이상 셀 82.6%)이 내가 제안한 90% 기준에 못 미쳤으므로, 기준을 낮추지 말고 **셀마다 "다른 날과도 일치했는가"를 데이터에 기록해 통과한 셀만 숫자를 열고 나머지는 '모름'**으로 두는 쪽을 권한다. 그 사이에도 데이터만으로 정직하게 보여 줄 수 있는 정보(계단, 오르막, 큰길 횡단 개수, 교차로 단위 이력 유무, 우회 거리)가 있어서 첫 화면이 '측정 전'만 보이지 않게 할 수 있다. 구조는 단일 HTML + 정적 JSON + 서버리스 1개로 MVP에 충분하다. 바꿀 것은 두 가지뿐이다. 횡단 계산과 gate 판정을 DOM 없는 순수 모듈로 분리하고, 신호 패턴 데이터에 요일 종류·점등/점멸 분리·셀별 근거를 추가한다. 인증키는 브라우저에 절대 들어가지 않고 오프라인 스크립트(GitHub Secrets)에서만 쓴다.

### 2-3. 현장 30분 설계 (사용자 부담을 최소로)

**왜 한 교차로로 되나, 그리고 왜 한 교차로로는 모자라나.** 방향 대응은 4개 가설(같은 방위, 반대 방위, 직각 둘) 중 하나를 고르는 문제라서, 한 교차로에서 4개 횡단의 시각을 맞춰 보면 한 가설만 남는다. 다만 컨트롤러 제조사·설정이 다르면 다른 교차로에서 다른 대응일 수 있다 [미확인]. 그래서 한 곳은 "가설을 가르는" 용도이고, 일반화는 1번(명세 답)과 5번(셀별 근거)이 맡는다. 가능하면 형태가 다른 곳 2~3곳(4지, 3지, 일방통행 포함)이 이상적이나 첫 번째가 가르는 것만 되면 충분히 진척이다.

**어디서.** 08시 패턴이 4방향 모두 있고 보류(holdout) 적중률 99% 이상, 관측 15분 이상인 교차로가 183곳이다 [측정]. 도심 쪽 예: 무교동사거리(id 3967, 패턴 날짜 10/26 월, 주기 170초), 종로구청입구(1817, 10/26 월, 170초), 종로1가(1819, 10/26 월, 170초), 세종대로사거리(1821, 10/17 토 날짜라 평일 현장과 비교에는 불리), 명동성당(2875, 10/26 월). 사용자가 다니는 동선에 가까운 곳이 있으면 그쪽이 낫다. 에이전트가 183곳에서 가까운 후보를 뽑아 준다.

**언제.** 평일 08~10시(패턴이 있는 시간대). 한 주기가 약 170초라 30분이면 약 10주기다. 휴대전화 시계를 인터넷 시각과 맞춘 뒤 시작한다.

**무엇을.** 횡단보도 4개마다 "초록 켜짐 / 점멸 시작 / 빨강" 시각을 3주기 이상(스톱워치 랩 또는 영상 촬영 후 판독), 그리고 그중 2곳의 길이(줄자 또는 걸음 수×보폭, 지도 앱 거리재기 병행).

**판정.** 에이전트가 기록 시각을 패턴 예측(`day0 + t − ref mod c`, `win`)에 대 본다. 가설별로 예측 초록 시작 4개와 실측의 차이를 낸다. 한 가설이 4개 횡단 모두 ±3초 안이면 채택, 아니면 미해결. 기록에는 현장 날짜를 같이 남겨, 패턴 날짜와의 요일 차이도 같이 본다.

**한계.** 패턴은 과거 하루의 값이라(예: 10/26) 현장 요일의 위상이 그 날과 어긋날 수 있다. 어긋나면 "대응이 틀림"과 "날짜가 안 맞음"이 섞인다. 그래서 **횡단 4개 사이의 상대 시각(예: 북쪽 팔이 켜진 뒤 몇 초에 동쪽 팔이 켜지는가)**을 먼저 보고, 절대 시각은 그 다음에 본다. 상대 시각은 하루 위상 오차에 둔감하다. 점멸 시작의 실측 시각이 `permissive` 구간 시작과 맞는지는 같은 기록에서 나오지만, 패턴이 점등/점멸을 합쳐 두었기 때문에 그 비교는 5번(분리 재내보내기) 뒤에 한다 [현재 데이터로는 불가].

| 이력이 있다는 표시의 의미 | - | - | "자료가 있다"일 뿐 "건널 시간이 충분하다"가 아니다 | PRODUCT_SPEC §4 범례(이력 있음/미확인)와 일치 |

**쓰면 안 되는 것(gate 뒤로 미룬다):** 횡단별 이력 유무(방향 키), 멈춤 N곳(방향·요일·도착 위상), 여유 초, 지도상 '쉬운 횡단' 등급.

**정직한가에 대한 판단.** 위 표의 위쪽 항목들은 "무엇이 있다"는 지도 사실이고, 아래쪽은 "이 자료가 있다"는 존재 사실이다. 어느 쪽도 "건널 수 있다"를 말하지 않는다. 두 가지는 지켜야 한다.

1. **이름과 내용이 어긋나지 않게.** 후보 이름이 `여유 있는 길`이면 사용자는 여유를 측정했다고 읽는다. PRODUCT_SPEC §6도 "이름은 선택지의 이름이지 검증된 여유의 주장이 아니다"라고 한다. gate가 닫혀 있는 동안 두 후보의 차이 줄은 위 표의 사실(횡단 3곳 적음 · 계단 0 · +4분)만 쓰고, 이름이 만든 인상을 사실이 받쳐 주게 한다. 이름을 바꿀지는 John·Sally의 몫이다.
2. **"모름"을 숨기지 않게.** 지도상 횡단 N곳 중 이력 있는 교차로가 몇 곳인지를 같이 보이지 않으면 "횡단이 적은 길"이 "신호 부담이 적은 길"로 읽힌다.

**한계.** 이 표의 값은 후보 비교에는 유용하지만 비교 기준 자체가 "개인 걸음으로 건널 시간"이 아니므로, 쭉고의 핵심 약속(내 걸음으로 초록불 안에 건널 수 있나)은 gate 뒤에야 전달된다. 이 격차는 데이터 문제가 아니라 제품 정의 문제이고 John·Sally가 풀어야 한다. 그늘로가 해·그늘을 전 지역에서 계산하는 것과의 비대칭은 구조로는 없앨 수 없다 [Mary 12].

## 4. 열린 뒤의 계산 구조

### 4-1. 용어

신호 패턴에서 한 횡단의 한 주기 안에는 세 구간이 있다고 가정한다(검증 전). 점등 `S`(고정녹색), 점멸 `F`, 빨강. 법령은 녹색 점멸에서 새로 횡단을 시작하지 못하게 한다 [문서: 도로교통법 시행규칙 별표 2, Codex Q2]. 그러면 숫자가 세 가지로 갈린다.

| 이름 | 식 | 뜻 | 쓰임 |
|---|---|---|---|
| 완료 여유 (초록 시작 기준) | `A = (S + F) − L/v` | 초록이 켜진 순간 출발하면 끝낸 뒤 남는 시간 | 지금 PRODUCT_SPEC §6의 "정적 개인 횡단 여유"가 이것에 가깝다 |
| 막판 진입 여유 | `B = F − L/v` | 점등 마지막 순간에 들어가도 점멸 안에 끝나는가. 음수면 점등 끝에 들어가면 못 마친다 | "초록이 보일 때 아무 때나 들어가도 되는가"에 대한 정직한 답. 느린 걸음에서 A와 B의 차가 가장 크다 |
| 진입 가능 시간 | `E = S` | 새로 들어갈 수 있는 구간의 길이 | 걷는 중, 기다리는 중. 첫 화면 숫자로는 쓰지 않는다 |

도착 시각을 아는 경우의 동적 여유 `rem − L/v`는 따로 둔다(도착 시각 오차 `σ`가 진입 가능 시간 대비 충분히 작을 때만 노출, Codex Q2 지적대로 20초 같은 고정 임계가 아니라 `E`나 여유 대비 비율로). 빨강 직전의 전적색(all-red) 시간은 자료에 없어서 모델에 넣지 않는다. 이것이 계산이 과대평가하는 쪽이라는 점을 '계산 기준'에 쓴다.

**점멸 의미(`permissive`=점멸)가 거짓이면** `S`와 `F`를 나눌 수 없고, `A`만 가능하며 `B`와 `E`는 모름이다. 구조가 이를 견디도록 `S`/`F` 각각에 품질 값을 붙인다.

### 4-2. 데이터 구조 (확인 / 추정 / 모름)

한 횡단마다 근거를 값과 같이 들고 다닌다. 품질은 `ok | est | unk` 세 값이고, 합칠 때 가장 약한 쪽을 따른다(08 §2-3과 동일).

```
crossing = {
  id, signal: { id, legApp, legSignal, mapping: { q, evidence } },   // 방향 대응: 현장/명세로 확정되면 ok, 가정이면 est(이면 gate 닫힘)
  length:    { m, q, src: "oa21209" | "graph-lane", matchM, halves },
  phase:     { c, ref, steady: [[a,b]], flash: [[b,c]] | null,        // flash가 null이면 B, E는 unk
               dayType: "weekday" | "weekend", hour,
               evidence: { daysAgree, daysTotal, agreeMean, observedMin, patternDate } },
  speed:     { v, src: "manual" | "learned" | "default" }
}
gate(crossing, ctx) → { open: bool, missing: ["mapping","flash","length","day","speed"] }
```

- **gate는 순수 함수이고 fail-closed.** 증거 필드가 없으면 false다. `open`이 아닌 이유(`missing`)를 반환해서 화면의 "자료 확인 중"을 이유별로 바꾸고, 어느 조건이 가장 많이 막는지 지표로 센다.
- **경로 요약.** 확인된 횡단 중 가장 빠듯한 `A`(또는 `B`)와 "모름 N곳"을 항상 같이 낸다. 모름이 더 많으면 숫자를 키우지 않는다(Sally 5-3, 08 T3).
- 속도를 바꿔도 변하는 것은 `L/v`뿐이다. `S`/`F`/`L`은 속도와 무관하므로 속도 선택 UI는 재계산이 가볍다.

### 4-3. 구간 의미를 바꿀 때 영향받는 곳

`sigWait`/`MIN_GREEN=8`/`simulate`는 건드리지 않는다. 이전 문서(08 §2-3 단계 A)와 같은 입장이다. 새 필드를 추가하고, 경로 탐색 비용 함수는 gate가 열린 뒤에 따로 바꾼다. 이유는 멈춤 횟수가 흔들리면 비교가 어렵기 때문이다. 단 Codex가 인정했듯 `MIN_GREEN=8`은 개인 속도에서 나온 값이 아니므로, 화면에는 "멈춤"과 "여유"를 같은 근거인 것처럼 묶지 않는다.

### 5-3. 바꿀 것 (최소)

1. **`src/crossing-core.js` 신설(순수 모듈).** `gate()`, 완료 여유 `A`/막판 진입 여유 `B`/진입 가능 시간 `E` 계산, 품질 합성, 점멸 경계에 걸쳐 쪼개진 초록 창 합치기(08 §2-3: `[[138,140],[0,31]]`는 33초지 2초가 아니다), 요일 종류 판정. DOM·fetch·localStorage 금지. 근거: 이미 `walking-profile.js`, `walk-card.js`가 같은 방식이고(Rule of Three를 넘겼다), 시험이 화면 스텁 없이 돌고, `gate`가 PRODUCT_SPEC §6의 "한 곳에서 관리"를 구조로 만든다.
2. **신호 패턴 데이터 형식 확장.** `win`을 `steady`와 `flash`로 나누고, `dayType`과 `evidence{daysAgree,daysTotal,agreeMean}`를 셀에 붙인다. `export_history_plans.py` 변경이며 14일 CSV.GZ가 필요하다(§6의 4번). 형식이 바뀌어도 앱은 옛 형식을 `unk`로 읽어 깨지지 않게 한다.
3. **CI 두 줄:** `python scripts/build_prototype.py && git diff --exit-code docs/prototype/index.html`.
4. **서울 전체가 아닌 "검증 구역" 개념.** 데이터 파일 하나(`seoul/verified.json`: 교차로 id 목록 + 확인 항목 플래그)로 구현할 수 있다. 앱 로직이 아니라 데이터로 gate가 열리므로, 구역이 늘어도 코드는 바뀌지 않는다.

바꾸지 않는 것: 번들러·프레임워크·서버 DB·계정·실시간 신호 API. 이유는 지금 문제의 원인이 구조가 아니라 증거라서다. 서버가 필요해지는 시점(실시간 신호, 사용자 데이터 동기화)은 gate가 열리고 5명 걷기가 끝난 뒤의 질문이다.

### 5-4. 키 관리

- **인증키는 브라우저에 들어가지 않는다.** OA-21209는 정적 자료라 오프라인 스크립트가 한 번 받아 `crosswalk-len.json`으로 만든다. 앱은 키를 모르고, 서버리스 함수도 필요 없다.
- 열린데이터광장 키는 GitHub Secrets에 `SEOUL_OPENAPI_KEY` 같은 새 이름으로 넣는다. 현재 저장소 Secrets는 `DATA_GO_KR_KEY`, `SEOUL_TDATA_API_KEY` 두 개(이름만 확인, 값은 읽지 않음)이고 이는 다른 사이트 키라 같은 키로 단정하지 않는다 [문서: Codex Q4 ①].
- 사용자는 값을 채팅에 붙이지 않고 GitHub 설정에 직접 넣는다. 에이전트는 `workflow_dispatch` 작업에서 환경변수로만 읽고 로그에 찍지 않는다. 키가 필요한 workflow는 기본 브랜치에서만 돌게 한다.
- 8088 포트는 HTTP 샘플만 확인됐다. 서버 측 스크립트에서만 호출하고 브라우저에서는 호출하지 않는다(혼합 콘텐츠). HTTPS 엔드포인트 존재 여부는 [미확인].
- 공공누리 1유형 자료는 출처 표시가 필요하다. 앱의 '계산 기준'과 푸터에 출처·기준일을 넣는다 [문서: 08 §2-2 "공공누리 1유형"].

### 5-5. 데이터 갱신 방식

- MVP에서는 **자동 매일 갱신을 하지 않는다.** 신호 패턴은 14일 기준선이고 실시간이 아니다 [문서: `signal-plans.json`의 kind]. 갱신은 수동(월 단위) `workflow_dispatch`로 충분하다.
- 이유: (1) Q1~Q3가 풀리기 전에 자동화하면 미검증 숫자를 매일 새로 쓴다. (2) 매일 시간대 JSON 3~24개가 커밋되면 저장소 객체가 커진다(파일당 1.3~1.5MB, 압축 후 약 130~150KB여도 매 커밋에 새 객체). 저장소에 이미 `scripts/data_branch.sh`(데이터 브랜치)가 있으니 필요해지면 그쪽에 둔다.
- Codex Q7에 따르면 기존 3종 실시간 API는 2026-11-15에 종료되고 대체 서비스(10381 통합 OpenAPI, 10382 이력 파일)가 안내돼 있다. `collect.yml`은 이미 `disabled_manually`다. 이력 파일(10382)은 계속 쓸 수 있는 경로이므로 MVP 데이터 파이프라인은 이력 파일 기반이다.
- 패턴이 낡는 문제: 신호 계획이 바뀌면(공사, 행사) 14일 전 패턴이 틀린다. 앱은 '기준일'을 보이고, 일정 일수가 지난 패턴은 `unk`로 만료시키는 규칙을 둔다. 만료 일수는 근거가 없어 가정으로 둔다 [가설].

| R1 | **신호 방향 대응이 틀림** | 모든 신호 숫자의 전제. 08의 측정에서 두 대응이 모두 아는 횡단 72곳의 초록/빨강이 69%만 일치, 멈춤 횟수가 달라진 경로 25개 중 13개 [측정, 표본 작음] | ① 현장 30분 1곳(§2-3) ② T-Data 문의 ③ 길이가 붙은 뒤 횡단 길이와 초록+점멸 길이의 상관 재검(전제가 약해 보조용) | gate 2 |

| R3 | **횡단 길이 단위·축·매칭 오류** | 지금은 92%가 5개 값인 차선 환산. OA-21209가 단위를 안 밝히고 NODE/LINK가 섞였고, 중앙분리대 분할 처리 불명 [문서] | 키 발급 → 전량 수령 → 매칭률과 현장 줄자 2곳 대조. 합격 기준은 §2-4에 선결 | gate 4 |
| R4 | **날짜 안정성: 평일 95%여도 셀 82.6%, 08~10시만, 09시 관측 구멍** | 기준(90%) 미달. 또한 하루 안에서도 시간대마다 관측이 듬성하다 [문서: Codex Q3, 08 §2-1] | 14일 CSV.GZ로 셀별 일치 기록 → "통과 셀만 숫자" 정책. 자료 접근이 선결 | gate 5 |
| R5 | **한 곳에서 맞은 것을 서울 전체로 일반화** | 현장은 1~3곳, 컨트롤러 설정이 다를 수 있음 [미확인]. 맞는 곳에서만 숫자를 열지 않으면 틀린 곳에서 틀린 숫자가 확신 있게 나옴 | "검증 구역"을 데이터로 두고 그 안에서만 개방, 구역 밖은 '모름'. 가능하면 형태가 다른 교차로 2~3곳 현장 | gate 전체 |

(순위는 gate를 막는 힘과 발견의 어려움 기준이다. R1이 가장 크고 현장 한 번으로 가장 많이 줄어든다.)

### 6-2. 의존 관계 순서 (일정 아님)

```
[에이전트, 사용자 0]  요일 불일치→모름 / gate 함수·fixture / 데이터만 표시(§3)
        │ (병렬, 아래와 무관하게 먼저 가능)
[사용자 5~10분] 키 발급 ──→ [에이전트] OA-21209 전량·매칭 ──→ 길이 'ok/est' 분포
[사용자 5~10분] T-Data 문의 게시 ──→ (답 도착 대기, 미확인)
[에이전트] 후보 교차로·기록지 ──→ [사용자 30분] 현장 ──→ [에이전트] 가설 판정 ──→ 방향 대응 채택/미해결
[사용자 자료 접근 한 번] 14일 CSV.GZ ──→ [에이전트] 셀별 일치·요일 분리·점등/점멸 분리 ──→ 데이터 형식 확장
        └───────────────┬───────────────┘
        각 횡단의 5조건이 모두 ok인 곳만 gate 개방 (검증 구역)
                        │
        [사용자] 5명 걷기 (gate 개방 구역에서만 의미가 있다)
```

기다림이 생기는 곳은 두 곳이다. T-Data 문의 답과 자료 접근이다. 그래서 둘을 가장 먼저 시작해 두고, 기다리는 동안 에이전트가 할 수 있는 모든 것(gate 함수, 데이터만 표시, 현장 준비)을 한다.

## 7. 다른 역할의 입장에 대해 예상되는 반대·충돌 2개와 내 대응

1. **John·Sally: "서울 전체에 숫자가 나와야 그늘로와 겨룬다. 구역 한정은 MVP가 너무 작다."**
   - 내 대응: 구역 한정은 숫자에만 적용한다. 지도, 계단, 오르막, 큰길 횡단 N곳, 우회 거리는 서울 전체에 열린다(§3). 숫자를 서울 전체에 열려면 R1~R4가 모두 서울 전체에 대해 참이어야 하는데, 지금은 한 곳도 확인되지 않았다. 틀린 숫자를 전체에 확신 있게 보이는 것보다, 작은 구역에서 맞는 숫자를 보이고 구역을 데이터로 늘리는 것이 되돌리기 쉽다. 구역 크기는 현장·자료 접근 속도가 정한다.
2. **Mary(또는 Codex 입장): "'긴 횡단' 표시도 차선 환산이라 길이 숫자가 아니다. 넓은 길 표시조차 gate 위반이다."**
   - 내 대응: 동의하는 부분이 크다. 그래서 미터 숫자는 쓰지 않고 '큰길 횡단'이라는 분류와 '추정' 라벨만 쓰며, "긴 횡단 N곳"은 OA-21209 매칭이 '확인' 조건을 통과한 횡단에만 붙인다(§3). 분류는 지도 사실이고 개인 여유 숫자 gate(§6)의 대상이 아니다. 다만 분류가 "건너기 어렵다"로 읽히면 같은 문제가 되므로 문구는 "큰길" 이상으로 가지 않는다.

## 8. 다른 역할에게 묻고 싶은 것 2개

1. **John에게:** "검증 구역 안에서만 숫자가 열리는 MVP"도 MVP 완료로 인정하는가? 인정하지 않으면 서울 전체 gate를 기다려야 해서 일정 의존이 크게 달라진다.
2. **Sally에게:** 4-1의 세 숫자(완료 여유 A, 막판 진입 여유 B, 진입 가능 시간 E) 중 첫 화면에 몇 개까지 놓을 수 있는가? 나는 한 개(A)를 권하고, A와 B의 차가 큰 느린 걸음에서만 B를 상세에 둔다. 화면 쪽이 둘을 한 장면에 담을 수 있다면 구조는 둘 다 지원한다.

## 9. 사용자에게 필요한 결정·작업 (최대 5개)

1. **열린데이터광장 인증키 발급(약 10분)** 후 GitHub Secrets에 `SEOUL_OPENAPI_KEY`로 직접 저장. 값은 채팅에 붙이지 않는다. 이것이 길이 확인의 전제다.
2. **현장 30분 1회:** 평일 08~10시, 4방향 교차로 한 곳(무교동사거리·종로구청입구 등 또는 동선에서 가까운 곳)에서 횡단보도 4개의 초록·점멸·빨강 시각을 스톱워치로 3주기 이상, 횡단 2곳의 길이를 줄자나 걸음 수로. 기록지와 후보 목록은 에이전트가 준비한다.
3. **T-Data 문의 게시:** 10382/10381의 방향 필드가 걷는 방향인지 횡단 위치인지, `permissive`가 녹색 점멸인지 묻는 한 건. 문안은 에이전트가 쓴다.
4. **14일 이력 자료 접근 방식 선택:** 이 샌드박스에서는 Release 자산 호스트가 403이었다 [문서: 08]. 네트워크 허용을 열어 줄지, 사용자가 369MB를 내려받아 전달할지, 또는 Codex 쪽 로컬 자료를 쓸지 정한다. 이것이 막혀 있으면 날짜 안정성(R4)과 점멸 분리(R2)는 진행되지 않는다.
5. **첫 공개 범위 결정:** (a) 숫자는 검증 구역에서만 열고 나머지는 §3의 사실 정보로 공개(권고), (b) 서울 전체 gate를 기다린 뒤 공개. 이 결정이 Threads 공개 시점과 Vercel 플랜 확인(수익·광고 계획이 있으면 Hobby 약관 확인) 시점도 정한다.

## 10. 미확인 (한곳에 모음)

- `permissive`=녹색 점멸 여부, 방향 필드의 정의, T-Data 문의 답이 올 시간.
- 한 교차로의 방향 대응이 다른 교차로에도 같은가(컨트롤러 제조사·설정 차이).
- OA-21209 전량의 범위·단위 원본 정의·중앙분리대 분할, OA-15554 `HOL`/`VEL`의 축과 단위, 20MB 공간 ZIP 수령 가능 여부.
- 14일 CSV.GZ 접근 방법. 09시 관측 0건의 원인(원본/변환).
- Vercel 플랜 한도(배포 크기, 상업 이용), `https` 엔드포인트 유무(OA-21209), 이동망 실제 로딩 시간.
- 신호 패턴 만료 일수의 적정값, 신호 계획 변경 빈도.
- 이 문서에서 처음 낸 숫자 중 간선 단위 통계(25,751 중 길이 분포, 이력 커버리지 58.0%/35.9%)는 일방통행 반쪽을 포함한 간선 기준이며 횡단 묶음이나 사용자 경로 가중이 아니다 [측정 범위의 한계].
- 실제 휴대전화 야외 보행 0회, 화면 시험(Playwright) 이번에 실행하지 않음. 앱 코드는 읽기만 했다.
