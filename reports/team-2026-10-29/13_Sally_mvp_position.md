## 1. 결론

gate가 닫혀 있어도 쭉고의 첫 가치는 **"여유 초"가 아니라 "이 길에서 건너야 할 횡단이 몇 곳이고, 그중 내가 아는 곳이 몇 곳인지"라는 세 숫자**로 첫 화면에서 보일 수 있다. 이미 앱이 계산해 쥐고 있는 값이다(결과의 `경로상 신호 6곳`, 횡단 목록 6곳 중 이력 있음 2·없음 4 **[확인]**). 그늘로의 해/그늘 대비에 해당하는 쭉고의 대비는 **노랑 링(이력 있음) 대 점선 `?`(모름)** 이고, 이것을 홈 지도 → 결과의 한 열 → 횡단 목록까지 같은 모양으로 이어 놓는다. 숫자 열은 gate가 열리면 같은 자리에서 `횡단 여유 ~N초`로 바뀌므로 지금 만든 화면이 버려지지 않는다. 그리고 지금 첫 5초(로고 3.2초 → 설문 2문항)는 가치 없이 지나간다. 이것이 gate보다 먼저 고칠 UX 문제다. 구현 결함은 §6에 캡처 근거와 함께 12건 적었고, 그중 `0초` 표시·남은 토글·빈 지도 위 링은 규칙(`DESIGN_SYSTEM`, `PRODUCT_SPEC`)과 직접 충돌한다.

## 3. 제안

### 3-1. gate가 닫힌 첫 사용자에게 가치를 전하는 방법 (결정 사항 1)

원칙 하나: **닫힌 것은 "여유 초"뿐이다. 횡단의 수·이력 유무는 계산돼 있으니 보여 준다.** 단, 이 숫자를 `여유`·`쉬움`·`안전`처럼 읽히게 하지 않는다. 이름은 `횡단 N곳`, `이력`, `모름` 세 단어만 쓴다.

**① 첫 5초 흐름 [제안]**

```
0.0s  로고(건너뛰기 가능, 최대 약 3.2s)
        서두르지 않아도 되는 길            <- 컨셉 한 줄(사용자 확정 문구)
        출발 전에 횡단을 미리 세어 봐요       <- 지금 실제로 하는 일
3.2s  설문 1/2  (건너뛰기를 윤곽 버튼으로, 12px 회색 글 아님)
5s    홈: 지도 위 노랑 링 + "근처 횡단 이력 12곳" + 예시 길 행
8s    예시 길 탭 -> 결과: 27분 | 횡단 6곳 | 이력 2 · 모름 4
```

**② 홈 첫 실행 와이어 (390x844, 최근 찾은 곳 없음)**

```
+--------------------------------------+ 0
| 쭉고 //                            ⚙ |

| 출발지를 정해 주세요           변경 |
+--------------------------------------+ 148
|                                      |
|  지도 (실제 서울)                    |
|        (O)                           |
|                    (O)               |
|   (O)                                |
```

- 지도에는 **링(이력 있음)만** 깐다. 점선 `?`는 경로 위에서만 그린다. 홈에서 `?`를 수백 개 뿌리면 "대부분 모름" 화면이 되고 [추정], 지금 범례의 `미확인`은 화면에 없는 표식을 설명하고 있다(§6 D4). 범례는 화면에 해당 표식이 있을 때만 그 칸을 보인다.
- `근처 횡단 이력 N곳`: 보이는 영역 안 링 개수. 숫자 하나가 "이 앱이 아는 것"을 말한다. 계산 비용은 Amelia에게 묻는다(§5).
- `최근 찾은 곳`이 비어 있을 때는 제목을 숨기고 **예시 길 한 행**을 넣는다. 지금은 빈 제목 아래 작은 텍스트 링크다(`07`). `예시` 표식은 유지(실제 길이 아니라는 뜻).
- 공감 문장은 하단 한 줄만. 두 번째 방문부터는 최근 장소가 이 자리를 차지하고 문장은 사라진다.

- 열 머리 `횡단 여유 / 초록 시작 기준`을 gate 닫힘 동안 **`횡단 6곳`** 으로 바꾸고, 칸 안에 링·`?` 6개를 한 줄로 늘어놓는다(숫자 + 모양, 글은 `이력 2 · 모름 4` 한 줄). 지도의 모양과 같다. 눈이 지도에서 목록으로 같은 기호를 따라간다.
- gate가 열리면 **같은 열 머리가 `횡단 여유`로 돌아가고** 칸은 `~N초`(+모르는 곳 수)가 된다. 열 하나의 내용 교체이므로 레이아웃 변경이 없다. 이 열의 모양은 `PRODUCT_SPEC §6`의 "모름이 있으면 그 수를 붙인다"와도 같다.
- 후보가 같으면 행을 하나로 두고 이름은 `여유 있는 길`(사용자 결정 이름). 지금은 이름이 `걷기 경로`로 나온다(§6 D5). `여유 있는 길`이라는 이름 옆에는 `건널 수 있음`류 문구를 붙이지 않고, 열 머리가 `횡단 6곳`이라서 이름이 숫자를 보증하는 것처럼 읽히지 않는다 [추정, 현장 확인 없음].
- `08:40 예시 · 임시 걸음 기준 · 과거 신호 이력 · 두 후보가 같은 길이에요` 한 줄은 쪼갠다: 같은 길 안내는 행 바로 아래, `예시 · 임시 걸음 기준` 은 행 끝 작은 태그로. 4가지 사실을 12px 한 줄에 묶지 않는다.

**④ 정보 없는 횡단 목록(펼침)** — 빈 라디오 원을 지도와 같은 기호로 바꾼다.

```
‹  경로의 횡단 6곳
(O) 세종대로사거리 남쪽        이력 있음
(?) 서대문역 북쪽              모름
 ...

```

### 3-4. 공유(Threads 빌드인퍼블릭) 장면 (결정 사항 4)

걷기 기록 앱·카운트다운은 삭제 확정이라 제외했다.

- **장면 1 — "모르는 곳은 모른다고 적었다"**: 결과 화면 캡처 한 장. 열 머리 `횡단 6곳`, 칸의 `(O)(O)(?)(?)(?)(?)`, 한 줄 `이력 2 · 모름 4`. 글 예: `신호 이력으로 건너는 여유를 보여 주려고 만든 앱인데, 오늘은 6곳 중 2곳밖에 몰랐다. 그래서 숫자 대신 모름을 그대로 보여 주기로 했다.` 이 화면은 정직 규칙이 곧 제품의 얼굴이라는 점이 한 장에 나온다. 화면의 값은 **예시 길** 값임을 캡션에 쓴다.
- **장면 2 — "서울 교차로 2,352곳"**: 홈 지도 확대 캡처(`07b`와 같은 구도, 링 두세 개). 글 예: `서울 교차로 2,352곳의 신호 이력을 지도에 연결했다. 아는 곳에만 노란 원이 있다.` 2,352는 meeting brief의 수치. 홈에 `근처 횡단 이력 N곳` 숫자가 들어간 뒤에 찍는다(지금은 숫자 글이 없어 장면이 약하다).

둘 다 걷는 사람의 실사용 후기가 아니다. 실기기 보행 시험은 0회이므로 "써 봤더니"류 글은 쓰지 않는다.

## 4. 예상되는 반대·충돌 2개와 내 대응

1. **John(PM): "MVP는 gate를 여는 일이 먼저다. UX로 닫힌 숫자를 포장하지 말자."** → 포장이 아니라 사실 3개를 보이는 것이다. 열 머리가 gate 상태에 따라 `횡단 6곳` ↔ `횡단 여유`로 바뀌는 구조라 gate 작업과 병행되고 버려지지 않는다. gate가 언제 열리는지 모르는 동안 첫 사용자를 지금 빈손으로 두지 않기 위한 것이다.
2. **Winston/Amelia: "`횡단 6곳`의 정확도는? 이것도 검증 전 숫자다."** → 맞다. 이 개수는 OSM 횡단과 신호 이력 연결에 의존하고 정확도는 **[모름]**. 대응: 이름을 `지도에서 찾은 횡단 6곳`(계산 기준 시트에 같은 문구)로 하고 `~` 없이 개수만 쓰되 시트에 출처를 적는다. 정확도가 의심되면 홈의 `근처 이력 N곳`만 먼저 넣고 결과 열은 후속으로 미룬다. 데이터 쪽 판단을 따른다.

(별도 충돌) `PRODUCT_SPEC` 머리말은 걷기 종료 인증 카드 복원을 적고, 회의 안건은 걷기 기록 앱 삭제 확정이라고 적는다. 카드가 기록 기능으로 읽히는지에 따라 MVP 범위가 달라진다. 결정 4로 올린다.

## 5. 다른 역할에게 묻고 싶은 것 2개
