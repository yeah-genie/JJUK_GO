## 0. 판정 요약

1. **엔진은 Codex 브랜치에서 가져오고, 제품 화면은 Claude 쪽 정의(06·07)로 새로 간다.** 이 체크아웃의 신호 데이터는 내장 4곳뿐이다(`app.js` 52행 `REAL`, 2026-10-28분). John의 "멈춤 N곳"은 이 상태로는 광화문 밖에서 전부 '모름'이다. 공식 이력 패턴 파이프라인(2,352곳)은 새로 만들 이유가 없다.
2. **가져오는 방법은 "파일 단위 checkout 한 번 → 제품 면 덜어내기"가 가장 작다.** 손으로 조각 이식하면 `search`/`simulate`/`computeTrip`/`renderResult`가 모두 얽혀 있어(737줄 변경) 같은 일을 더 위험하게 다시 하게 된다. 두 브랜치는 같은 조상(`eeb4f90`)에서 갈라졌고 이 체크아웃 쪽 변경은 문서뿐이라 코드 충돌이 없다 [측정: `git merge-tree`, 충돌 표지 0].
3. **가져오기 전에 알아야 할 데이터 문제가 3개 있다.** 모두 이번에 수치로 확인했다.
   - **요일:** 앱이 쓰는 08~10시 패턴의 30%가 토·일 날짜에서 맞춘 것이다. 그 패턴으로 화요일(10/27)을 맞히면 79%인데, "항상 빨강"이라고만 해도 77%다. 평일에서 맞춘 패턴은 98.5%였다 [측정].
   - **방향:** 신호 방향 코드(nt/et/st/wt)와 앱의 횡단보도 방향(n/e/s/w)이 직각으로 어긋났을 가능성이 있다. 두 대응 방식이 모두 아는 횡단 72곳에서 초록/빨강이 69%만 일치했고, 경로 25개 중 13개의 멈춤 횟수가 달라졌다 [측정, 가설].
   - **횡단 길이:** 그래프의 횡단 길이는 측정값이 아니라 차선 수 환산이다. 신호 횡단 25,751개 중 92%가 5개 값 중 하나다 [측정].
4. **"횡단 여유"는 두 가지로 나눠야 한다.** (a) 도착 시각과 무관한 **정적 여유 = 초록 길이 − 내 걸음으로 건너는 시간**, (b) 도착 시점의 **동적 여유 = 남은 초록 − 건너는 시간**. 06이 말한 "멈춤 N곳 + 건널 여유"의 두 번째 숫자는 (a)여야 한다. (b)는 출발 시각이 몇 초만 틀려도 부호가 뒤집힌다(§2-3).
5. **`MIN_GREEN=8`은 느린 걸음에서 틀린다.** 15.8m 횡단(2차로 양방향 환산값)에서 이 규칙이 '무정차'로 센 도착 중 실제로 다 못 건너는 도착이 0.8m/s 50%, 1.0m/s 34%, 1.2m/s 23%다(도착이 초록 안에서 균일하다는 가정) [측정+계산].
6. **구조는 단일 HTML 산출을 유지하고 파일은 하나만 나눈다.** 순수 계산을 `src/core.js`(약 250줄 예상)로 뺀다. 번들러는 들이지 않는다(§3).
7. **"출입구 연결 35m"은 Codex가 추가한 규칙이다.** 이 체크아웃에는 없고, 대신 300m까지 말없이 붙인다. 쉬운 말과 3단계 처리(자동 / 거리 보여주고 확인 / 거절)는 §5.
8. **John 정의에서 기술적으로 무리한 것 3개:** 멈춤 횟수를 "내 걸음 때문에 달라지는 숫자"로 내세우는 것, 도착 시점 여유를 초 단위로 보이는 것, 성공 기준 3(±1 멈춤 현장 일치)을 데이터 문제 해결 전에 돌리는 것(§6).

| 같은 방위 | 앱 현재 방식(n→nt) | **−0.24** |

(`permissive-Movement-Allowed`가 녹색 점멸이고 점멸 시간이 횡단 길이/1.0m/s로 정해진다는 **전제가 서야** 해석이 된다. 그 전제 자체도 미확인이다. 전제가 거짓이면 이 상관은 아무 뜻도 없다. 다만 전제가 없을 때 "같은 방위"가 일관되게 음의 상관, 직각이 일관되게 양의 상관으로 부호가 뒤집힌 것은 우연으로 보기 어렵다.)

[가설] C-ITS의 `nt`는 "북쪽으로 걷는 사람의 신호"이고 앱의 `n`은 "북쪽 팔을 건넘"이라, 같은 이름이 서로 직각이다. 이 가설이 맞으면 남·북 팔의 횡단보도는 `et/wt`로, 동·서 팔은 `nt/st`로 찾아야 한다.

결과에 주는 영향 [측정]: 서울 중심 지하철역 45쌍(0.9~2.5km, 시드 고정)에서 33경로가 나왔다. 신호가 있는 횡단 145곳 중 '같은 방위'로 아는 곳 54.5%, '직각'으로 아는 곳 67.6%. **두 방식 모두 아는 72곳에서 초록/빨강 일치 69%, 멈춤 여부 일치 65%, 경로 25개 중 13개가 멈춤 횟수가 달라졌다.** 즉 지금 John의 "멈춤 N곳" 숫자는 이 가정 하나에 절반이 걸려 있다. 현장 또는 명세로 확정하기 전에는 정확하다고 쓰지 않는다.

**앱 연결 방식(가져온 뒤).**

**패턴 자체의 질.** 한 방향·시간대 안에 초록 창이 둘 이상인 곳이 1,781/10,947(16%)이다(경계에서 쪼개진 것 761개를 합친 뒤의 수) [측정]. 원인은 분석하지 않았다 [미확인]. 정적 여유를 계산할 때 어느 창을 쓸지 정해야 한다(§2-3: 도착 시각을 포함한 창).

### 2-2. 횡단보도 길이

**현재 그래프는 무엇을 갖고 있나 [코드·측정].** `scripts/sidewalks.py`가 큰길(`trunk/primary/secondary`, 4차로 이상 `tertiary`)의 중심선에서 `차로 수 × 3.2m / 2 + 1.5m`만큼 떨어진 양쪽 보도 노드를 잇는 선을 만든다(`offsets`, `LANE_M=3.2`). 이 선이 횡단보도 간선(`cls 5`)이고 길이는 `link()`가 `polylen`으로 구해 `round(L,1)`로 저장한다. 차로 수가 없으면 등급 기본값(`trunk/primary` 6, `secondary` 4, 링크 2)을 쓴다.

| 사실 | 값 |
|---|---|
| `cls 5` 간선 | 38,739개. 이 중 신호 연결(`sig` 있음) 25,751개, 3,616개 신호 묶음 |
| 양방향 한 선(`half=0`) | 9,932개 중앙값 15.8m, 분포 6.2~41.4m, 서로 다른 값 37가지, 상위 5개 값이 92.3% (15.8 / 22.2 / 9.4 / 12.6 / 6.2) |
| 일방통행 반쪽(`half=1`) | 15,819개 중앙값 11.6m, 서로 다른 값 89가지, 상위 5개 값이 92.5% |
| 신호 없는 `cls 5` | 12,771개: 중앙분리대 연결(최대 45m 반경으로 이음)과 'OSM 횡단보도 표시만' 있는 곳 |

즉 **측정값이 아니라 차선 수 환산이다.** 실제 횡단보도 길이(도로 폭, 사선, 보도 확장, 안전지대)와의 관계는 확인된 적이 없다. 독립 신호와 대어 본 결과도 약하다: 위 ⟨점멸 구간 길이⟩ 대조에서 같은 방위 기준 상관은 −0.09(전체)·−0.24(교차로 내부)였다. 다만 이것이 "길이가 틀려서"인지 "방향 대응이 틀려서"인지 "전제가 틀려서"인지는 **분리할 수 없다** [미확인].

**'추정'으로 쓰는 구체 방법 (가장 작은 변경).**

1. `buildRoute`에서 횡단 한 곳의 길이를 **묶음 합**으로 만든다. 지금은 `push(s, dir, d, at)`가 "같은 신호를 60m 안에서 또 건너면 한 번으로" 세기만 하고 길이를 버린다. 일방통행 도로는 반쪽 둘과 그 사이의 연결선(cls 5, 신호 없음)으로 쪼개져 있어, 첫 간선 길이만 쓰면 반쪽(평균 11.2m)만 센다. 최소 변경:

```js
// buildRoute 안. 기존 push를 길이 누적형으로 바꾼다.
const push = (s, dir, d, at, len = 0) => {
  const z = x.find(z => z.s === s && d - z.d < 60);
  if (z) { z.len += len; z.last = true; } else x.push({ s, dir, d, at, len, last: true });
};
let lastX = null;
for (const [u, v, e] of steps) {
  ...
  if (e.sig) { push(e.sig, e.dir, start, startAt, e.lenOff ?? e.len); lastX = x.find(z => z.s === e.sig); }
  else if (e.cls === 5 && lastX) lastX.len += e.lenOff ?? e.len;   // 중앙분리대 연결선도 이어서 더한다
  else lastX = null;
  ...
}
// 각 x에 길이 출처를 붙인다: 공식 매칭이 있으면 'ok', 없으면 'est'
```

2. 표기: 이 길이는 항상 `lenQ: "est"`, 출처 `"graph-lane"`. 화면의 '계산 기준'에는 "횡단 길이: 지도의 차로 수로 어림한 값"이라고만 적는다.
3. 한계를 코드에 박아 둔다: 묶음 합이 60m를 넘거나(경로 시험의 신호 횡단 묶음 145개 중 최대 61.4m, p90 36.2m) 중앙분리대 연결선이 들어가면 `lenQ`를 `"est"`로 유지하고 정적 여유(§2-3)를 **'모름'으로 내리는 상한**(`LEN_MAX_PLAUSIBLE_M`)을 둔다. 이 상한 값은 근거가 없어서 가정으로 표기한다.

한계 요약: 차선 환산(92%가 5개 값) / 사선·안전지대 미반영 / 중앙분리대 이음이 실제 횡단과 다를 수 있음(이음 반경 45m) / 두 단계로 건너는 큰길(보행섬)을 구분하지 못함 / 신호 없는 횡단보도(12,771개 중 일부)는 시간 계산에서 아예 빠짐.

**OA-21209 / OA-15554 를 나중에 붙이고 대조하는 방법.** (이 세션은 외부 호스트가 막혀 두 데이터셋을 받아 본 적이 없다. 컬럼·범위·좌표 품질은 전부 [미확인]이고, 아래는 받은 뒤 할 일의 설계다.)

1. **받기:** 사용자 PC 또는 키가 있는 환경에서 OA-21209(WGS84, 위치와 길이, 공공누리 1유형) 파일 또는 Open API 결과를 `datastore/crosswalk/` (Git 무시)에 저장. OA-15554는 EPSG:5186 좌표라 변환이 필요하고(`pyproj` 설치 여부 [미확인]), 길이 컬럼이 있는지는 테이블 정의서(hwpx)를 열어 봐야 안다.
2. **매칭:** `scripts/match_crosswalk_len.py` 새로 작성. 그래프의 신호 횡단 묶음마다 중점 M과 선 방향 θ를 구하고, 공식 레코드 중 **M에서 25m 이내**이며 (선 정보가 있으면) **방향 차이 25° 이내**인 가장 가까운 것 하나를 고른다. 레코드가 점이면 방향 조건은 못 쓴다. 25m·25°는 근거 없는 시작값이고, 수동으로 30곳을 확인해 조정한다(가정).
3. **출력:** `seoul/crosswalk-len.json` — `{"a:b":[길이m, "oa21209", 매칭거리m]}` (대상 최대 25,751개, 예상 수백 KB 텍스트). 앱은 `loadCell`에서 간선을 만들 때 `e.lenOff`로 붙인다(위 코드의 `e.lenOff ?? e.len`).
4. **대조 보고(합격 기준을 먼저 정한다):** 매칭률(신호 묶음 대비), 공식−그래프 차이의 중앙값·p90, 차선 수 등급별 편향. **'확인' 승격 조건:** 매칭 거리 ≤ 25m(방향 정보가 있으면 방향도), 공식 길이가 4~60m 범위일 것. 이 조건을 못 채우면 '추정' 유지. 매칭률이 낮으면(예: 절반 미만) "일부 횡단만 확인"으로 표기하고 전체를 확인이라 하지 않는다. 기준 수치는 첫 보고를 보고 사용자와 정한다.
5. **그래프 보정(선택):** 매칭된 쌍으로 차로 수별 실제 길이를 회귀해 `LANE_M`·여백을 고치면 **매칭 안 된** 횡단의 '추정'이 나아진다. 그 값은 계속 '추정'이다.
6. **두 공공데이터끼리도 대조:** 둘 다 매칭되면 서로의 차이도 기록해 신뢰도에 쓴다.
7. 기준연도(2020 표기)와 갱신일(2026.10.29 표기)이 섞여 있다는 문서 기록 때문에, 레코드의 기준 시점을 `crosswalk-len.json` 메타에 남긴다.

### 2-3. 횡단 여유 계산식과 '확인/추정/모름'

**용어를 먼저 정한다.** 06이 "횡단 여유"라고 한 숫자는 서로 다른 두 가지다.

- **정적 여유** `slack = G − L/v − s0`
  G = 도착 시각이 속한 **초록 창 하나의 길이**(경계를 넘어 쪼개진 두 조각은 합친다), L = 횡단 길이, v = 내 걸음 속도, s0 = 출발 지연(근거 없음 → 기본 0, 화면 '계산 기준'에만 노출). 도착 시각과 출발 시각에 의존하지 않는다. 길이와 속도와 신호 계획만으로 정해진다. Sally의 막대(전체 폭 = 초록, 칠한 부분 = 내가 건너는 시간, 남는 칸 = 여유)가 그리는 값이 바로 이것이다.
- **동적 여유** `margin = rem − L/v − s0`
  rem = 도착 시점의 남은 초록. 도착 시각이 몇 초만 달라도 부호가 바뀐다.

**왜 정적을 머리 숫자로 해야 하나.** 경로 위의 n번째 횡단 도착 시각은 앞의 모름 신호(평균 45초 가정, 실제로는 한 주기 안 어디든)와 걸음 속도 오차가 누적된다. 신호 주기가 130~190초대(시험 대상 1,747개의 중앙값 160초, p10 130초, p90 190초)이고 초록 창이 34초 안팎이라 [측정: 12,918개 창 중앙값 34초, p5 20초, p95 50초], 도착 시각이 ±20초만 틀려도 동적 여유는 의미가 사라진다. 정적 여유는 출발 시각 오차에 영향이 없다. 동적 여유는 (a) 걷는 중 GPS로 도착 시각이 몇 초 안으로 정해졌을 때, (b) 경로의 첫 횡단, (c) 앞에 모름이 없을 때만 쓴다. 도착 시각 불확실성은 `sigma_s`로 따로 들고, 20초(가정)를 넘으면 동적 여유를 숨긴다.

**`MIN_GREEN = 8` 고정의 문제 [측정+계산].** 지금 `sigWait`는 "초록이 8초 이상 남았으면 대기 0, 8초 미만이면 놓친 것"으로 센다. 8초는 사람의 걸음 속도와 횡단 길이를 모른다.

| 횡단 길이 | 내 걸음 | 필요 시간 | 초록 창이 아예 모자란 비율 | MIN_GREEN=8이 '대기 0'으로 센 도착 중 실제로 다 못 건너는 비율 |
|---|---|---|---|---|
| 15.8m (양방향 한 선의 가장 흔한 값) | 0.8m/s | 19.8초 | 4.0% | **50%** |
| | 1.0m/s | 15.8초 | 1.3% | **34%** |
| | 1.2m/s | 13.2초 | 1.0% | **23%** |
| 22.2m (6차로 환산) | 0.8m/s | 27.7초 | 22.9% | **77%** |
| | 1.0m/s | 22.2초 | 8.5% | **59%** |
| | 1.2m/s | 18.5초 | 3.2% | **45%** |
| 30m | 0.8m/s | 37.5초 | 67.3% | — |
| 44.5m (경로 시험에서 나온 값) | 1.0m/s | 44.5초 | 86.8% | — |

(마지막 열 계산: 도착이 초록 창 안에서 균일하다고 가정하고, 창 12,918개 각각에 `(필요시간−8)/(창길이−8)`을 평균. 창은 점등+점멸을 합친 길이이므로 '초록 끝' 기준이고, 점멸 중에는 건너기 시작하면 안 된다는 규칙을 적용하면 더 나빠진다.) 가장 느린 걸음이 가장 크게 틀린다. 정확히 John의 대상(걸음이 느린 사람)에게 가장 틀리는 숫자다.

한계: 점멸 구간을 따로 반영하지 못하는 것은 데이터 구조 때문이다. `win`은 `protected`(점등으로 추정)와 `permissive`(점멸로 추정)를 합쳐 초록으로 센다(`green = state.startswith(('protected','permissive'))`). 10/27 관측의 평균 구간 길이는 protected 11.8초, permissive 15.1초, 한 교차로 예시(정동 1537)는 점등 13초 → 점멸 23초였다 [측정]. **점멸 중에는 횡단을 시작하면 안 된다**는 규칙이 맞고 `permissive`가 점멸이 맞다면, 시작 가능 구간은 초록의 절반 이하일 수 있다. 법령 원문과 `permissive`의 정의는 둘 다 미확인이다. 데이터에 `win_steady`(점등 끝 시각)를 추가하면 풀리지만 14일 CSV.GZ로 다시 내보내야 한다(§4 S3). 그때까지는 정적 여유의 G가 "점등+점멸 합"임을 '계산 기준'에 쓰고, 값은 '추정'으로 둔다.

**속도 값 [문서].** 학술 자료에서 일반 1.0m/s, 교통약자 0.8m/s로 언급된다. 법령 원문·경찰청 매뉴얼은 확인하지 못했다(Mary §4). 이 문서도 확인하지 못했다. Codex의 프리셋은 0.9/1.2/1.4(천천히/보통/빠르게)다. 제안은 데이터 주도 프리셋 배열을 유지하되 값을 제품 쪽(John·사용자)이 정하게 하는 것이다:

| 안 | 값 | 득 | 실 |
|---|---|---|---|
| 유지 | 0.9 / 1.2 / 1.4 | 지금 시험·표기와 같다 | '천천히'가 참고값 0.8보다 빨라 느린 걸음의 여유를 낙관한다. 보통 1.2는 신호 설계 기준 1.0보다 빨라 여유가 크게 나온다 |
| 참고값 정렬 | 0.8 / 1.0 / 1.2 | 신호 설계 기준과 같은 기준으로 계산해 "설계상 여유"와 맞다 | 모든 도착 시간 예상이 길어진다(1.2→1.0이면 걷는 시간 +20%). 화면 시간 숫자가 바뀌어 기존 비교와 이어지지 않는다 |

이것은 제품 결정이다. 코드는 배열 하나만 바뀐다.

**단계적 도입(과한 재작성 금지).**
- 단계 A: `search`의 `sigWait`(= `MIN_GREEN`)와 멈춤 정의를 **그대로 둔다.** 경로 탐색·멈춤 횟수가 흔들리지 않는다. 정적 여유와 동적 여유를 **별도 필드로 추가**한다(`simulate`가 돌려주는 `xings[i]`에 필드만 추가).
- 단계 B: 방향 대응(R1)·길이(R3)가 정리된 뒤 `sigWait(s,t,dir,need)`로 `MIN_GREEN` 자리를 `need`로 바꾼다. 이때 멈춤 횟수가 늘어난다(내 7경로 시험에서 1.2m/s 기준 멈춤 합이 6 → 8로 늘었다, 표본이 작아 방향성만) [측정].

**데이터 구조: '확인/추정/모름'을 어디에 싣나.** 값마다 품질을 하나의 열거형으로 붙이고, 합칠 때는 가장 약한 쪽을 따른다(Sally의 규칙 5-3과 같음).

```js
// src/core.js (DOM 없음). 초 단위, 미터 단위.
const Q = { OK: "ok", EST: "est", UNK: "unk" };                 // 확인 / 추정 / 모름
const worst = (...qs) => qs.includes("unk") ? "unk" : qs.includes("est") ? "est" : "ok";
const CROSS = { START_LOSS_S: 0, SIGMA_MAX_S: 20, LEN_MAX_PLAUSIBLE_M: 60 }; // 전부 가정값. '계산 기준'에 그대로 노출
const DIR_MAP = "same";                                         // "same" | "perp". 현장 확인 전 기본값을 확정하지 않는다
const PERP = { n: ["e","w"], s: ["w","e"], e: ["n","s"], w: ["s","n"] };
function legFor(id, t, dir) {                                    // signalPlan 앞에 한 겹: 방향 대응을 한 곳에 격리
  if (DIR_MAP === "same" || !dir) return dir;
  return PERP[dir].find(d => signalPlan(id, t, d)) ?? null;
}
const dayType = date => [0, 6].includes(new Date(date + "T00:00:00+09:00").getDay()) ? "weekend" : "weekday";

// 횡단 한 곳의 근거. x = buildRoute가 만든 {s, dir, len, lenQ, halves}, t = 도착 시각(자정 기준 초), v = 내 걸음(m/s)
function crossingFacts(x, t, v, sigmaS, todayDate) {
  const dir = legFor(x.s, t, x.dir), r = dir === null ? null : signalPlan(x.s, t, dir);
  const need = x.len / v + CROSS.START_LOSS_S;
  const len = { m: Math.round(x.len * 10) / 10, q: x.len > CROSS.LEN_MAX_PLAUSIBLE_M ? Q.UNK : (x.lenQ || Q.EST), src: x.lenSrc || "graph-lane", halves: x.halves || 0 };
  if (!r) return { id: x.s, q: Q.UNK, why: "no-pattern", len, need };
  if (dayType(r.date) !== dayType(todayDate)) return { id: x.s, q: Q.UNK, why: "daytype-mismatch", len, need, patternDate: r.date };
  const st = sigState(x.s, t, dir), win = greenWindow(r, t);   // win: 도착 시각이 속한(또는 다음) 초록 창 하나의 길이
  const slack = win - need;
  const margin = st.g && sigmaS <= CROSS.SIGMA_MAX_S ? st.rem - need : null;
  return {
    id: x.s, q: worst(Q.OK, len.q),                            // 길이가 추정이면 여유도 추정
    signal: { q: Q.OK, kind: "history", date: r.date, holdout: r.holdout_accuracy, observedMin: r.observed_min, daytypeMatch: true },
    len, speed: v, need, green: { now: st.g, rem: st.rem ?? null, window: win },
    wait: sigWait(x.s, t, dir),                               // 단계 A: MIN_GREEN 규칙 그대로
    slack, margin, sigmaS,
  };
}
// 경로 요약: 06·07이 쓰는 숫자 두 개 + 모름을 합산하지 않는 규칙
function summarize(facts) {
  const known = facts.filter(f => f.q !== Q.UNK);
  return {
    stops: { n: known.filter(f => f.wait > 2).length, unk: facts.length - known.length, of: facts.length }, // '멈춤 n곳 · 모름 m곳'
    tightest: known.length ? known.reduce((a, b) => a.slack <= b.slack ? a : b) : null,                 // '가장 빠듯한 횡단': 추정이면 q 'est'
  };
}
```

그리고 `greenWindow(r, t)`는 경계를 넘어 쪼개진 조각(예: `[[138,140],[0,31]]`, 구 `REAL`의 2691번이 이 모양)을 합쳐서 계산해야 한다. 안 합치면 33초 창이 2초로 계산된다. 내 데이터 점검에서 쪼개진 것이 761개(7%)였다 [측정]. 단위 시험 1순위다.

멈춤 횟수의 품질 표기: 신호 패턴이 있고 요일이 맞으면 '확인'(과거 이력 기준, 방향 대응은 가정), 아니면 '모름'으로 분류해 숫자에 합산하지 않는다. 방향 대응이 확정되기 전까지 "확인" 표기는 `signal.q`에 `assumption: "dir-map"`을 같이 달아 '계산 기준'에서 밝힌다(Sally 5-3의 '가정' 단어 규칙과 같은 층).

`state`(전역 객체 하나)·계산(`core.js`)·화면(`render*`)의 구분은 이미 코드에 있다. 파일로 나누는 건 계산 하나만 한다. 화면이 1,000줄을 넘지 않는 한 `render*`를 더 쪼개지 않는다.

**생성물 어긋남 방지(권고, 작음).** `index.html`은 생성물이고 Vercel이 그대로 서빙한다. CI에 두 줄을 더하면 "소스만 고치고 다시 안 만든" 사고를 막는다: `python scripts/build_prototype.py && git diff --exit-code docs/prototype/index.html`. 아직 CI에는 없다 [코드: `.github/workflows/ci.yml`은 pytest만].

**아티팩트/정적 호스팅 제약 [문서·코드].** 아티팩트 호스팅이 바이너리를 받지 않아 타일·글리프를 base64 `.txt`로 두었고 `fetchB64`가 푼다. 이 방식은 건드리지 않는다. 새로 추가하는 데이터(`signal-hours`, `crosswalk-len.json`)는 JSON 텍스트라 문제 없다. 아티팩트 도구 설명상 한 버전 511파일·256MB, 텍스트 파일 하나 16MB까지다. 이 앱은 402파일/약 100MB(전부 가져올 때) 또는 약 381파일/73MB(권고안)로, 한도 안이지만 **실제로 게시해 보지는 않았다** [미확인]. 게시 위치 결정(Vercel/아티팩트)은 이 문서 범위 밖이다.

  3. 맞는 쪽이 정해지기 전에는 화면에 "신호 방향은 가정" 표기를 유지한다.

**R2. 다른 날 패턴을 오늘에 쓰는 가정(요일 포함).**

**R3. 횡단 여유의 두 입력, 길이와 초록의 뜻.**

## 5. '출입구 연결 35m' 쉬운 설명과 안전한 처리

### 5-1. 쉬운 설명 (사용자에게 그대로 쓸 수 있는 말)

> 앱은 지도에 찍은 점으로 바로 길을 찾지 않고, **걸어갈 수 있는 길(보도·횡단보도)** 위에서만 길을 찾아요. 그래서 먼저 "내가 고른 곳에서 가장 가까운 걸을 수 있는 길"을 찾아 거기에 점을 붙여요.
> 그런데 고른 곳이 건물 안이나 학교 운동장, 아파트 단지 안이면 가장 가까운 길이 꽤 멀 수 있어요. 지금 앱은 **35m**(대략 큰 횡단보도 두 개를 이은 길이)가 넘으면 "엉뚱한 길에 붙여서 틀린 길을 안내하지 않으려고" 멈추고 "출입구 가까이에서 골라 주세요"라고 말해요.
> 즉 "출입구 연결 35m"는 **"고른 곳과 걸을 수 있는 길 사이를 앱이 알아서 이어 줘도 되는 최대 거리가 35m"**라는 뜻이에요.

사용자가 본 문구는 결과 화면 맨 아래 안내(`#result-safety`, `new:982`)의 "출입구 연결 35m 이내도 현장 확인이 필요해요"다. 이 문장은 그 시점엔 해당 없는 사람에게도 항상 뜬다. **고치는 방법:** 고정 안내에서 빼고, 연결 거리가 실제로 있을 때만 "출발은 지도 점에서 길까지 약 NNm를 걸어 시작해요"로 보인다.

**헷갈리지 않게: 코드에 35m가 두 개 있다.** 위의 것은 앱이 사용자의 점을 길에 붙이는 한계(`snap`, `new:288`, `new:737`)다. 다른 하나는 지도 데이터를 만들 때 **신호 교차로 중심에서 35m 안 노드를 그 신호로 센다**는 규칙(`scripts/build_seoul_map.py` 289행 `near(lon, lat, 35)`, 결과 화면 `note`에도 적혀 있다)이다. 서로 무관하다. 사용자가 물은 것은 앞의 것이다.

### 5-2. 현재 동작과 측정

| | 구(이 체크아웃) | 신(Codex) |
|---|---|---|
| 붙이는 방식 | 가장 가까운 **노드**(`snap` old 105-117) | 가장 가까운 **간선 위 점**(투영) + 간선 분할(`new:276-312`) |
| 먼 점 | 300m까지 말없이 붙임(`computeTrip`의 `a.d>300`) | 35m 넘으면 멈춤 |
| 문제 | 300m 멀리 있는 길에 말없이 붙어 시간을 틀리게 보임 | 너무 빡빡 |

[측정] 장소 검색 데이터 15종류에서 총 1,452곳을 종류별로 간격 추출해 `snap`을 돌렸다(전수 아님, 종류별 80~140곳):

| 보행로까지 거리 | 곳 수 | 비율 |
|---|---|---|
| 35m 이하(자동) | 1,260 | 86.8% |
| 35~60m | 139 | 9.6% |
| 60~100m | 45 | 3.1% |
| 100~200m | 7 | 0.5% |
| 200m 초과 | 1 | 0.1% |

종류별로 35m 초과 비율이 크게 다르다: 학교 63%(중앙값 40m), 쇼핑 30%, 동네 22%, 대학교 16%, 주민센터 11%, 시장 10%, 명소 10%, 역 5%. 지하철역 쌍 실험에서도 독립문역·서울역·신촌역 3곳이 "출입구 가까이에서 골라 주세요"에 걸렸다. 35m를 넘은 192곳 중 184곳은 100m 이내다 [측정]. 표본은 종류별 균등에 가깝지 실제 검색 빈도와 다르다 [미확인].

### 5-3. 안전한 처리 (3단계, 코드 수준)

원칙: 말없이 붙이지 않는다(구 방식 폐기). 멀면 **거리를 보여 주고 사용자가 확인**한다. 너무 멀면 거절한다. 35m와 100m는 상수로 이름 붙인다: 35m는 Codex가 정한 값(근거 문서 없음), 100m는 위 표본의 분포에서 나온 시작값이다. 둘 다 [가정].

```js
// core.js
const LINK = { AUTO_M: 35, ASK_M: 100 };
const linkTier = d => d == null ? "none" : d <= LINK.AUTO_M ? "auto" : d <= LINK.ASK_M ? "ask" : "refuse";

// app.js snap(): 반환값에 붙은 점과 거리를 추가한다. 현재는 35m 넘으면 {id:null, d}만 돌려줘 점 위치를 잃는다.
//   return { id, d, pt: point, tier: linkTier(d) };      // pt = 보행로 위 가장 가까운 점([lon,lat])
// snap의 "best > 35 이면 id:null" 분기는 없애고 항상 가장 가까운 점을 돌려준다(단 후보 간선이 하나도 없으면 none).
```

```js
// computeTrip 안, 지금의 a.id==null||b.id==null||a.d>35||b.d>35 한 줄을 이렇게 바꾼다
const a = snap(state.from.ll), b = snap(state.to.ll);
state.link = { from: a, to: b };
const bad = [["from", a], ["to", b]].find(([, s]) => s.tier === "none" || s.tier === "refuse");
if (bad) {
  state.error = { title: "가까운 길을 못 찾았어요",
    text: `${bad[0] === "from" ? "출발" : "도착"} 위치에서 가장 가까운 보행로가 ${bad[1].d != null ? "약 " + Math.round(bad[1].d) + "m" : "너무"} 멀어요. 지도에서 출입구나 길 가까이를 다시 골라 주세요.`,
    focus: bad[1].pt ?? null };                       // 지도에서 가장 가까운 점을 보여 준다
  return;
}
const ask = [["from", a], ["to", b]].find(([k, s]) => s.tier === "ask" && !state.linkOk?.[k + ":" + s.id]);
if (ask) {                                             // 확인 단계: 결과를 만들지 않고 시트를 띄운다
  state.pendingLink = { which: ask[0], d: Math.round(ask[1].d), pt: ask[1].pt };
  state.tripKey = null; return;                        // 확인 후 같은 함수를 다시 부른다
}
```

확인 시트 문구(한 화면, 글 적게):

```
출발 위치에서 가장 가까운 길은 약 60m 떨어져 있어요.
건물이나 단지 안일 수 있어요.
[이 길에서 시작]   [지도에서 다시 고르기]
```

- "이 길에서 시작"을 누르면 `state.linkOk[...] = true`로 두고 `computeTrip`을 다시 부른다. 선택은 `tripKeyNow()`에 포함해 캐시가 잘못 재사용되지 않게 한다.
- `search()`는 이미 `entry = distLL(state.from.ll, 붙은 노드)/SPEED`를 시작 비용에 더한다 [코드 `new:317`]. 확인한 거리만큼 시간이 더해진다는 뜻이다. 이 구간은 지도 점→보행로 **직선**이라 장애물을 모른다. 결과의 도착 예상에 `'처음 60m는 길 밖 직선 · 추정'`을 붙이고(품질 `est`), 지도에는 점→붙은 점을 점선으로 그린다.
- 결과 요약에는 연결 거리를 `link: { m, tier, confirmed }`로 둔다. 35m 이하는 숫자를 숨기고(`auto`), 확인한 것은 숫자와 '확인함'을 보인다.
- GPS 시작점은 오차까지 본다: `tier`를 `d`가 아니라 `d + accuracy` 로 계산하면 "내 위치" 오차가 50m인 사람이 말없이 자동 통과하지 않는다(가정).

시험: VM에서 합성 간선 위 20m/60m/150m 점이 각각 `auto/ask/refuse`. Playwright에서 `학교` 좌표로 시트가 뜨고 확인 후 경로. 지금 실패하는 `check_walk_browser.cjs`는 가짜 GPS 시작점을 보행로 위로 옮겨 고친다.
