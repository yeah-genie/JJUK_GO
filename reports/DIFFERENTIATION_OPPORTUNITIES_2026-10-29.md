# 차별화 기회 조사 — 세 후보와 첫 실험

2026-10-29. 사용자 요청: 기존 지도앱의 편한길과 겹치는 문제를 넘어 차별화 포인트를 에이전트들과 조사. 이전 보고서의 문제 진단을 반복하는 대신 보행 특화 경쟁 서비스·사용자 문제·현재 구현 가능성을 넓혀 검토했다.

**추천 후보는 ‘원래 걷던 길에서 불편한 구간 하나만 바꾸기’다.** 새로운 독점 기술이라는 뜻은 아니다. 허용시간 안에서 익숙한 나머지 동선을 최대한 보존하고, 무엇을 피하고 무엇이 늘었는지 이해하기 쉬운 사용 흐름으로 선택받을 수 있는지 검증한다. 현재 앱에는 이 흐름이 구현되어 있지 않다. 사용자 최종 제품 방향/브랜드 확정으로 해석하지 않는다.

## 조사 방식과 실제 역할

- `opportunity_users`: 사용 상황·행동 연구·실제 선택 이유·재사용 반론.
- `opportunity_competitors`: 국내 범용 지도와 보행 특화/해외 제품의 공식 기능.
- `opportunity_feasibility`: 기존 그래프/신호/지형으로 가능한 최소 실험과 자료 한계.
- 주 에이전트: 공통 방향 대조, 공식 자료 추가 확인, 후보 통합·GitHub 기록.

세 에이전트가 직접 의견을 교환했다. 사용자 담당의 국소 수정 가설에 개발 담당이 현재 그래프 활용 가능성과 원래 길 확인 필요를 보탰고, 경쟁 담당이 OsmAnd의 특정 도로 회피를 찾아 고유 기능 주장을 반박했다. 따라서 추천은 ‘구간 회피 발명’에서 **시간 한도·익숙한 동선 보존·불편 교환 설명을 쉽게 수행하는 좁은 사용 작업**으로 한정했다. 실제 한국 사용자 인터뷰·현장 보행·소비자 앱 사용성 비교는 이번에 수행하지 않았다.

## 사용자의 문제에 대한 근거와 빈칸

[Transport for All의 당사자 조사 요약](https://www.transportforall.org.uk/the-issues/journey-planning/)은 이동에 필요한 시설·휴식·접근 정보의 부족과 부정확한 정보 문제를 다룬다. [보행/휠체어 이동 조사](https://www.transportforall.org.uk/the-issues/active-travel/walking-and-wheeling/)는 보도 장애물 때문에 되돌아가거나 우회하는 부담을 다룬다. 영국의 장애 당사자 맥락이며 서울 일반 보행자의 비율이나 앱 수요로 일반화할 수 없다.

사용자 담당은 [계단/에스컬레이터 선택 관찰 연구](https://onlinelibrary.wiley.com/doi/10.1155/2014/965305)에서 높이·시설 구조·휴대짐이 선택 모델의 변수로 다뤄진 점을 확인했다. 베이징 환승역 연구이며, 서울의 짐 모드 수요나 지불 의사를 입증하지 않는다. 개별 불편이 상황마다 달라질 수 있다는 문제 근거와 특정 앱 기능의 수요 증거는 구분한다.

한국 사용자에게 세 후보가 실제 유용한지, 어느 후보가 경쟁 앱보다 쉬운지, 유료로 쓸지는 아직 모른다. 좋아요/기술 호기심을 수요 근거로 대체하지 않는다.

## 후보 1 — 원래 길의 불편한 구간만 바꾸기

**사용 상황:** ‘집 가는 길은 아는데 저 계단/언덕 하나만 피하고 싶다. 2분까지만 더 걸을 수 있다.’

처리할 작업:

1. 사용자가 확인한 원래 길을 보여준다. 최단길을 사용자의 평소 길이라고 추정하지 않는다.
2. 바꾸고 싶은 구간 하나를 선택한다. 초기에는 확인된 샘플 경로의 계단/언덕을 고르게 해 복잡한 지도 그리기를 피한다.
3. 추가시간 한도 안에서 그 구간을 피하고 기존 길에 복귀하는 대안을 찾는다.
4. 바뀐 부분·복귀 지점·추가시간·새로 늘어난 불편을 함께 보여준다. 원래 길을 유지하는 선택도 제공한다.

화면 설명용 가상 예시: ‘이 계단 구간을 피해요 / 예상2분 추가 / 신호1곳 증가 / 다음 교차로에서 원래 길에 합류’. 실제 계산/개선 성과가 아니다.

**검증할 차별 포인트:** 익숙한 경로 전체를 새로 익히지 않아도 원하는 불편 하나를 해결하는가. 경쟁 앱의 경유지 편집·도로 회피보다 입력이 쉽고 결과를 이해하기 쉬운가. 총시간 한도와 나머지 경로 보존을 함께 지키는가. ‘세계 최초’가 아닌 특정 작업에서 선택받는 사용 경험의 가설이다.

**현재 자료와 맞는 이유:** 불편을 사용자가 지정하므로120m 지형으로 신체 부담을 자동 판정할 필요를 일부 줄인다. 기존 OSM 그래프를 활용할 수 있어 새 대용량 ZIP 수집부터 시작할 필요가 없다. 다만 원래 길 확인, 실제 구간 제외, 복귀 조건, 전체 경로 재계산이 필요하다. 기존 세 가중치 후보 비교의 점수만 바꿔서는 구현되지 않는다.

**버릴 조건:** 원래 길 입력이 번거롭거나 경쟁 앱으로 더 쉽게 해결되는 경우, 대안이 늘 이미 아는 길인 경우, 우회가 다른 큰 불편을 만들거나 나머지 동선을 지나치게 바꾸는 경우. 좋은 길 한 번 발견 뒤 재사용이 없으면 일회성 가치와 반복 사용 사업성을 분리한다.

## 후보 2 — 실제 들어갈 문까지 확인한 접근 경로

**사용 상황:** ‘목적지 근처에는 왔는데 계단 없는 문이나 실제 들어갈 수 있는 입구가 어느 쪽인지 모르겠다.’

특정 지역의 목적지10곳 안팎에 실제 입구·연결 보행로·계단·통행 조건·확인일을 남기는 실험이다. 지역/입구별 확인 근거를 보여주며, 새로 확인하지 않은 자료를 오늘 확인된 것처럼 표시하지 않는다. 시설 운영자와 정보 유지 협력을 검토할 수 있지만 기관/장소의 지불 의사는 미확인이다.

**차별 가설:** 목적지 좌표 도착 뒤 생기는 되돌아감과 불확실성을 줄이는 지역 단위 정보 품질. 범용 지도도 입구·실내 안내를 제공하므로 입구 표시 자체는 고유하지 않다.

**한계:** 기존35m 보행로 연결은 실제 문 통행 확인이 아니다. [서울 도보 네트워크](https://data.seoul.go.kr/dataList/OA-21208/A/1/datasetView.do) 설명의 원자료 기준과 최신성을 구분해야 한다. OSM [입구 태그](https://wiki.openstreetmap.org/wiki/Key:entrance) 존재도 실제 서울 자료의 완전성을 뜻하지 않는다. 현장 조사·시간대·폐쇄 여부를 계속 관리할 운영 비용이 크다. 계단 없음/무장애/항상 개방 보장을 먼저 약속하지 않는다.

**우선순위:** 후보1에서 실제로 중요한 목적지 몇 곳의 품질 보강으로 작게 시작할 수 있다. 서울 전체의 별도 입구 서비스는 지금 권하지 않는다.

## 후보 3 — 부담이 한 번에 몰리지 않는 길

**사용 상황:** ‘총 오르막이 조금 있어도 괜찮지만 긴 언덕을 한 번에 계속 오르기는 부담스럽다.’

누적 상승량 외에 연속 오르막/계단 길이와 그 사이의 완만한 구간, 확인된 휴식점을 보여주는 가설이다. 더 오래 걸어도 연속 부담을 나누는 경로를 실제로 선호하는지 검증한다. 수치로 의료적 피로나 안전을 판정하지 않는다.

**차별 가설:** 불편의 합계뿐 아니라 어디에 얼마나 이어지는지를 선택 기준으로 삼는 경험. 기존 경사 프로필/접근성 서비스와도 겹치므로 연속 부담 기능의 독점성을 주장할 수 없다.

**한계와 보류 이유:** 현재120m 지형으로 짧은 급경사·계단·평탄 구간을 신뢰성 있게 나눌 수 없다. [OSM 벤치](https://wiki.openstreetmap.org/wiki/Tag:amenity=bench)는 실제 앉을 수 있고 접근 가능한 휴식점의 보증이 아니다. 현장 표본과 수요 확인 전 주요 기능으로 내세우지 않는다.

## 우선순위 판단

| 후보 | 현재 구현 가능성 | 핵심 검증 부담 | 권고 |
|---|---|---|---|
| 불편 구간 하나만 바꾸기 | 기존 그래프로 좁은 데모 가능 | 기존 길 입력 부담, 우회 선택, 경쟁 사용성 비교 | **첫 실험** |
| 실제 입구 접근 확인 | 소수 목적지는 수동 검증 가능 | 지속 현장 관리·개방 조건·신뢰성 | 첫 실험의 지역 품질 보강 |
| 연속 부담을 나누기 | 현재 지형만으로 부족 | 정밀 구간 조사·휴식점·체감 선택 검증 | 연구 후보로 보류 |

단순한 짐 모드/개인화 모드, 그늘 옵션, 경로 저장 추가는 단독 차별 전략에서 제외한다. 상황별 수요가 있을 수 있어도 이미 많은 회피/선호 옵션과 겹치기 때문이다. 공사·날씨·혼잡·신호를 모두 실시간으로 반영하는 약속도 현재 데이터로 실행할 수 없다.

## 후보1의 첫 검증 설계 — 제안

- 실제 불편 한 구간이 분명한 경로2~3개를 먼저 선정한다. 선정·현장 확인은 아직 수행하지 않았다.
- 실제 사용자가 원래 걷는 길, 네이버/카카오의 해당 선호 최선 옵션, 구간 회피가 가능한 경쟁 도구, 쭉고의 수정 후보를 비교한다. 경쟁 앱의 기본값만 상대하지 않는다.
- 원래 길 확인과 구간 선택을 도움 없이 할 수 있는지, 기존 도구보다 조작 부담이 적은지, 어떤 부분이 바뀌는지 이해하는지 측정한다.
- 현장에서 피하고 싶은 구간이 실제로 빠졌는지, 허용 추가시간 안에 드는지, 새로운 부담이 생겼는지 확인한다. 예측상 우회시간과 실제 우회시간을 구분한다.
- 실제 길을 바꿨는지와 같은 상황에서 다시 선택할지를 기록한다. 소수 탐색 실험으로 모집단의 수요나 유료 전환을 주장하지 않는다.
- 충분한 이득이 없으면 후보를 보류하거나 수정한다. 새로운 슬로건으로 성공처럼 포장하지 않는다.

개발 담당의 좁은 데모 공수 추정은 후보1 약3~5개발일, 후보2 데이터 틀 약3~5개발일, 후보3 약5~10개발일이다. **현장 검수·사용자 검증·운영·출시 일정은 제외한 가정적 추정**이며 확정 일정이 아니다. 개인속도/걷기 ETA 일치, 미확인 경사의 유리한 순위 처리 방지는 어느 후보에서도 선행 또는 병행해야 한다.

## 현재 수행 상태

이번에는 조사·독립 검토·교차 반박·제안 기록만 했다. 기능 구현, 신규 API 연결, 새 파일 대량 다운로드, 사용자 모집, 외부 메시지 발송, 앱 재배포를 하지 않았다. 기존 ‘비슷한 시간이면 덜 힘들게’ 방향과 보행 우선/버스·지하철 후순위는 유지한다. 후보1은 추천이며 사용자 최종 확정과 구분한다.
