# 편한 길 UI — 개발·QA 독립 검토

2026-10-29 · BMAD 개발·QA 관점의 별도 에이전트 검토. 대상은 현재 작업 중인 `docs/prototype/src/app.js`, `template.html` 변경이다. 부모 에이전트와 화면 제어가 충돌하지 않도록 브라우저·Playwright·배포 작업은 수행하지 않았다. 소스는 수정하지 않았다.

## 결론

코드에서 확정할 수 있는 배포 차단급 런타임 오류는 발견하지 못했다. 이전의 중간 높이 스크롤 금지 규칙을 제거하고, 내용과 걷기 버튼을 서로 다른 flex 영역으로 나눈 방향은 사용자 신고에 맞다. 다만 아래 두 연결부는 새 UI 구조에 맞춰 정리하는 것이 좋다. 실제 터치 스크롤이 해결됐다는 최종 판단에는 부모 에이전트의 브라우저 확인과 사용자 기기 확인이 필요하다.

## 발견 사항

### P2. 접힌 출발 시각 각주를 ‘보이는 안내’로 취급한다

`renderGoCard()`는 시뮬레이션이 있으면 `go-wrap.hidden = false`로 만든다. 이제 이 요소는 기본적으로 닫힌 `departure-options` 안에 있다. 그런데 `renderResult()`의 `cov-note`는 여전히 `!go-wrap.hidden`을 보고 숨겨진다. 카드가 실제로 보이지 않아도, 그 각주가 대신 설명한다고 판단하는 이전 조건이 남았다.

기본 결과에도 가정 안내가 있고 `route-facts`에도 미확인 수가 있으므로 모든 불확실성이 사라지는 문제는 아니다. 다만 상세의 짧은 안내가 의도 없이 항상 생략된다. 조건을 중복 없이 단순화하거나 실제 출발 정보 공개 상태를 기준으로 판단해야 한다.

### P2. 터치 태블릿의 오른쪽 패널과 지도 여백 계산이 다르다

`@media (min-width:700px) and (any-pointer:coarse)`는 패널을 오른쪽 폭460px로 옮긴다. 그러나 `fit()`은 계속 `bottom: sheetH() + 30`, `right:64`로 아래 패널을 가정한다. 왼쪽의 넓고 높은 지도 공간이 남는데도 위쪽의 짧은 영역에 경로를 맞추게 된다.

경로 데이터가 틀리는 오류는 아니지만, 사용자가 신고한 태블릿에서 지도를 충분히 활용하지 못하는 연결 문제다. 오른쪽 패널이 실제 적용되면 그 폭만큼 오른쪽 여백을 두고 아래 여백은 작게 계산하는 것이 일관적이다. 일반 전화기·데스크톱 폰 프레임에는 기존 아래 패널 계산을 유지해야 한다.

## 현재 변경에서 확인한 점

- `.sheet-body`: `flex:1 1 0`, `min-height:0`, `overflow-y:auto`, `touch-action:pan-y`로 실제 내용 스크롤 영역을 명시했다. 이전 `.sheet:not(.full) .sheet-body { overflow:hidden }` 규칙은 제거됐다.
- `.sheet-footer`: 스크롤 내용의 형제이며 `flex:none`이다. 중간/전체 높이에서 버튼이 내용과 함께 밀려 내려가지 않는 구조다.
- 결과 시트는 내용의 가변 높이로 중간 높이를 다시 추정하지 않고 화면 높이에 비례한 중간/전체 높이를 쓴다. 상세 내용이 늘어나면 내부 스크롤로 처리한다.
- 접힌 `peek` 상태는 콘텐츠 대부분과 footer를 숨긴다. 따라서 ‘걷기 버튼 고정’은 현재 중간/전체 상태에 해당한다. 모든 패널 상태에 항상 버튼을 보여주겠다는 완료 기준이라면 이 상태를 따로 결정해야 한다.
- 패널 조절 손잡이에 키보드 초점·역할·Enter/Space 동작을 추가했다. 시각적인 ‘올려서 비교’ 문구는 코드에서 제거됐다.
- 출발 카운트다운을 없애고 출발 요약을 별도 접힘 영역으로 옮겼다. 기본 화면의 추가시간 선택은 계단·오르막 후보 비교에 연결된다.
- `comfortCopy()`는 계단/경사에서 불리해진 차이도 본문에 쓴다. 같은 경로이면 더 편해졌다고 꾸미지 않는다. 다만 지형 추정의 정확도가 좋아졌다는 뜻은 아니다.

## 직접 실행한 확인

- `node --check docs/prototype/src/app.js`: 통과.
- `node scripts/check_walk_logic.cjs`: 통과. 기존 시간/지도/GPS 회귀 검사와 편한 길 문구 검사 포함.

브라우저 테스트 파일은 읽었으나 실행하지 않았다. Node 검사는 CSS 레이아웃·터치 제스처를 검증하지 않는다.

## 부모 에이전트의 별도 브라우저 증거

아래는 독립 검토자가 직접 수행한 검사가 아니라, 화면 제어를 맡은 부모 에이전트가 전달한 CUA 확인 결과다.

- 브라우저 배율67%에서 물리 표시261×565, CSS viewport390×844를 확인했다.
- 결과의 `.sheet-body`는 `overflow:auto`, `touch-action:pan-y`였다.
- 상세를 펼쳤을 때 `scrollHeight:766`, `clientHeight:648`이었고, 브라우저 스크롤 동작 뒤 `scrollTop:117.01`을 확인했다. 해당 화면에서 내부 스크롤 가능성을 뒷받침한다.
- footer의 걷기 버튼이 폰 영역 안에 있는 것을 확인했다.

실제 Android 터치와 `any-pointer:coarse` 태블릿 분기는 아직 실기기로 검증하지 않았다. 부모는 위 두 P2의 수정 예정 사항을 공유했다. 이 보고서의 발견 사항은 수정 전 검토 결과이며, 수정 완료·재검증의 증거로 취급하지 않는다.

## 화면 확인 완료 기준

1. 320×667, 390×844에서 중간 높이 상태의 시트 내용을 실제 휠/터치 제스처로 이동했을 때 `scrollTop`이 증가해야 한다. 걷기 버튼은 같은 위치에 남아야 한다.
2. 기본 상세와 선택 출발 비교를 모두 연 뒤 가장 아래 추정 기준에 도달할 수 있어야 한다. 닫기·예산 변경 후에도 스크롤이 다시 막히지 않아야 한다.
3. 1280×800 터치 태블릿에서 폰 장식 테두리가 없어지고 오른쪽 패널과 지도 경로가 함께 보이는지 확인해야 한다. 단순 폭 변경만으로 `any-pointer:coarse` 검증을 대신하지 않는다.
4. 2시간 이상 소요시간, 긴 목적지명, 두 경로 카드, 추가시간0/2/5/10분을 확인한다. 가로 넘침이나 버튼/설명의 잘림이 없어야 한다.
5. 로딩/오류에서는 이전 경로의 걷기 버튼이 남지 않아야 한다. 정상 결과로 돌아오면 버튼이 복구돼야 한다.
6. 같은 경로/다른 경로/시간 우선 선택 각각에서 문구와 카드 선택이 맞아야 한다. 첫 화면에는 출발 카운트다운과 불필요한 조작 안내가 없어야 한다.

실제 Android 태블릿의 터치·브라우저 확대·주소창 높이 변화는 이번 독립 검토에서 측정하지 않았다.
